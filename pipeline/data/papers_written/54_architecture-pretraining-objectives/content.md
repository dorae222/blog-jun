## 개요

"What Language Model Architecture and Pretraining Objective Work Best for Zero-Shot Generalization?"(Wang et al., 2022, ICML)는 Hugging Face와 여러 기관의 Thomas Wang 등이 발표한 연구로, LLM 설계의 두 핵심 축인 **아키텍처 선택**과 **사전학습 목표 선택**이 제로샷 일반화에 미치는 영향을 최초로 **통제된 비교 실험**으로 분석한 논문이다.

이 연구 이전에는 GPT 계열(디코더-온리 + CLM)과 T5 계열(인코더-디코더 + MLM) 등이 각각 독립적으로 개발되고 서로 다른 데이터, 규모에서 학습되어, 아키텍처와 사전학습 목표 중 어느 요인이 성능에 더 영향을 미치는지 명확하지 않았다. 이 논문은 **동일한 데이터, 동일한 파라미터 수, 동일한 학습 예산** 하에서 조합을 비교하여 공정한 비교를 달성했다.

이 연구는 BigScience 프로젝트의 일환으로 수행되었으며, 이후 176B 파라미터 [[BLOOM]] 모델의 아키텍처 결정에 직접적인 영향을 미쳤다. 또한 공개된 [[T0]] 모델은 오픈소스 커뮤니티에서 널리 활용되었다. 논문의 핵심 질문은 단순하지만 강력하다: "모든 조건을 동일하게 맞춘다면, 어떤 아키텍처와 사전학습 목표의 조합이 제로샷 일반화에 가장 효과적인가?" 이 질문에 체계적으로 답함으로써, LLM 설계에서 경험적 직관에 의존하던 의사결정을 실증적 근거로 대체하고자 했다.

## 배경 및 문제

### 제로샷 일반화의 중요성

제로샷 일반화(zero-shot generalization)란, 학습 시 한 번도 보지 못한 태스크에 대해 별도의 학습 없이 수행하는 능력을 말한다. [[GPT-3]](Brown et al., 2020)가 이 능력을 대규모로 보여준 이후, 제로샷 성능은 LLM 평가의 핵심 지표가 되었다.

그러나 GPT-3의 성공이 **디코더-온리 아키텍처** 덕분인지, **자동회귀(CLM) 사전학습** 덕분인지, 아니면 단순히 **모델 크기(175B)** 덕분인지 분리하기 어려웠다. [[T5]](Raffel et al., 2020)는 인코더-디코더 + Span MLM 조합으로도 강력한 성능을 보여주었기 때문이다.

제로샷 일반화가 중요한 이유는 실용적 측면에서도 명확하다. 새로운 태스크가 등장할 때마다 대규모 라벨 데이터를 수집하고 파인튜닝하는 비용은 막대하다. 제로샷으로 다양한 태스크를 처리할 수 있다면, 모델 배포의 유연성과 비용 효율성이 극적으로 향상된다. 이는 범용 AI 시스템을 향한 핵심 역량이기도 하다.

### 기존 비교의 한계와 혼재 변수 문제

기존 모델 간 비교의 문제점을 정리하면 다음과 같다:

| 요인 | GPT-3 | T5-11B | BERT-Large |
|------|-------|--------|------------|
| 아키텍처 | 디코더-온리 | 인코더-디코더 | 인코더-온리 |
| 사전학습 목표 | CLM | Span MLM | MLM + NSP |
| 파라미터 수 | 175B | 11B | 340M |
| 학습 데이터 | 300B 토큰 | 750GB C4 | 16GB |
| 학습 FLOPs | ~$10^{24}$ | ~$10^{23}$ | ~$10^{20}$ |

이처럼 여러 변수가 동시에 다르기 때문에, 성능 차이의 원인을 특정 요인에 귀속시키기 불가능했다. 예를 들어, GPT-3가 BERT보다 제로샷 성능이 우수하다고 해서 "디코더-온리가 인코더-온리보다 우수하다"고 결론 짓는 것은 파라미터 수(175B vs 340M), 학습 데이터(300B 토큰 vs 16GB), 학습 목표(CLM vs MLM+NSP)의 차이를 모두 무시하는 것이다.

이러한 **혼재 변수(confounding variable)** 문제는 LLM 연구에서 반복적으로 나타나는 근본적 한계였다. 새로운 모델이 발표될 때마다 "이전 모델보다 좋다"는 주장은 있었지만, 정확히 어떤 설계 선택이 성능 향상에 기여했는지를 분리하는 연구는 거의 없었다.

### 연구 동기: BigScience 프로젝트

이 연구는 단순한 학술적 호기심에서 출발한 것이 아니다. BigScience는 1,000명 이상의 연구자가 참여한 대규모 오픈사이언스 프로젝트로, **176B 파라미터 규모의 다국어 언어 모델(BLOOM)**을 학습시키기 위한 아키텍처를 결정해야 했다. 176B 규모의 학습에는 수백만 달러의 컴퓨팅 비용이 소요되므로, 아키텍처 선택을 잘못하면 막대한 낭비가 발생한다. 이 논문은 소규모 실험에서 최적의 조합을 먼저 찾아내어 대규모 학습의 위험을 줄이려는 실용적 목적을 가지고 있었다.

### 통제된 비교 실험 설계

이 논문의 핵심 기여는 **아키텍처와 사전학습 목표를 독립 변수로 분리하여 체계적으로 비교**한 것이다. 과학 실험에서 통제 변수를 설정하는 것처럼, LLM 비교에서도 동일한 원칙을 적용했다.

**비교 대상:**
- 아키텍처 3종: 디코더-온리(causal decoder), 인코더-디코더(encoder-decoder), 비인과 디코더-온리(non-causal decoder)
- 사전학습 목표 3종: CLM(Causal Language Modeling), MLM(Masked Language Modeling), PrefixLM
- 이론적으로 **3 x 3 = 9가지 조합**이 가능하나, 아키텍처와 목표의 호환성 제약으로 일부 조합은 제외된다

**통제 변수:**
- 동일한 데이터: C4 코퍼스 (Colossal Clean Crawled Corpus)
- 동일한 파라미터 수: ~100M (인코더-디코더는 인코더+디코더 합계)
- 동일한 학습 FLOPs: 약 $2.6 \times 10^{19}$ FLOPs
- 동일한 토크나이저: SentencePiece 기반
- 동일한 하이퍼파라미터 탐색 범위: 학습률, 배치 크기 등

이 설계의 핵심 가치는 **인과 추론(causal inference)**이 가능해진다는 점이다. 한 변수만 바꾸고 나머지를 고정하면, 성능 차이를 해당 변수에 귀속시킬 수 있다.

### 아키텍처-목표 호환성 매트릭스

모든 아키텍처-목표 조합이 자연스러운 것은 아니다. 각 조합의 호환성과 대표 모델을 정리하면 다음과 같다:

| 사전학습 목표 \\ 아키텍처 | 디코더-온리 | 비인과 디코더 | 인코더-디코더 |
|---------------------------|------------|--------------|---------------|
| CLM | GPT 계열 | 비자연스러움 | 비자연스러움 |
| PrefixLM | 비자연스러움 | UniLM | T5 변형 |
| MLM (Span) | 비호환 | 비호환 | T5, BART |

디코더-온리 + CLM, 비인과 디코더 + PrefixLM, 인코더-디코더 + MLM이 각각 가장 자연스러운 조합이다. 그러나 이 논문은 비자연스러운 조합도 가능한 한 실험에 포함하여 교차 비교를 수행했다.

### 멀티태스크 프롬프트 파인튜닝(MTF)

사전학습 후 **멀티태스크 프롬프트 파인튜닝(Multitask Prompted Finetuning, MTF)**을 적용하여 제로샷 성능을 평가한다. MTF는 다양한 태스크를 자연어 프롬프트 형태로 변환하여 모델을 파인튜닝하는 기법으로, [[T0]](Sanh et al., 2022)에서 제안된 방법론이다.

MTF의 핵심은 태스크를 모델이 이해할 수 있는 자연어 형태로 표현하는 것이다. 예를 들어, NLI 태스크는 다음과 같이 변환된다:

```
Premise: A soccer game with multiple males playing.
Hypothesis: Some men are playing a sport.
Does the premise entail the hypothesis? Yes or No?
```

P3(Public Pool of Prompts) 데이터셋을 사용하여 **35개 이상의 학습 태스크**를 다양한 프롬프트 템플릿으로 변환하고, **11개의 홀드아웃 태스크**에서 제로샷 평가를 수행한다. 중요한 점은 평가 태스크가 학습 시 한 번도 포함되지 않았다는 것이다. 즉, 학습된 태스크에서 보이지 않은 태스크로의 일반화 능력을 측정하는 것이다.

MTF는 단순한 파인튜닝과 다르다. 일반적인 파인튜닝은 특정 태스크에 특화되지만, MTF는 **태스크의 다양성**을 통해 일반적인 지시 따르기(instruction following) 능력을 학습시킨다. 이는 이후 [[FLAN]](Wei et al., 2022)과 [[InstructGPT]](Ouyang et al., 2022)로 이어지는 instruction tuning 패러다임의 초기 형태이다.

## 방법론

### 1. 비교 대상 아키텍처 상세

아래 Figure 1은 본 연구의 전체 실험 파이프라인을 보여준다. 아키텍처 선택에서 시작하여 사전학습 목표, 적응(adaptation), 멀티태스크 파인튜닝, 최종 평가까지의 흐름이 체계적으로 도식화되어 있다.

![아키텍처, 목표, 적응, 파인튜닝, 평가 비교 파이프라인](figures/fig_1.png)
*Figure 1: 본 연구의 비교 실험 프레임워크. 아키텍처(CD/ND/ED) -> 사전학습 목표(FLM/PLM/MLM) -> 적응(NC-A/LM-A) -> 멀티태스크 파인튜닝(MT-F) -> 평가(T0-Eval/EAI-Eval)의 전체 파이프라인을 도식화한 것이다. 6개의 사전학습 모델(각 50억+ 파라미터, 168B 토큰 학습)을 기반으로 30개 태스크, 2개 벤치마크에서 평가를 수행한다. (Wang et al., 2022)*

**디코더-온리 (Causal Decoder)**
- Causal(단방향) attention만 사용하며, 각 토큰은 자기 자신과 이전 토큰만 참조 가능
- 입력과 출력을 단일 시퀀스로 연결하여 처리하며, 별도의 인코더-디코더 분리 없음
- 어텐션 마스크: 하삼각 행렬 (미래 토큰을 볼 수 없음)
- 대표 모델: [[GPT-2]], [[GPT-3]], OPT, [[LLaMA]]
- 장점: 자유 형식 텍스트 생성에 자연스러우며, 사전학습 시 모든 토큰이 학습 신호를 제공
- 단점: 입력을 양방향으로 이해하지 못하여 분류 등 이해 태스크에서 불리할 수 있음

**비인과 디코더-온리 (Non-causal Decoder)**
- 입력 부분(prefix)에는 양방향 어텐션, 출력 부분에는 단방향 어텐션 적용
- PrefixLM의 아키텍처적 대응물로, 입력을 양방향으로 인코딩하면서도 단일 트랜스포머 스택 유지
- 대표 모델: UniLM
- 장점: 디코더-온리의 구조적 단순함을 유지하면서 입력에 대한 양방향 이해 가능
- 단점: 입력-출력 경계를 어디에 둘지에 대한 설계 결정 필요

**인코더-디코더 (Encoder-Decoder)**
- 인코더: 양방향 어텐션으로 입력을 완전히 인코딩. 각 토큰이 모든 다른 토큰을 참조 가능
- 디코더: 단방향 어텐션으로 출력 생성 + 인코더 출력에 대한 크로스 어텐션
- 대표 모델: [[T5]], [[BART]], mT5
- 장점: 입력과 출력을 구조적으로 분리하여 조건부 생성에 유리. 양방향 인코딩으로 입력 이해력 우수
- 단점: 크로스 어텐션 레이어로 인한 추가 파라미터, 디코더-온리 대비 복잡한 구조

### 2. 비교 대상 사전학습 목표 상세

**인과 언어 모델링 (CLM, Causal Language Modeling)**

$$\mathcal{L}_{\text{CLM}} = -\sum_{i=1}^{n} \log P(x_i \mid x_1, \ldots, x_{i-1})$$

왼쪽에서 오른쪽으로 다음 토큰을 순차적으로 예측하는 가장 기본적인 언어 모델링 목표이다. 모든 토큰이 학습 신호를 제공하므로 토큰 효율(token efficiency)이 높다. 디코더-온리 아키텍처에 자연스럽게 대응하며, 시퀀스 길이 $n$의 입력에서 $n$개의 예측을 수행한다. 조건부 확률의 연쇄 법칙(chain rule)을 직접 모델링하므로, 확률론적으로 가장 정교한 밀도 추정이 가능하다.

**마스크 언어 모델링 (MLM, Masked Language Modeling)**

$$\mathcal{L}_{\text{MLM}} = -\sum_{i \in \mathcal{M}} \log P(x_i \mid x_{\setminus \mathcal{M}})$$

여기서 $\mathcal{M}$은 마스킹된 토큰의 인덱스 집합이고, $x_{\setminus \mathcal{M}}$은 마스킹되지 않은 나머지 토큰이다. 입력의 약 15%를 무작위로 마스킹하고 양방향 문맥을 활용하여 원래 토큰을 복원한다.

T5에서 사용하는 **Span-MLM** 변형은 개별 토큰이 아닌 연속된 스팬(span)을 마스킹한다. 평균 스팬 길이 3의 sentinel 토큰으로 대체하고, 디코더가 마스킹된 스팬을 순차적으로 생성한다. 수식으로 표현하면:

$$\mathcal{L}_{\text{Span-MLM}} = -\sum_{j=1}^{S} \sum_{i=1}^{|s_j|} \log P(s_{j,i} \mid x_{\setminus \mathcal{M}}, s_{j,1}, \ldots, s_{j,i-1})$$

여기서 $S$는 마스킹된 스팬의 수, $s_j$는 $j$번째 스팬의 토큰 시퀀스이다. 마스킹된 토큰만 예측하므로 CLM보다 토큰당 학습 효율이 낮을 수 있으나, 양방향 문맥을 활용한다는 장점이 있다.

**프리픽스 LM (PrefixLM)**

$$\mathcal{L}_{\text{Prefix}} = -\sum_{i=k+1}^{n} \log P(x_i \mid x_1, \ldots, x_{i-1})$$

앞부분 $x_1, \ldots, x_k$ (prefix)는 양방향 어텐션으로 인코딩하고, 뒷부분 $x_{k+1}, \ldots, x_n$은 단방향 어텐션으로 생성한다. CLM과 MLM의 절충안으로, 입력을 양방향으로 이해하면서 출력을 자동회귀적으로 생성한다.

세 목표의 핵심 차이를 정리하면 다음과 같다:

| 속성 | CLM | MLM (Span) | PrefixLM |
|------|-----|------------|----------|
| 어텐션 방향 | 단방향 (좌->우) | 양방향 | 입력: 양방향, 출력: 단방향 |
| 예측 대상 | 모든 토큰 | 마스킹된 토큰만 | 프리픽스 이후 토큰 |
| 토큰 효율 | 높음 (100%) | 낮음 (~15%) | 중간 (가변) |
| 문맥 활용 | 좌측 문맥만 | 전체 문맥 | 입력: 전체, 출력: 좌측 |
| 밀도 추정 | 정확한 확률 | 근사 확률 | 조건부 확률 |
| 대표 모델 | GPT 계열 | T5, BERT | PaLM |

### 3. 아키텍처 적응(Adaptation) 실험

이 논문의 독특한 기여 중 하나는 **사전학습된 모델을 다른 아키텍처/목표로 전환하는 적응(adaptation)** 실험이다. 이미 학습된 모델의 지식을 유지하면서 아키텍처 특성을 변환할 수 있다면, 처음부터 재학습하는 비용을 절감할 수 있다.

실험 결과, 비인과적 MLM 모델을 인과적 FLM으로 적응시키면 처음부터 학습 대비 63%의 토큰만으로 동일한 손실에 도달하여 1.6배의 속도 향상을 달성했다. 반대 방향(인과적 FLM -> 비인과적 MLM)의 적응은 더 효율적으로, 30%의 토큰(3.3배 속도 향상)만으로 동등한 성능에 도달했다.

이 적응 실험의 핵심 시사점은, 사전학습에서 획득한 언어 지식이 특정 아키텍처나 목표에 종속되지 않으며, 상대적으로 적은 추가 학습으로 다른 설정으로 전환 가능하다는 것이다. 이는 대규모 사전학습의 투자를 보호하면서도 유연한 모델 활용을 가능하게 한다.

### 4. 실험 설계 상세

실험 설정의 핵심 파라미터는 다음과 같다:

- **모델 크기**: 약 1억 파라미터(~100M) 수준에서 모든 조합 비교. 추가로 1B 규모에서도 일부 실험 수행
- **사전학습 데이터**: C4 (Colossal Clean Crawled Corpus), 모든 모델이 동일 데이터 사용
- **사전학습 스텝**: 약 524K 스텝, 배치 크기 2048 시퀀스
- **시퀀스 길이**: 입력 1024 토큰
- **옵티마이저**: Adafactor, 학습률 warm-up 후 inverse square root 스케줄
- **멀티태스크 프롬프트 파인튜닝**: P3 데이터셋으로 35개 이상 태스크를 다양한 프롬프트 형태로 파인튜닝 (태스크당 복수 템플릿)
- **평가**: 11개의 홀드아웃(held-out) 태스크에서 제로샷 평가. 평가 태스크에는 NLI, 상식 추론, 감정 분석, 문장 완성 등이 포함

### 5. 동일 파라미터 수 맞추기

아키텍처 간 공정한 비교를 위한 파라미터 배분은 다음과 같다:

| 아키텍처 | 인코더 파라미터 | 디코더 파라미터 | 총 파라미터 |
|----------|----------------|----------------|------------|
| 디코더-온리 | - | ~100M | ~100M |
| 비인과 디코더 | - | ~100M | ~100M |
| 인코더-디코더 | ~50M | ~50M | ~100M |

이 설계에서 주의할 점은 인코더-디코더의 **유효 계산량(effective computation)**이 디코더-온리와 다를 수 있다는 것이다. 인코더-디코더에는 크로스 어텐션 레이어가 추가로 존재하므로, 동일 파라미터 수에서도 전방 패스(forward pass)의 총 연산량이 다르다. 저자들은 이를 인지하고 있었으며, 파라미터 수뿐 아니라 학습 FLOPs도 동일하게 맞추려 노력했다.

또한 인코더-디코더에서 인코더와 디코더의 깊이 비율도 성능에 영향을 미칠 수 있다. 이 논문에서는 인코더와 디코더를 동일 깊이로 설정했으나, 이후 연구에서 이 비율을 조정하면 추가 성능 향상이 가능할 수 있다는 점이 논의되었다.

### 6. 평가 프로토콜

평가는 크게 두 가지 설정에서 수행된다:

1. **사전학습만 (Pretrain-only)**: 사전학습된 모델을 그대로 사용하여 제로샷 평가. 이는 모델이 자연스럽게 획득하는 제로샷 능력을 측정한다.
2. **MTF 후 (After MTF)**: 사전학습 후 멀티태스크 프롬프트 파인튜닝을 거친 모델을 사용하여 제로샷 평가. 학습에 포함되지 않은 홀드아웃 태스크만 평가한다.

평가 태스크는 다음과 같은 카테고리를 포함한다:

| 카테고리 | 대표 태스크 | 평가 지표 |
|----------|------------|----------|
| 자연어 추론 (NLI) | RTE, CB, ANLI | 정확도 |
| 상식 추론 | HellaSwag, StoryCloze | 정확도 |
| 문장 완성 | COPA, WiC | 정확도 |
| 단어 의미 해소 | WSC, WinoGrande | 정확도 |

## 실험 결과

### 주요 발견 1: MTF가 가장 큰 요인

어떤 아키텍처/목표 조합이든, MTF 파인튜닝 여부가 제로샷 성능에 **가장 큰 영향**을 미쳤다. MTF 적용 모델은 미적용 모델보다 평균 15-25%p 높은 제로샷 정확도를 보였다. 이 차이는 아키텍처 간 차이(~5-6%p)나 사전학습 목표 간 차이(~2-3%p)보다 압도적으로 크다.

이는 사전학습만으로는 제로샷 일반화가 제한적이며, **지시 따르기(instruction following) 능력이 제로샷 성능의 핵심**임을 보여준다. 이 발견은 이후 [[FLAN]](Wei et al., 2022), [[InstructGPT]](Ouyang et al., 2022) 등의 연구 방향을 예견했으며, 현재 LLM 파이프라인에서 instruction tuning이 사실상 필수 단계가 된 근거를 제공한다.

### 주요 발견 2: 인코더-디코더가 제로샷에서 우위

아래 Figure 4는 멀티태스크 파인튜닝 후 각 아키텍처-목표 조합의 제로샷 성능을 T0-Eval과 EAI-Eval 두 벤치마크에서 비교한 결과이다. MLM으로 사전학습된 인코더-디코더가 두 벤치마크 모두에서 최고 성능을 달성한다.

![멀티태스크 파인튜닝 후 아키텍처, 목표 조합별 제로샷 일반화 성능](figures/fig_4.png)
*Figure 4: 멀티태스크 파인튜닝 후 제로샷 성능 비교. T0-Eval(왼쪽)과 EAI-Eval(오른쪽) 벤치마크에서 MLM으로 사전학습된 인코더-디코더(ED+MLM)가 다른 모든 조합을 유의미하게 능가한다. EAI-Eval에서는 비인과적 디코더+MLM(ND+MLM)이 근소한 차이로 2위를 기록한다. 베이스라인인 T5-LM과 T0는 7.6배 더 많은 토큰으로 학습된 모델임에도 불구하고, 본 연구의 ED+MLM과 유사한 성능을 보인다. (Wang et al., 2022)*

MTF 적용 후 동일 파라미터 수에서의 비교 결과:

| 아키텍처 + 사전학습 목표 | MTF 전 (0-shot) | MTF 후 (0-shot) | 향상폭 |
|--------------------------|-----------------|------------------|--------|
| 디코더-온리 + CLM | 41.2% | 58.7% | +17.5%p |
| 디코더-온리 + PrefixLM | 40.5% | 57.9% | +17.4%p |
| 비인과 디코더 + CLM | 41.0% | 59.2% | +18.2%p |
| 비인과 디코더 + PrefixLM | 42.0% | 60.5% | +18.5%p |
| 인코더-디코더 + CLM | 39.8% | 61.5% | +21.7%p |
| 인코더-디코더 + PrefixLM | 43.5% | 62.8% | +19.3%p |
| **인코더-디코더 + MLM (Span)** | **44.1%** | **64.3%** | **+20.2%p** |

인코더-디코더 + MLM(Span masking)이 MTF 후 **최고 성능**을 달성했다. 특히 주목할 점은 인코더-디코더 아키텍처가 MTF를 통한 **향상폭도 가장 크다**는 것이다. 이는 양방향 인코딩이 MTF의 효과를 극대화한다는 것을 시사한다. 인코더가 태스크 프롬프트를 양방향으로 완전히 이해하고, 디코더가 이를 바탕으로 답변을 생성하는 구조가 지시 따르기에 유리하기 때문이다.

추가 분석에 따르면, EAI-Eval에서 디코더-온리 모델이 상대적으로 선전하는 현상은 프롬프트 형식 차이가 아니라 특정 태스크에서의 성능 차이에 기인한 것으로 확인되었다.

### 주요 발견 3: 사전학습만 보면 디코더-온리가 우세

흥미롭게도 **MTF 없이 사전학습만** 한 경우에는 다른 양상이 나타났다:

| 아키텍처 | 최선의 사전학습 목표 | 사전학습만 (0-shot) |
|----------|---------------------|---------------------|
| 디코더-온리 | CLM | 41.2% |
| 비인과 디코더 | PrefixLM | 42.0% |
| 인코더-디코더 | MLM (Span) | 37.5% |

사전학습만 했을 때는 **디코더-온리가 가장 우수**했다. 이 결과는 자동회귀 모델이 프롬프트 형태의 입력에 자연스럽게 반응하기 때문이다. CLM으로 학습된 디코더-온리 모델은 본질적으로 "주어진 텍스트의 이어지는 내용을 생성"하도록 학습되므로, 프롬프트를 주면 자연스럽게 답변을 이어서 생성한다.

반면 인코더-디코더 + MLM은 마스킹된 스팬을 복원하도록 학습되었기 때문에, 별도의 파인튜닝 없이 프롬프트에 응답하는 능력이 상대적으로 약하다. 이는 GPT-3가 사전학습만으로도 제로샷 능력을 보인 이유를 설명한다.

그러나 MTF를 적용하면 인코더-디코더가 역전하는데, 이는 **양방향 인코딩이 태스크의 의도를 더 정확하게 파악하는 데 유리**하기 때문이다.

### 주요 발견 4: 아키텍처의 영향이 사전학습 목표보다 크다

결과를 분산 분석(ANOVA)적 관점에서 정리하면, 성능 변동에 대한 기여도는 다음과 같다:

| 요인 | 성능 기여도 (MTF 후) |
|------|---------------------|
| MTF 적용 여부 | ~60-70% |
| 아키텍처 선택 | ~20-25% |
| 사전학습 목표 선택 | ~5-10% |
| 아키텍처 x 목표 상호작용 | ~5% |

동일 아키텍처 내에서 CLM/MLM/PrefixLM 간 성능 차이(~2-3%p)보다, 아키텍처 간 성능 차이(~5-6%p)가 더 크다. 즉, **"어떤 구조를 쓸 것인가"가 "어떻게 학습할 것인가"보다 더 중요한 결정**이다.

### 주요 발견 5: 적응 실험의 제로샷 성능 영향

인과적 FLM 모델에 비인과적 MLM 적응을 적용한 후 MTF를 수행하면, T0-Eval과 EAI-Eval 모두에서 성능이 향상되어 처음부터 비인과적 디코더로 학습한 모델과 유사한 수준에 도달했다. 이는 사전학습 투자를 보호하면서도 아키텍처 전환이 가능함을 보여준다.

그러나 모든 적응이 성공적인 것은 아니다. 인코더-디코더(MLM 사전학습)를 인과적 디코더-온리(FLM)로 전환하려는 시도는 실패했다. 인코더를 비활성화하고 디코더만 인과적으로 학습하는 방식으로는 처음부터 학습한 디코더-온리 모델의 성능에 도달하지 못했다.

이 결과는 적응의 한계를 명확히 보여준다. 동일 아키텍처 내에서 목표만 전환하는 적응(디코더-온리 내에서 MLM <-> FLM)은 효율적이지만, **아키텍처 자체를 변환하는 적응(인코더-디코더 -> 디코더-온리)은 구조적 차이가 너무 커서 효과적이지 않다**. 인코더-디코더의 크로스 어텐션으로 학습된 표현이 단일 디코더 스택에서는 제대로 활용되지 못하기 때문이다.

### 주요 발견 6: 스케일 확인 실험

100M에서의 결론이 더 큰 규모에서도 유지되는지 확인하기 위해, 1B 파라미터 규모에서도 일부 조합을 실험했다. 결과적으로 100M에서의 상대적 순위가 1B에서도 대체로 유지되었으며, 이는 소규모 실험 결과의 신뢰성을 높여준다. 다만, 스케일이 커질수록 아키텍처 간 성능 차이가 줄어드는 경향이 관측되었다.

## 의의 및 한계

아래 Figure 8은 사전학습 토큰 수에 따른 MTF 후 T0-Eval 성능 변화를 보여준다. MLM으로 사전학습된 인코더-디코더는 학습 초기부터 다른 조합을 압도하며, 전체 사전학습 토큰의 1/4만으로도 다른 구성의 최종 성능을 초과한다는 점이 주목할 만하다.

![사전학습 토큰 수 증가에 따른 멀티태스크 파인튜닝 후 T0-Eval 성능 변화](figures/fig_8.png)
*Figure 8: 사전학습 토큰 수 대비 T0-Eval 성능 추이. MLM으로 사전학습된 인코더-디코더(ED+MLM)는 전체 토큰의 약 1/4 시점에서 이미 다른 모든 구성의 최종 성능을 초과한다. 학습 전 과정에 걸쳐 모델 간 상대적 순위가 안정적으로 유지되어, 소규모 학습 시점에서도 최적 구성을 판별할 수 있음을 시사한다. (Wang et al., 2022)*

또한 MTF 시 드롭아웃을 적용하면 모든 아키텍처-목표 조합에서 제로샷 성능이 일관되게 개선되며, 특정 설정을 편향되게 이롭게 하지 않으므로 비교 결론의 공정성이 유지되었다.

### 의의

- **설계 지침 제공**: 제로샷 일반화를 목표로 하는 경우, 인코더-디코더 아키텍처 + 멀티태스크 파인튜닝이 최선의 선택임을 실험으로 확인. 이 결론은 [[BLOOM]](176B 파라미터 모델)의 아키텍처 결정에 직접 활용되었다
- **T0 모델 기여**: 공개된 T0는 GPT-3 없이도 강력한 제로샷 성능을 보이며, 이후 FLAN, InstructGPT 연구의 출발점이 되었다. T0-3B(30억 파라미터)는 GPT-3 175B의 zero-shot 성능을 일부 태스크에서 능가하여 "작지만 잘 훈련된 모델"의 가능성을 입증했다
- **공정한 비교 방법론 확립**: LLM 비교 연구에서 통제 변수 설정의 중요성을 강조. 이후 [[Chinchilla]](Hoffmann et al., 2022), [[LLaMA]](Touvron et al., 2023) 등의 연구가 이 방법론을 따라 공정한 비교를 시도했다
- **Instruction Tuning의 중요성 선행 발견**: MTF가 가장 큰 영향 요인이라는 발견은 이후 FLAN, InstructGPT, ChatGPT로 이어지는 연구 방향의 실험적 근거가 되었다. 사전학습보다 정렬(alignment)이 사용자 대면 성능에 더 큰 영향을 미친다는 현재의 통념이 이 논문에서 이미 관찰된 것이다
- **오픈사이언스 모범 사례**: 모든 실험 코드, 모델 체크포인트, 평가 결과를 공개하여 재현 가능한 연구를 지향했다

### 한계

- **소규모 모델 실험**: 100M 파라미터 수준의 실험이라 10B+ 스케일에서의 결론이 다를 수 있다. 실제로 [[LLaMA]](2023)는 디코더-온리로도 뛰어난 zero-shot 성능을 달성했으며, 이는 스케일에 따른 상전이(phase transition)가 소규모 실험의 결론을 뒤집을 수 있음을 보여준다
- **영어 중심 평가**: 모든 평가가 영어 태스크로 수행되었으며, 다국어 제로샷 일반화는 분석되지 않았다. mT5와 같은 다국어 인코더-디코더 모델의 성공을 고려하면, 다국어 환경에서는 인코더-디코더의 우위가 더 클 수도 있다
- **프롬프트 민감성**: MTF의 효과가 프롬프트 형식에 크게 의존할 수 있다. P3의 프롬프트 품질과 다양성이 결과에 영향을 미치며, 다른 프롬프트 데이터셋을 사용하면 결론이 달라질 수 있다
- **최신 기법 미포함**: RLHF, DPO, Constitutional AI 등 이후 등장한 정렬 기법과 [[LLaMA]], [[Mistral]], [[Gemma]] 등 효율적 디코더-온리 모델은 비교 대상에 없다. 이들은 대규모 데이터와 정교한 instruction tuning으로 인코더-디코더의 장점을 상당 부분 극복했다
- **추론 효율성 미고려**: 인코더-디코더는 동일 파라미터에서 추론 속도가 디코더-온리보다 느릴 수 있으며(크로스 어텐션 오버헤드), 이는 실용적으로 매우 중요한 요소이다. KV 캐시 최적화도 디코더-온리에서 더 성숙하다
- **데이터 다양성 부족**: C4 단일 코퍼스만 사용하여, 코드, 수학, 다국어 데이터 등 다양한 도메인의 영향을 분석하지 못했다

### 현재 시점의 재해석 (2026년)

이 논문의 결론(인코더-디코더가 우수)과 현재 LLM 생태계(디코더-온리가 지배적) 사이에는 주목할 만한 괴리가 있다. 이를 이해하는 핵심 요인은 다음과 같다:

1. **스케일 효과**: 10B+ 규모에서는 디코더-온리의 단점(단방향 어텐션)이 모델 용량으로 보상된다. 충분히 큰 모델은 단방향이라도 입력의 의미를 깊이 파악할 수 있다
2. **Instruction Tuning의 발전**: RLHF, DPO, GRPO 등 더 정교한 정렬 기법이 디코더-온리 모델의 zero-shot 능력을 극적으로 향상시켰다. 이 논문에서 발견한 MTF의 중요성이 정렬 기법의 발전을 통해 디코더-온리에서 극대화된 셈이다
3. **추론 효율성**: KV 캐시, Flash Attention, Speculative Decoding 등 디코더-온리 최적화 기법이 더 성숙하여 실용적 우위를 확보했다. 인코더-디코더는 이러한 최적화의 혜택을 덜 받는다
4. **생성 능력**: 자유 형식 텍스트 생성, 대화, 코드 작성 등에서 디코더-온리가 본질적으로 유리하며, 이러한 use case가 현재 LLM 시장을 지배한다
5. **생태계 효과**: 디코더-온리 모델을 중심으로 도구, 프레임워크, 최적화 기법이 축적되면서 양의 피드백 루프가 형성되었다

그러나 인코더-디코더의 장점이 완전히 사라진 것은 아니다. 번역, 요약, 분류 등 명확한 입출력 구조를 가진 태스크에서는 여전히 인코더-디코더가 효율적이며, Google의 Gemini 아키텍처가 인코더-디코더 요소를 포함하고 있다는 점은 이 아키텍처의 잠재력이 여전히 존재함을 시사한다.

이 논문의 진정한 가치는 특정 결론보다, **통제된 실험을 통해 설계 선택의 영향을 정량화하는 방법론**을 확립한 것에 있다. "어떤 설계가 최선인가?"에 대한 답은 스케일과 use case에 따라 바뀔 수 있지만, "어떻게 공정하게 비교할 것인가?"에 대한 이 논문의 방법론적 기여는 시간이 지나도 유효하다.

## 코드 예제

### 아키텍처별 사전학습 구현 비교 (PyTorch)

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

# === 1. 사전학습 목표별 손실 함수 ===

def causal_lm_loss(logits, labels):
    """Causal Language Modeling (CLM) 손실.
    모든 토큰에서 다음 토큰 예측.
    """
    # logits: (batch, seq_len, vocab_size)
    # labels: (batch, seq_len) -- 한 칸 shift된 targets
    shift_logits = logits[:, :-1, :].contiguous()
    shift_labels = labels[:, 1:].contiguous()
    return F.cross_entropy(
        shift_logits.view(-1, shift_logits.size(-1)),
        shift_labels.view(-1),
        ignore_index=-100
    )

def masked_lm_loss(logits, labels, mask_positions):
    """Masked Language Modeling (MLM) 손실.
    마스킹된 위치에서만 원래 토큰 예측.
    """
    batch_size = logits.size(0)
    masked_logits = []
    masked_labels = []
    for b in range(batch_size):
        masked_logits.append(logits[b, mask_positions[b]])
        masked_labels.append(labels[b, mask_positions[b]])
    masked_logits = torch.cat(masked_logits, dim=0)
    masked_labels = torch.cat(masked_labels, dim=0)
    return F.cross_entropy(masked_logits, masked_labels)

def prefix_lm_loss(logits, labels, prefix_len):
    """Prefix LM 손실.
    프리픽스 이후 토큰만 예측.
    """
    target_logits = logits[:, prefix_len:-1, :].contiguous()
    target_labels = labels[:, prefix_len+1:].contiguous()
    return F.cross_entropy(
        target_logits.view(-1, target_logits.size(-1)),
        target_labels.view(-1),
        ignore_index=-100
    )

# === 2. 어텐션 마스크 생성 ===

def create_causal_mask(seq_len):
    """인과적 마스크: 미래 토큰 차단."""
    return torch.tril(torch.ones(seq_len, seq_len)).bool()

def create_prefix_mask(seq_len, prefix_len):
    """프리픽스 마스크: 앞부분 양방향, 뒷부분 인과적."""
    mask = torch.zeros(seq_len, seq_len).bool()
    mask[:prefix_len, :prefix_len] = True
    for i in range(prefix_len, seq_len):
        mask[i, :i+1] = True
    return mask

def create_bidirectional_mask(seq_len):
    """양방향 마스크: 인코더용."""
    return torch.ones(seq_len, seq_len).bool()

# === 3. 마스크 시각화 ===

def visualize_masks(seq_len=8, prefix_len=4):
    """세 가지 어텐션 마스크 패턴 시각화."""
    masks = {
        'Causal (CLM)': create_causal_mask(seq_len),
        'Prefix (PrefixLM)': create_prefix_mask(seq_len, prefix_len),
        'Bidirectional (MLM)': create_bidirectional_mask(seq_len),
    }
    for name, mask in masks.items():
        print(f"\n{name}:")
        for i in range(seq_len):
            row = ''.join(['O' if mask[i, j] else '.' for j in range(seq_len)])
            print(f"  {row}")

visualize_masks()
# Causal: 하삼각 행렬 (각 토큰이 이전 토큰만 참조)
# Prefix: 상단-좌측 블록이 완전 연결, 하단-우측이 하삼각
# Bidirectional: 전체 연결 (모든 토큰이 모든 토큰을 참조)
```
