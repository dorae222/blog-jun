# CAMEL: LLM 멀티에이전트 협력의 선구자

## 개요

:::info
**Paper:** CAMEL: Communicative Agents for "Mind" Exploration of Large Language Model Society (arXiv:2303.17760, NeurIPS 2023)
**저자:** Guohao Li, Hasan Abed Al Kader Hammoud, Hani Itani, Dmitrii Khizbullin, Bernard Ghanem
**소속:** King Abdullah University of Science and Technology (KAUST)
**코드:** [GitHub: camel-ai/camel](https://github.com/camel-ai/camel)
:::

LLM 하나가 강력하다면, **두 개의 LLM이 서로 다른 역할로 협력하면 어떨까?** CAMEL(Communicative Agents for "Mind" Exploration of Large Language Model Society)은 이 질문에 대한 최초의 체계적 연구입니다. 2023년 NeurIPS에서 발표된 이 논문은 두 LLM 에이전트에게 서로 다른 역할(예: "Python 프로그래머"와 "주식 트레이더")을 부여하고, 주어진 과제를 **인간 개입 없이 자율적으로 협력**하여 해결하도록 하는 Role-Playing 프레임워크를 제안합니다.

CAMEL의 핵심 기여는 세 가지입니다. 첫째, **Inception Prompting**이라는 새로운 프롬프팅 기법으로 에이전트 간 자율 대화를 가능하게 합니다. 둘째, AI Society, Code Generation, Math, Science 등 다양한 도메인에서 **25,000건 이상의 대화 데이터셋**을 자동 생성합니다. 셋째, 멀티에이전트 시스템의 **행동 패턴, 한계, 실패 모드**를 체계적으로 분석하여 후속 연구의 기반을 마련합니다.

이 논문은 AutoGen, CrewAI, MetaGPT 등 현재 널리 사용되는 멀티에이전트 프레임워크의 직접적 선구자로, 멀티에이전트 LLM 시스템이라는 연구 분야를 개척한 기념비적 논문입니다.

## 배경 및 동기

### 단일 에이전트의 한계

2023년 초 시점에서, LLM 기반 에이전트 연구는 주로 **단일 에이전트** 패러다임에 집중하고 있었습니다. [[react]]가 Thought-Action-Observation 루프를 통해 LLM 에이전트의 기본 패러다임을 확립했고, [[reflexion]]이 자기 반성을 통한 학습을 추가했지만, 이들은 모두 하나의 LLM이 모든 역할을 수행하는 구조였습니다.

단일 에이전트 접근법에는 근본적인 한계가 있습니다.

| 한계 | 설명 | 영향 |
|------|------|------|
| 관점의 단일성 | 하나의 LLM이 모든 시각을 담당 | 복잡한 문제에서 편향된 해결책 |
| 자기 검증의 어려움 | 자신의 출력을 스스로 평가 | 오류 발견 및 교정 능력 부족 |
| 역할 전환 비용 | 하나의 프롬프트에서 다중 역할 수행 | 역할 혼동, 일관성 저하 |
| 확장성 제한 | 단일 컨텍스트 윈도우에 모든 정보 집약 | 대규모 복잡 태스크 처리 불가 |

### 인간 협업에서의 영감

인간 사회에서 복잡한 문제 해결은 거의 항상 **역할 분담과 협업**을 통해 이루어집니다. 소프트웨어 개발에서 PM이 요구사항을 정의하고 개발자가 구현하듯, 의료 분야에서 진단 전문의와 치료 전문의가 협력하듯, 다른 전문성을 가진 주체들의 상호작용이 개별 전문가의 단독 작업보다 우수한 결과를 만들어냅니다.

CAMEL은 이 인간 협업 패턴을 LLM에 적용합니다. 두 에이전트가 각각 **지시자(instructor)**와 **실행자(executor)** 역할을 맡아 대화를 통해 과제를 해결하도록 설계합니다. 이때 핵심 질문은 "인간의 감독 없이도 에이전트들이 목표 지향적으로 협력할 수 있는가?"입니다.

### 기존 멀티에이전트 연구와의 차별점

CAMEL 이전에도 멀티에이전트 시스템 연구는 존재했지만, 대부분 강화학습 기반의 게임 환경(예: OpenAI Hide-and-Seek)이나 규칙 기반 시뮬레이션에 국한되었습니다. LLM을 활용한 멀티에이전트 시스템에 대한 체계적 연구는 CAMEL이 사실상 최초입니다.

| 기존 접근법 | CAMEL |
|------------|-------|
| 강화학습 기반, 수십만 스텝 학습 필요 | 프롬프팅만으로 즉시 협력 가능 |
| 고정된 행동 공간 | 자연어 기반 유연한 상호작용 |
| 특정 게임/환경에 특화 | 범용적 과제 해결 가능 |
| 에이전트 간 통신 프로토콜 사전 정의 | 자연어 대화로 자율 조율 |

## 핵심 아이디어

### Role-Playing Framework 아키텍처

CAMEL의 Role-Playing Framework는 세 가지 핵심 구성요소로 이루어집니다.

**1. AI User (지시자)**: 과제를 분해하고, 단계별 지시를 내리는 역할을 수행합니다. 예를 들어 "주식 트레이더" 역할의 AI User는 금융 도메인의 관점에서 요구사항을 구체화합니다.

**2. AI Assistant (실행자)**: AI User의 지시를 받아 실제 작업을 수행하고 결과를 보고합니다. "Python 프로그래머" 역할의 AI Assistant는 기술적 관점에서 구현을 담당합니다.

**3. Task Specifier**: 초기 아이디어를 구체적인 과제로 변환하는 역할입니다. "주식 거래 앱 개발"이라는 추상적 아이디어를 "과거 5년간의 S&P 500 데이터를 기반으로 Markowitz 포트폴리오 최적화를 수행하는 Python 프로그램 개발"과 같은 구체적 과제로 변환합니다.

이 세 구성요소의 상호작용 흐름은 다음과 같습니다.

```
[Task Specifier]
    │
    ▼ 구체적 과제 생성
[System Prompts 생성] ── Inception Prompting 적용
    │              │
    ▼              ▼
[AI User]  ←→  [AI Assistant]
(지시자)        (실행자)
    │
    ▼ 매 턴마다 교대
Instruction → Response → Instruction → Response → ... → <CAMEL_TASK_DONE>
```

### Inception Prompting 메커니즘 상세

Inception Prompting은 CAMEL의 핵심 기술 혁신입니다. 각 에이전트에게 **역할, 과제 설명, 행동 규칙을 포함한 상세한 시스템 프롬프트**를 제공하여, 인간 개입 없이도 목표 지향적 대화가 이루어지도록 합니다.

:::tip
Inception Prompting이라는 명칭은 영화 "인셉션"에서 따왔습니다. 꿈 속의 꿈처럼, 프롬프트 안에 에이전트의 역할과 행동 규칙을 "심어놓는(inception)" 방식입니다. 이 프롬프트가 에이전트의 행동을 처음부터 끝까지 지배하므로, 외부 개입 없이도 일관된 협력이 가능합니다.
:::

**AI User 시스템 프롬프트 구조:**

```
Never forget you are a {user_role} and I am a {assistant_role}.
Never flip roles!

We share a common interest in collaborating to successfully complete a task.
You must help me to complete the task.

Here is the task: {task}. Never forget our task!

You must instruct me based on my expertise and your needs
to complete the task ONLY in the following way:

1. Instruct with a numbered list with step-by-step instructions.
2. Each instruction should be concise and clear.
3. Do not add anything else other than the instruction.
4. Unless I tell you the task is completed, you should always
   start with: "Next request."
5. When the task is completed, you MUST only reply with
   a single word <CAMEL_TASK_DONE>.
```

**AI Assistant 시스템 프롬프트 구조:**

```
Never forget you are a {assistant_role} and I am a {user_role}.
Never flip roles!

You must help me to complete the task.
Here is the task: {task}. Never forget our task!

I must instruct you based on your expertise and my needs
to complete the task.

You must follow my instructions and provide a solution.
Unless I say the task is completed, you should always start
with: "Solution: ..."
```

이 프롬프트 설계에는 다음과 같은 핵심 원칙이 반영되어 있습니다.

| 원칙 | 프롬프트 요소 | 목적 |
|------|-------------|------|
| 역할 고정 | "Never flip roles!" | 역할 혼동(role-flipping) 방지 |
| 과제 유지 | "Never forget our task!" | 주제 이탈 방지 |
| 형식 통일 | "Next request." / "Solution: ..." | 대화 구조의 일관성 보장 |
| 종료 조건 | `<CAMEL_TASK_DONE>` 토큰 | 무한 루프 방지, 명확한 종료 신호 |
| 구체성 강제 | "numbered list with step-by-step" | 모호한 지시 방지 |

### Task Specifier의 역할

Task Specifier는 CAMEL 파이프라인에서 종종 간과되지만 중요한 구성요소입니다. 인간이 제공하는 초기 아이디어는 대부분 추상적이므로, 이를 두 에이전트가 실제로 작업할 수 있는 수준의 구체적 과제로 변환해야 합니다.

**변환 예시:**

| 원래 아이디어 | Task Specifier 출력 |
|-------------|-------------------|
| "주식 거래 앱 개발" | "yfinance API로 S&P 500 과거 5년 데이터를 수집하고, Markowitz 평균-분산 최적화로 최적 포트폴리오를 계산하며, matplotlib으로 효율적 프론티어를 시각화하는 Python 프로그램 개발" |
| "기후 변화 분석" | "NASA GISTEMP 데이터셋을 사용하여 1880-2023년 지구 평균 기온 추이를 분석하고, ARIMA 모델로 2050년까지의 기온 변화를 예측하는 보고서 작성" |
| "건강 관리 앱" | "사용자의 일일 식단을 입력받아 칼로리, 단백질, 지방, 탄수화물을 자동 계산하고, BMR 기반 권장 섭취량과 비교하여 영양 균형 피드백을 제공하는 웹 애플리케이션 설계" |

이 구체화 단계가 없으면, AI User와 AI Assistant 사이의 대화가 과제의 범위를 정하는 데에만 상당한 턴을 소모하게 됩니다.

## 방법론: 대화 생성 파이프라인

### 전체 파이프라인

CAMEL의 대화 생성 파이프라인은 다음 4단계로 구성됩니다.

**1단계 - 역할 생성**: GPT-4에 프롬프트를 제공하여 50개의 AI Assistant 역할(예: 의사, 변호사, 교수, 엔지니어)과 50개의 AI User 역할을 생성합니다.

**2단계 - 과제 생성**: 각 역할 쌍 $(r_{\text{user}}, r_{\text{assistant}})$에 대해 GPT-4가 10개의 과제 아이디어를 생성합니다. 50 x 50 = 2,500개의 역할 쌍에서 총 25,000개의 과제가 만들어집니다.

**3단계 - Task Specification**: Task Specifier가 각 과제 아이디어를 구체적 과제로 변환합니다.

**4단계 - Role-Playing 대화**: AI User와 AI Assistant가 Inception Prompting에 따라 자율적으로 대화를 수행합니다. 대화는 `<CAMEL_TASK_DONE>` 토큰이 출력되거나, 최대 턴 수(보통 40턴)에 도달하면 종료됩니다.

### 대화 도메인별 설계

CAMEL은 4개의 주요 도메인에서 대화를 생성합니다. 각 도메인은 서로 다른 역할 풀과 과제 유형을 가집니다.

| 도메인 | 역할 예시 | 과제 유형 | 대화 특성 |
|--------|----------|----------|----------|
| AI Society | 의사-환자, 교수-학생, CEO-엔지니어 | 일반 협업 | 자연어 중심, 역할 간 관점 교환 |
| Code | 프로그래머-데이터 과학자, 풀스택-DBA | 소프트웨어 개발 | 코드 생성 + 설명, 디버깅 |
| Math | 수학자-물리학자, 통계학자-경제학자 | 수학 문제 풀이 | 수식 도출, 증명 |
| Science | 생물학자-화학자, 물리학자-공학자 | 과학 연구 | 가설 수립, 실험 설계 |

### AI Society 시나리오 상세

AI Society는 CAMEL의 가장 범용적인 시나리오로, 50개의 AI User 역할과 50개의 AI Assistant 역할을 조합하여 2,500개의 역할 쌍을 생성합니다. 각 역할 쌍에 대해 10개의 과제가 생성되므로, 총 25,000건의 대화가 만들어집니다.

**역할 쌍 예시와 생성된 대화 패턴:**

```
역할 쌍: 의사(AI User) + 영양사(AI Assistant)
과제: "당뇨병 환자를 위한 식단 관리 프로그램 개발"

AI User (의사):
  "먼저 제2형 당뇨병 환자의 혈당 목표 범위를 설정하고,
   이에 맞는 일일 탄수화물 섭취 상한을 정해주세요."

AI Assistant (영양사):
  "Solution: 제2형 당뇨병 환자의 공복 혈당 목표는 80-130mg/dL,
   식후 2시간 혈당은 180mg/dL 미만입니다.
   이를 기반으로 일일 탄수화물 섭취량을 45-60g/식사로
   설정하겠습니다. 다음은 구체적인 식단 구성입니다..."

AI User (의사):
  "Next request. 이제 신장 기능이 저하된 환자를 위해
   단백질과 나트륨 제한 조건을 추가해주세요."
```

관찰된 흥미로운 행동 패턴으로는 에이전트들이 **자연스럽게 하위 과제를 분해**하고, 각 단계에서 **역할에 맞는 전문 용어와 관점**을 사용한다는 점입니다. 의사 역할의 AI User는 임상적 관점에서 요구사항을 제시하고, 영양사 역할의 AI Assistant는 영양학적 지식을 바탕으로 응답합니다.

### Code Generation 시나리오 상세

Code Generation 시나리오에서는 프로그래밍 관련 역할 쌍이 소프트웨어 개발 과제를 수행합니다. 이 시나리오는 AI Society와 달리 **실행 가능한 코드**가 대화의 핵심 산출물입니다.

단일 에이전트와의 비교에서 두 에이전트 협력의 장점이 두드러집니다.

| 측면 | 단일 에이전트 | CAMEL 두 에이전트 |
|------|-------------|----------------|
| 요구사항 정의 | 한 번에 완벽한 프롬프트 필요 | AI User가 점진적으로 정교화 |
| 디버깅 | 자체 코드 검토 (자기 편향) | AI User가 외부 관점에서 검토 |
| 구조화 | 한꺼번에 전체 코드 생성 | 기능별 단계적 구현 |
| 피드백 루프 | 사용자 개입 필요 | 자동 피드백 및 수정 |

### Math/Science 시나리오의 특징

Math와 Science 시나리오는 AI Society나 Code와는 다른 독특한 특성을 보입니다.

**Math 시나리오**: 수학 관련 역할 쌍(예: 수학자-물리학자)이 수학적 문제를 공동으로 해결합니다. 이 시나리오에서는 에이전트들이 수식을 생성하고 증명 과정을 논의하는데, **수학적 정확성이 보장되지 않는다**는 한계가 관찰되었습니다. 에이전트들이 그럴듯하지만 부정확한 증명을 생성하고, 상대 에이전트가 이를 검증 없이 수용하는 경우가 빈번했습니다.

**Science 시나리오**: 과학 연구 관련 역할 쌍이 가설 수립, 실험 설계, 데이터 분석 등의 과제를 수행합니다. 이 시나리오는 **도메인 전문 지식의 깊이**가 대화 품질에 큰 영향을 미치며, LLM의 과학적 지식의 한계가 직접적으로 드러나는 영역입니다.

## 실험 결과와 발견

### 역할 부여의 효과

CAMEL의 가장 중요한 발견 중 하나는 **역할 부여(role assignment)가 LLM의 행동에 실질적 영향을 미친다**는 것입니다.

같은 GPT-4 모델이라도 부여된 역할에 따라 행동이 크게 달라집니다.

| 역할 | 행동 특성 | 언어 패턴 |
|------|----------|----------|
| "Python 전문가" | 효율적 코드, 최적화 고려, 엣지케이스 처리 | 기술 용어 빈번 사용, 코드 주석 상세 |
| "초보 프로그래머" | 기본적 구현, 단순한 로직 | 설명적 언어, 질문 빈번 |
| "의사" | 임상적 관점, 증거 기반 판단 | 의학 용어, 진단 프로세스 언급 |
| "교수" | 체계적 설명, 개념 분해 | 학술적 어투, 참고문헌 언급 |

이 발견은 **LLM의 페르소나 설정이 단순한 스타일 변화가 아니라 실질적인 문제 해결 능력에 영향을 미침**을 시사합니다.

### 협력의 시너지 효과

두 에이전트의 대화는 단일 에이전트의 일방적 생성보다 **더 구조화되고 완결적인 결과물**을 생산하는 경향이 있습니다. 이는 다음과 같은 메커니즘에 의해 발생합니다.

**점진적 정교화(Progressive Refinement)**: AI User가 매 턴마다 새로운 요구사항을 추가하므로, AI Assistant의 출력이 점진적으로 정교해집니다. 이는 인간이 긴 프롬프트를 한 번에 작성하는 것보다 자연스러운 방식입니다.

**암묵적 피드백(Implicit Feedback)**: AI User가 AI Assistant의 이전 응답을 바탕으로 다음 지시를 생성하므로, 잘못된 방향은 자연스럽게 교정됩니다. 다만, 이 "교정"의 정확성 자체가 LLM에 의존한다는 한계가 있습니다.

**구조적 분해(Structural Decomposition)**: 역할 분담으로 인해 과제가 자연스럽게 하위 과제로 분해됩니다. AI User는 "무엇을"에 집중하고, AI Assistant는 "어떻게"에 집중하므로, 각각의 출력 품질이 향상됩니다.

### 실패 모드 분석

CAMEL은 멀티에이전트 시스템의 실패 모드를 체계적으로 분류한 최초의 연구이기도 합니다.

:::warning
CAMEL 논문에서 발견된 실패 모드들은 2024-2025년의 최신 멀티에이전트 프레임워크에서도 완전히 해결되지 않았습니다. 이들은 LLM 기반 멀티에이전트 시스템의 구조적 한계로, 시스템 설계 시 반드시 고려해야 합니다.
:::

**1. Role-Flattening (역할 평탄화)**

장기 대화에서 에이전트들이 점차 역할에서 벗어나는 현상입니다. 초반에는 "의사"와 "영양사"가 명확히 구분되지만, 20턴 이후에는 두 에이전트의 응답이 일반적인 LLM 응답 패턴으로 수렴합니다. 이는 LLM의 학습 데이터에서 지배적인 "도움이 되는 AI 어시스턴트" 패턴이 역할 프롬프트를 점차 압도하기 때문입니다.

**2. Hallucination Propagation (환각 전파)**

한 에이전트가 생성한 잘못된 정보가 다른 에이전트에 의해 **검증 없이 수용**되는 현상입니다. 단일 에이전트에서의 환각은 해당 에이전트의 출력에만 영향을 미치지만, 멀티에이전트 시스템에서는 환각이 대화를 통해 **증폭되고 고착화**됩니다.

예시: AI Assistant가 존재하지 않는 Python 라이브러리를 언급 -> AI User가 이를 수용하고 해당 라이브러리 활용을 전제로 다음 지시를 생성 -> 이후 대화 전체가 잘못된 전제 위에 구축됨

**3. Repetitive Agreement (반복적 동의)**

두 에이전트가 새로운 진전 없이 서로의 의견에 반복적으로 동의하는 패턴입니다. "좋은 제안입니다" -> "감사합니다, 맞습니다" -> "동의합니다"의 루프가 형성되어 과제가 실질적으로 진행되지 않습니다.

**4. Premature Termination (조기 종료)**

과제가 실제로 완료되지 않았는데 `<CAMEL_TASK_DONE>` 토큰이 생성되는 경우입니다. 에이전트가 과제의 일부만 수행하고 나머지를 간과하거나, 과제 완료 기준을 너무 관대하게 적용하는 경향이 있습니다.

## 한계 및 의의

### 기술적 한계

**1. 비용 효율성**

두 에이전트가 평균 20턴의 대화를 수행하면, 단일 에이전트 대비 **약 20배의 API 호출 비용**이 발생합니다. 복잡한 과제에서 턴 수가 증가하면 비용은 급격히 상승합니다.

| 시나리오 | 평균 턴 수 | 단일 에이전트 대비 비용 | GPT-4 기준 예상 비용/대화 |
|---------|----------|-------------------|----------------------|
| 단순 과제 | 10턴 | 10x | ~$2-5 |
| 중간 과제 | 20턴 | 20x | ~$5-15 |
| 복잡 과제 | 40턴 | 40x | ~$15-40 |

**2. 수렴 보장 부재**

에이전트 간 대화가 항상 목표에 수렴하지는 않습니다. 약 15%의 대화에서 무한 루프, 반복적 동의, 주제 이탈 등의 failure mode가 관찰되었으며, 이를 사전에 감지하고 교정하는 메커니즘이 부재합니다.

**3. 검증 메커니즘의 부재**

AI User가 AI Assistant의 출력을 "검증"하지만, 이 검증 자체가 LLM에 의존하므로 **진정한 외부 검증이 아닙니다**. 코드 실행, 수학적 증명 검증, 사실 확인 등의 외부 도구와의 연동이 없어, 그럴듯하지만 잘못된 결과가 최종 산출물로 채택될 위험이 있습니다.

**4. 역할 설계의 수동성**

50개의 역할과 그 조합은 사전에 수동으로 설계됩니다. 주어진 과제에 최적인 역할 조합을 **자동으로 탐색하는 메커니즘이 없습니다**. 이후 MetaGPT 등에서 이 문제를 일부 해결합니다.

### 학술적 의의

**1. 멀티에이전트 LLM 패러다임의 개척**

CAMEL은 "LLM 에이전트들이 역할을 분담하여 협력한다"는 패러다임을 확립한 최초의 체계적 연구입니다. 이 패러다임은 이후 수백 편의 후속 연구와 수십 개의 오픈소스 프레임워크로 확장되었습니다.

**2. Inception Prompting의 범용성**

Inception Prompting은 CAMEL을 넘어 다양한 멀티에이전트 시스템에서 재사용되는 핵심 기법이 되었습니다. 에이전트에게 역할, 규칙, 과제를 시스템 프롬프트로 주입하는 패턴은 현재 거의 모든 에이전트 프레임워크의 표준입니다.

**3. 대규모 대화 데이터셋**

25,000건 이상의 멀티에이전트 대화 데이터셋은 이후 연구에서 벤치마크, 학습 데이터, 분석 대상으로 광범위하게 활용되고 있습니다.

**4. 실패 모드의 체계적 분류**

Role-flattening, hallucination propagation, repetitive agreement 등의 실패 모드를 최초로 식별하고 분류한 것은, 이후 멀티에이전트 시스템의 안정성 연구에 핵심적 기여를 했습니다.

**2. 도구 통합**: 대화만으로는 한계가 있으므로, 코드 실행, 웹 검색, 데이터베이스 조회 등 [[llm-tool-use-patterns]]을 멀티에이전트 시스템에 통합

**3. 확장 가능한 아키텍처**: 2개 에이전트의 고정 구조에서, 과제에 따라 **동적으로 에이전트 수와 역할을 조정**하는 유연한 아키텍처로 발전

**4. 평가와 벤치마크**: 멀티에이전트 시스템의 성능을 체계적으로 평가하기 위한 벤치마크와 지표 개발

### 실무 적용 시 고려사항

CAMEL의 Role-Playing 패턴을 실무에 적용할 때 고려해야 할 사항들입니다.

**프롬프트 설계**: Inception Prompting의 핵심 원칙(역할 고정, 과제 유지, 형식 통일, 종료 조건)을 유지하되, 도메인에 맞게 세부 규칙을 조정해야 합니다.

**비용 관리**: 최대 턴 수를 합리적으로 설정하고, 불필요한 대화를 조기에 감지하여 중단하는 메커니즘이 필요합니다. 경량 모델(GPT-3.5, Claude Haiku 등)을 AI User에 사용하고, 고성능 모델을 AI Assistant에 사용하는 비대칭 전략도 효과적입니다.

**검증 통합**: CAMEL의 가장 큰 한계인 검증 부재를 해소하기 위해, 코드 실행 환경, 테스트 프레임워크, 외부 API 등을 대화 루프에 통합해야 합니다. AutoGen이 이 방향의 좋은 참고 사례입니다.

## 결론

CAMEL은 "두 LLM이 서로 다른 역할로 협력하면 개별 LLM보다 더 나은 결과를 만들 수 있다"는 직관적이지만 검증되지 않았던 가설을 체계적으로 실증한 논문입니다. Inception Prompting이라는 우아한 기법으로 인간 개입 없는 자율적 에이전트 협력을 가능하게 했으며, 25,000건 이상의 대화 데이터셋을 통해 멀티에이전트 시스템의 가능성과 한계를 모두 드러냈습니다.

이 논문의 핵심 기여는 네 가지 차원에서 평가할 수 있습니다. 첫째, **패러다임 측면에서** 단일 에이전트에서 멀티에이전트로의 전환을 제시했습니다. 둘째, **기법 측면에서** Inception Prompting이라는 범용적 멀티에이전트 프롬프팅 기법을 개발했습니다. 셋째, **데이터 측면에서** 대규모 멀티에이전트 대화 데이터셋을 공개했습니다. 넷째, **분석 측면에서** role-flattening, hallucination propagation 등 멀티에이전트 시스템의 근본적 한계를 식별하고 분류했습니다.

CAMEL은 단순해 보이는 "두 LLM의 대화"라는 설정에서 놀라울 정도로 풍부한 연구 주제를 발굴해낸 논문입니다. 이 논문이 개척한 멀티에이전트 LLM 패러다임은 AutoGen, MetaGPT, CrewAI 등으로 이어지며, AI 에이전트 생태계의 핵심 축을 형성하고 있습니다.
