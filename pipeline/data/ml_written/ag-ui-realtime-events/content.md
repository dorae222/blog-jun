# AG-UI 실시간 이벤트: 에이전트 실행을 UI로 보여주는 방법

MCP와 A2A가 각각 도구 연결과 에이전트 간 작업 위임을 다룬다면, AG-UI는 사용자가 보는 화면을 다룬다. 사용자는 최종 답변만 원하는 것이 아니라 어떤 도구가 호출됐는지, 어느 단계에서 멈췄는지, 추가 입력이 필요한지를 알고 싶어 한다.

## 문제: 에이전트마다 다시 짜는 UI 글루 코드

에이전트 앱을 만들어 본 사람은 비슷한 코드를 반복해서 짠다. 모델이 토큰을 흘려보내면 화면에 이어붙이고, 도구를 호출하면 "검색 중" 같은 표시를 띄우고, 내부 상태가 바뀌면 진행률 카드를 갱신하고, 승인이 필요하면 버튼을 노출한다. 문제는 이 연결(glue) 코드가 프레임워크마다, 프로젝트마다 매번 새로 작성된다는 점이다. 백엔드가 LangGraph인지 CrewAI인지에 따라, 프런트엔드가 React인지 Vue인지에 따라 같은 로직이 조금씩 다른 모양으로 다시 태어난다.

AG-UI(Agent-User Interaction)는 이 반복을 없애려는 시도다. 에이전트가 "생각하고, 도구를 부르고, 상태를 바꾸는" 과정을 UI로 흘려보내는 이벤트 스트림을 표준화한다. 백엔드는 정해진 형태의 이벤트를 내보내기만 하면 되고, 프런트엔드는 그 이벤트를 구독해 렌더링하기만 하면 된다. 둘 사이의 계약이 고정되면 백엔드와 프런트엔드를 각각 독립적으로 교체해도 연결 코드를 다시 짜지 않아도 된다. CopilotKit이 주도하는 이 프로토콜의 목표는 정확히 그 지점, 에이전트와 사용자 인터페이스 사이의 반복되는 배관 작업을 규격으로 대체하는 것이다.

## 이벤트를 먼저 설계한다

AG-UI 글에서 핵심은 컴포넌트가 아니라 이벤트다. 에이전트 런타임은 message, tool call, tool result, state delta, interrupt 같은 이벤트를 내보내고, UI는 이를 받아 화면 상태를 갱신한다. 이 경계를 지키면 React, Vue, 모바일 앱, 콘솔 UI가 같은 실행 로그를 공유할 수 있다. 반대로 화면 컴포넌트부터 설계하면, 렌더링 세부 사항이 통신 규약에 스며들어 프런트엔드를 바꿀 때마다 백엔드까지 손대야 하는 결합이 생긴다. 그래서 AG-UI는 "무엇을 그릴까"보다 "어떤 신호를 흘려보낼까"를 먼저 정한다.

## 이벤트 흐름: 실행 수명주기부터 상태 갱신까지

AG-UI의 이벤트는 대략 몇 개의 범주로 묶인다. 정확한 이벤트 이름과 개수는 스펙 버전에 따라 달라질 수 있으므로, 여기서는 이름을 외우기보다 어떤 종류의 신호가 오가는지를 범주 수준에서 본다.

- 실행 수명주기(run lifecycle): 하나의 에이전트 실행이 시작되고 끝나는 경계를 알린다. run이 시작됐다는 신호로 UI는 로딩 상태로 진입하고, 종료 신호로 최종 상태로 정리한다. 실행 중 오류가 나면 오류 이벤트로 UI가 실패를 표시한다.
- 텍스트 메시지 청크(text message): 모델이 만든 답변을 토큰 단위로 흘려보낸다. 메시지의 시작, 내용 조각, 끝이 나뉘어 오기 때문에 UI는 조각을 이어붙여 타이핑되는 것처럼 보여줄 수 있다.
- 도구 호출(tool call): 에이전트가 도구를 부를 때 호출 시작, 인자, 종료가 단계적으로 전달된다. UI는 "어떤 도구를 어떤 인자로 부르는 중"인지를 실시간으로 노출할 수 있다.
- 상태 갱신(state): 에이전트 내부 상태를 UI와 맞춘다. 전체 상태를 한 번에 실어 보내는 snapshot과, 바뀐 부분만 실어 보내는 delta가 있다. delta를 쓰면 큰 상태 객체를 매번 통째로 보내지 않아도 화면을 최신으로 유지할 수 있다.

이 범주들이 하나의 timeline으로 흐른다. run이 열리고, 텍스트가 스트리밍되다가, 중간에 도구가 호출되고, 상태가 갱신되고, 다시 텍스트로 돌아오고, run이 닫힌다. UI는 이 순서를 그대로 화면의 상태 전이로 옮긴다. Figure 2의 이벤트 스트림이 보여주는 것이 바로 이 흐름이다.

구체적인 예로 문서를 조사해 요약하는 research 에이전트를 생각해 보자. 사용자가 질문을 던지면 run 시작 이벤트가 UI를 로딩 상태로 바꾼다. 곧이어 상태 갱신 이벤트가 `collecting`을 알리며 진행률 카드를 띄우고, 검색 도구 호출 이벤트(시작, 인자, 종료)가 "웹 검색 중"이라는 표시를 켰다 끈다. 자료를 다 모으면 상태가 `summarizing`으로 바뀌고, 이때부터 텍스트 메시지 청크가 요약문을 토큰 단위로 흘려보내 화면에 한 글자씩 채워진다. 마지막으로 run 종료 이벤트가 로딩 표시를 걷어내고 완성된 답변만 남긴다. 백엔드가 하는 일은 이 이벤트들을 순서대로 내보내는 것뿐이고, "언제 무엇을 그릴지"는 이벤트의 종류가 이미 알려 준다.

## UI state patch

에이전트가 긴 작업을 실행할 때 UI는 한 번에 완성된 JSON을 받지 않는다. 중간 상태가 계속 바뀐다. 그래서 state delta는 중요하다. 예를 들어 research 상태가 `collecting`, `reading`, `summarizing`으로 바뀌면 UI는 진행률 카드와 로그를 갱신한다. delta 방식은 대역폭을 아끼고 화면 갱신을 부드럽게 만들지만, patch를 적용하는 쪽이 순서와 중복을 견뎌야 한다는 부담을 진다. 같은 delta를 두 번 받거나 순서가 뒤바뀌어도 최종 화면이 일관되도록 patch를 설계해 두는 것이 뒤에서 다룰 재연결 처리의 전제가 된다.

## Interrupt와 human-in-the-loop

AG-UI는 단순 streaming보다 넓다. 에이전트가 결제 승인, 배포 실행, 외부 메일 발송처럼 위험한 행동을 하려면 사용자의 명시적 확인을 받아야 한다. Interrupt 이벤트는 이 지점을 UI에 노출하고, 사용자의 응답을 다시 런타임으로 돌려보낸다. 즉 이벤트 스트림이 서버에서 클라이언트로 흐르는 한 방향만이 아니라, 사용자의 결정이 다시 실행으로 돌아가는 왕복 경로를 만든다. 이 왕복이 있어야 사람이 판단에 개입하는 흐름(human-in-the-loop)을 화면 위에서 자연스럽게 표현할 수 있다.

## 전송과 통합: 스트리밍으로 붙이는 프런트엔드

AG-UI가 이벤트 기반이라는 사실은 전송 방식에도 직접 영향을 준다. 이벤트는 한 번에 모아서 주는 것이 아니라 생기는 대로 흘려보내야 하므로, 서버에서 클라이언트로 향하는 단방향 스트리밍이 자연스럽다. 대표적으로 SSE(Server-Sent Events)처럼 HTTP 연결 위에서 이벤트를 계속 밀어 보내는 방식이 잘 맞는다. 전송 계층 자체는 특정 기술에 묶이지 않지만, "이벤트를 순서대로 계속 받는다"는 성질은 공통이다.

프런트엔드 쪽에서는 이 이벤트 스트림을 받아 프레임워크의 상태로 옮기는 얇은 어댑터가 필요하다. React라면 이벤트를 구독해 컴포넌트 상태를 갱신하고, 도구 호출 이벤트가 오면 해당 UI 위젯을 띄우는 식이다. AG-UI가 규정하는 것은 이벤트의 형태와 의미이고, 그것을 어떤 컴포넌트로 그릴지는 애플리케이션의 몫이다. 그래서 같은 백엔드 이벤트 스트림을 웹, 모바일, 콘솔이 각자의 방식으로 렌더링할 수 있다.

## 스택에서의 위치: A2A, MCP와 직교하는 층

AG-UI는 에이전트 통신 스택에서 사용자와 가장 가까운 층을 담당한다. 다른 프로토콜과 겹치지 않고 직교한다.

- 백엔드 에이전트끼리의 통신은 [[a2a|A2A]]가 맡는다. 한 에이전트가 다른 에이전트에 작업을 위임하는 수평 통신이고, 배경은 [[a2a-01-overview|A2A 등장 배경]]에서 다룬다.
- 에이전트가 도구와 리소스에 접근하는 것은 [[mcp|MCP]]가 맡는다. 에이전트와 도구 사이의 수직 통신이고, 개요는 [[mcp-01-overview|MCP 개요]]에 정리되어 있다.
- 에이전트와 사용자(프런트엔드) 사이는 AG-UI가 맡는다. 앞의 두 층에서 일어난 일을 사람이 볼 수 있게 화면으로 옮긴다.

이 관계에서 AG-UI는 MCP의 도구 호출이나 A2A의 Task를 대체하지 않는다. MCP 도구 호출 결과와 A2A Task 진행 상태를 사용자에게 보여주는 표현 계층이다. 따라서 AG-UI 이벤트 이름을 업무 도메인에 맞게 정의하되, 하위 프로토콜의 객체를 숨기지 않는 것이 좋다. 세 층이 어떻게 맞물리는지 전체 지도는 [[agent-protocol-stack|Agent Protocol Stack]]에서 한눈에 볼 수 있다.

## 실무 관점: 무엇을 노출하고 어떻게 복구하나

실제로 AG-UI를 붙일 때는 두 가지 판단을 먼저 한다.

첫째, 어떤 이벤트를 UI에 노출할지 고른다. 에이전트가 내보내는 모든 이벤트를 그대로 화면에 흘리면 사용자는 노이즈에 파묻힌다. 최종 답변만 보여주면 "왜 오래 걸리는지" 알 수 없고, 내부 상태를 전부 보여주면 오히려 이해를 방해한다. 그래서 사용자가 판단에 쓸 수 있는 신호(어떤 도구를 부르는 중인지, 어느 단계인지, 승인이 필요한지)를 골라 노출하고, 순수한 내부 계산은 접어 둔다. 이 선택이 곧 에이전트 앱의 UX 수준을 가른다.

둘째, 스트리밍 중 오류와 재연결을 설계한다. 이벤트 스트림은 오래 열려 있는 연결 위에서 흐르므로 도중에 끊길 수 있다. 연결이 끊겼을 때 어디서부터 다시 받을지, 재연결 후 화면 상태를 어떻게 복원할지 정해야 한다. 여기서 상태 갱신 방식이 중요해진다. 바뀐 부분만 보내는 delta만으로는 중간에 놓친 변경을 복구하기 어려우므로, 재연결 시점에 전체 상태 snapshot으로 한 번 맞춘 뒤 다시 delta를 이어받는 조합이 안전하다. 또 상태 patch가 idempotent해야 같은 이벤트를 두 번 받아도 화면이 어긋나지 않는다.

마지막으로 오류 이벤트를 UI에서 어떻게 표현할지도 미리 정한다. run 도중의 실패는 조용히 사라지면 안 되고, 사용자가 재시도할 수 있는 형태로 드러나야 한다. 도구 호출이 실패했는지, 모델이 멈췄는지, 연결이 끊긴 것인지를 구분해 보여주면 사용자와 개발자 모두 문제를 좁히기 쉽다.

## 정리

AG-UI는 에이전트가 "생각하고, 도구를 부르고, 상태를 바꾸는" 과정을 UI로 흘려보내는 이벤트 스트림을 표준화한다. 매번 새로 짜던 백엔드-프런트엔드 사이의 글루 코드를 고정된 이벤트 계약으로 대체하는 것이 핵심이다. 이벤트는 실행 수명주기, 텍스트 메시지 청크, 도구 호출, 상태 갱신 같은 범주로 흐르고, UI는 이를 구독해 화면 상태로 옮긴다.

스택에서 AG-UI의 자리는 분명하다. 에이전트 사이는 A2A, 에이전트와 도구 사이는 MCP, 에이전트와 사용자 사이는 AG-UI다. 세 층은 경쟁하지 않고 각자의 책임을 나눠 가진다. AG-UI를 도입할 때 외울 것은 이벤트 이름이 아니라 "어떤 신호를 사용자에게 보여줄 것인가"와 "끊겼을 때 어떻게 복구할 것인가"라는 두 질문이다.
