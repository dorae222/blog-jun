# 에이전트 통신 표준 지도: MCP, A2A, AG-UI, AGNTCY

에이전트 시스템을 만들 때 가장 먼저 부딪히는 문제는 모델 성능이 아니라 연결 방식이다. 에이전트가 외부 도구를 어떻게 호출할지, 다른 에이전트에게 어떻게 일을 맡길지, 사용자는 중간 과정을 어떻게 볼지, 조직은 어떤 에이전트를 신뢰 가능한 대상으로 등록할지 결정해야 한다. 이 네 질문은 서로 비슷해 보이지만 프로토콜 경계는 다르다.

MCP, A2A, AG-UI, AGNTCY는 이 경계를 나눠서 다루는 표준들이다. 하나가 다른 하나를 대체하는 관계가 아니라, 실제 프로덕션 시스템에서는 서로 결합된다. 이 글은 네 표준을 한 장의 레이어 지도로 묶고, 각 층을 깊게 다루는 시리즈로 안내하는 허브다.

![에이전트 통신 표준 스택](figures/architecture.svg?v=layout-20260706-fix2)

*Figure 2: 에이전트 통신 표준 스택. MCP는 도구/데이터, A2A는 에이전트 간 작업, AG-UI는 사용자 인터페이스, AGNTCY는 발견/신뢰 축에 대응한다. (Source: 각 공식 문서 기반 자체 작성)*

## 세 가지 연결면

| 연결면 | 표준 | 핵심 객체 | 질문 |
|--------|------|-----------|------|
| Agent ↔ Tools/Data | MCP | Tool, Resource, Prompt, Root, Sampling, Elicitation | 이 에이전트가 어떤 외부 시스템에 안전하게 접근할 수 있는가 |
| Agent ↔ Agent | A2A | Agent Card, Task, Message, Part, Artifact | 다른 에이전트에게 일을 맡기고 결과를 추적할 수 있는가 |
| Agent ↔ User | AG-UI | Event, Message, Tool Call, State Delta, Interrupt | 사용자가 에이전트의 진행 상황을 보고 개입할 수 있는가 |

MCP는 에이전트 내부의 수직 연결이다. 에이전트가 CRM, GitHub, PostgreSQL, 파일 시스템 같은 도구와 리소스를 호출한다. A2A는 에이전트 사이의 수평 연결이다. 영업 에이전트가 마케팅 에이전트에게 캠페인 초안을 요청하고, 마케팅 에이전트가 산출물을 Artifact로 돌려준다. AG-UI는 이 모든 과정을 사용자가 볼 수 있게 이벤트로 만든다. 이 표는 통신면 세 개를 다루고, 여기에 발견과 신뢰를 담당하는 AGNTCY가 가로지르는 네 번째 층으로 더해진다.

## 왜 한 표준으로 끝나지 않는가

도구 호출은 짧고 명확한 함수 호출에 가깝다. 반면 에이전트에게 일을 맡기는 것은 장시간 실행되는 Task에 가깝다. 사용자가 보는 UI는 다시 별도의 문제다. 사용자는 JSON-RPC 응답보다 "지금 어떤 도구를 호출했고, 어떤 단계가 끝났는지"를 보고 싶어 한다.

이 차이를 무시하면 모든 것이 REST API가 된다. REST API만으로도 만들 수는 있지만, 스키마 합의, 스트리밍, 권한 전파, 사용자 승인, 중간 산출물 표현을 매번 다시 설계해야 한다. 프로토콜 표준은 이 반복 설계를 줄인다.

층을 나누면 각 층이 독립적으로 진화할 수 있다는 이점도 크다. MCP 서버를 새 도구로 교체해도 A2A 위임 구조는 그대로이고, UI 프레임워크를 바꿔도 백엔드 에이전트는 건드릴 필요가 없다. 반대로 한 덩어리 REST API였다면 이런 변경이 매번 전체 재배포로 번진다. 지도에서 층을 구분하는 진짜 이유는 그림을 깔끔하게 그리기 위해서가 아니라, 바꿀 곳과 그대로 둘 곳을 분리하기 위해서다.

## 네 개의 층, 네 개의 책임

같은 "에이전트 통신"이라는 말 안에 실제로는 성격이 다른 네 가지 문제가 들어 있다. 각 표준은 그중 하나를 맡고, 서로의 책임을 넘보지 않을 때 가장 잘 합성된다. 글머리에서 던진 네 질문을 그대로 각 층에 대응시키면, 도구 접근은 MCP, 일 위임은 A2A, 사용자 노출은 AG-UI, 발견과 신뢰는 AGNTCY로 나뉜다.

### MCP - 수직, 에이전트와 도구

MCP(Model Context Protocol)는 한 에이전트가 도구(Tool), 데이터(Resource), 프롬프트(Prompt)에 접근하는 수직 연결을 표준화한다. 에이전트 "바깥으로" 나가는 통신이 아니라 에이전트 "안에서" 외부 시스템을 끌어오는 통신이다. 책임 범위는 명확하다. 어떤 도구를 노출하고, 어떤 리소스를 읽게 하며, 그 접근에 어떤 권한과 승인을 걸지가 전부 이 층에서 정해진다. 개념은 [[mcp|MCP 스펙 카드]]에서 한눈에 보고, 구현으로 들어가려면 [[mcp-01-overview|MCP 시리즈]] 1편에서 시작해 서버 기능([[mcp-02-server-features|2편]]), 클라이언트 기능([[mcp-03-client-features|3편]]), 전송 계층([[mcp-04-transports|4편]]), 보안과 운영([[mcp-05-security-operations|5편]])을 거쳐 [[mcp-06-fastmcp-internal-api|6편 FastMCP 내부 API]]까지 이어진다.

### A2A - 수평, 에이전트와 에이전트

A2A(Agent-to-Agent Protocol)는 서로 다른 에이전트가 Task를 위임하고 협업하는 수평 연결을 표준화한다. 프레임워크가 제각각인 에이전트들이 공통의 방식으로 서로를 발견하고, 일을 넘기고, 결과를 되받는다. 책임 범위는 Agent Card로 능력을 광고하는 발견, Task로 장시간 작업의 상태를 추적하는 라이프사이클, 그리고 대화(Message)와 결과물(Artifact)을 분리해 회수하는 산출물 관리다. 전체 그림은 [[a2a|A2A 스펙 카드]]에서 보고, [[a2a-01-overview|A2A 시리즈]]는 등장 배경 1편에서 시작해 스펙 분석([[a2a-02-specification|2편]]), MCP와의 직교성([[a2a-03-vs-mcp|3편]]), Python SDK 실전([[a2a-04-python-sdk-tutorial|4편]]), ADK 통합과 보안([[a2a-05-adk-integration|5편]])으로 이어진다.

### AG-UI - 프런트엔드, 에이전트와 사용자

AG-UI는 에이전트의 활동을 UI에 실시간 이벤트로 흘려보내는 프런트엔드 연결을 표준화한다. 백엔드에서 무슨 일이 일어나는지를 사용자가 볼 수 있게 만드는 것이 목적이다. 책임 범위는 실행 단계를 스트림으로 내보내는 event, 화면 상태를 부분 갱신하는 state delta, 그리고 사용자의 승인이나 수정 입력을 받는 interrupt다. 개념은 [[ag-ui|AG-UI 스펙 카드]]에서 보고, 이벤트 모델을 구체적으로 다루는 글은 [[ag-ui-realtime-events|AG-UI 실시간 이벤트]]다.

### AGNTCY - 디렉토리, 발견과 신뢰

AGNTCY는 조직 경계를 넘는 에이전트 발견과 신뢰를 다룬다. 앞의 세 층이 "어떻게 통신하는가"라면 AGNTCY는 "누구와 통신해도 되는가"에 답한다. 분산된 디렉토리에서 에이전트 메타데이터를 찾고, 신뢰 그래프로 어떤 상대를 후보로 남길지 판단한다. 통신 자체보다 디스커버리와 신뢰에 무게를 두기 때문에 A2A의 Agent Card 발견과 일부 겹치지만, 조직 사이의 분산 신뢰 모델이라는 점이 다르다. 자세한 내용은 [[agntcy-agent-discovery-trust|AGNTCY 에이전트 발견과 신뢰]]에서 다룬다.

처음 읽는다면 도구 접근(MCP)부터 시작해 위임(A2A), 사용자 노출(AG-UI), 발견과 신뢰(AGNTCY) 순으로 층을 쌓아 올리고, 네 층을 하나의 레퍼런스 아키텍처로 묶는 것은 [[agent-protocol-production-reference|Agent Protocol 종합 실전]]에서 확인한다.

## 이름만 비슷한 네 표준

네 이름은 처음에 서로 헷갈리기 쉽다. 특히 AG-UI와 AGNTCY는 철자가 비슷하지만 담당 영역이 정반대다. AG-UI는 에이전트와 사람 사이의 화면 통신이고, AGNTCY는 에이전트와 에이전트 사이의 발견과 신뢰다. A2A와 AGNTCY도 겹쳐 보이지만, A2A는 이미 아는 상대에게 일을 넘기는 통신이고 AGNTCY는 그 상대를 어디서 찾고 믿어도 되는지를 먼저 판단한다. MCP만 방향이 처음부터 분명하다. 에이전트가 도구를 불러오는 유일한 수직 축이다. 그래서 이 지도를 읽을 때는 약자를 외우기보다 "사람과의 통신인가(AG-UI), 에이전트끼리의 통신인가(A2A), 상대를 찾는 문제인가(AGNTCY), 도구를 부르는 문제인가(MCP)"라는 방향으로 구분하는 편이 오래 남는다.

## 실제 조합 패턴

가장 일반적인 패턴은 다음과 같다.

1. React UI는 AG-UI로 Orchestrator Agent의 실행 이벤트를 구독한다.
2. Orchestrator Agent는 A2A로 Research Agent와 Writer Agent에 Task를 위임한다.
3. 각 전문 에이전트는 MCP로 사내 검색, 데이터베이스, 문서 렌더링 도구에 접근한다.
4. 진행 상태는 AG-UI 이벤트로 사용자에게 노출되고, 산출물은 A2A Artifact로 회수된다.

이 구조에서 MCP 서버는 도구 제공자이고, A2A 에이전트는 업무 능력 제공자이며, AG-UI는 사용자 경험 제공자다. 세 표준을 한 레이어에 몰아넣지 않는 것이 핵심이다.

## 네 층이 함께 도는 예

위 패턴을 실제 요청 하나로 따라가 보면 각 층이 어디서 등장하는지 분명해진다. 사용자가 대시보드에서 "지난 분기 이탈 위험 고객을 뽑고, 각 고객에게 보낼 리텐션 메일 초안을 만들어줘"라고 입력했다고 하자.

1. **AG-UI로 시작한다.** React 대시보드는 orchestrator agent에 요청을 넘기고 실행 이벤트를 구독한다. 사용자는 "고객 조회 중", "초안 작성 중" 같은 단계를 실시간으로 본다.
2. **AGNTCY로 상대를 찾는다.** orchestrator는 이 작업에 필요한 전문 에이전트를 디렉토리에서 검색한다. "고객 분석" 능력을 가진 Analytics Agent와 "카피라이팅" 능력을 가진 Writer Agent를 발견하고, 신뢰 정책을 통과한 후보만 남긴다.
3. **A2A로 일을 넘긴다.** orchestrator는 Analytics Agent에 "이탈 위험 고객 추출" Task를 위임하고, 그 결과를 받아 Writer Agent에 "리텐션 메일 초안" Task를 넘긴다. 각 Task의 상태와 산출물은 Artifact로 추적된다.
4. **MCP로 도구를 쓴다.** Analytics Agent는 내부적으로 MCP로 데이터 웨어하우스와 BI 도구를 호출하고, Writer Agent는 MCP로 사내 브랜드·톤 가이드 Resource를 읽는다.
5. **다시 AG-UI로 돌아온다.** 완성된 초안과 근거는 AG-UI 이벤트로 대시보드에 렌더링되고, 사용자는 승인하거나 수정한다.

한 요청이 네 층을 모두 지나지만 책임은 겹치지 않는다. 발견은 AGNTCY, 위임은 A2A, 도구 접근은 MCP, 사용자 노출은 AG-UI가 맡는다. 장애가 났을 때도 "어느 층의 문제인가"부터 물으면 원인을 좁히기 쉽다.

관측 관점에서는 이 여러 층이 하나의 흐름으로 이어져야 한다. AG-UI의 실행 이벤트, A2A의 Task, MCP의 도구 호출이 각자 자기 식별자를 남기고, 그 식별자들이 하나의 trace로 연결될 때 비로소 "사용자 요청 하나가 어느 에이전트의 어느 도구까지 흘렀는지"를 되짚을 수 있다. 지도를 볼 때 박스 이름만 보지 말고 층 사이를 잇는 화살표에 주목하라고 말하는 이유가 여기에 있다.

## 언제 무엇이 필요한가

네 표준을 전부 도입할 필요는 없다. 시스템이 지금 풀려는 문제에 따라 필요한 층이 다르다.

| 상황 | 필요한 층 | 판단 기준 |
|------|-----------|-----------|
| 에이전트가 외부 DB, API, 파일에 접근해야 한다 | MCP | 도구와 리소스 접근은 수직 연결 문제다 |
| 여러 에이전트가 하나의 목표를 나눠 처리한다 | A2A | 작업 위임과 결과 추적은 수평 연결 문제다 |
| 사용자가 진행 상황을 실시간으로 보고 중간에 개입해야 한다 | AG-UI | 실행 상태 노출과 승인은 프런트엔드 문제다 |
| 조직 밖의 에이전트를 안전하게 찾아 신뢰해야 한다 | AGNTCY | 발견과 신뢰는 디렉토리 계층 문제다 |
| 단일 에이전트와 몇 개의 도구만으로 끝난다 | MCP만 | 나머지 세 층은 아직 과설계다 |

표를 읽는 방향은 "무슨 기술이 좋은가"가 아니라 "지금 어떤 경계가 필요한가"다. 경계가 늘어날 때마다 층을 하나씩 얹으면 된다. 네 층을 한 번에 조합하는 프로덕션 관점의 정리는 [[agent-protocol-production-reference|Agent Protocol 종합 실전]]에서 이어진다.
