# MCP Client Features: Roots, Sampling, Elicitation

MCP는 서버가 기능을 제공하고 클라이언트가 호출하는 단방향 프로토콜처럼 보이지만, 실제 스펙은 클라이언트가 서버에 제공하는 기능도 정의한다. Roots, Sampling, Elicitation이 그 세 축이다.

세 기능의 공통점부터 짚는 편이 이해가 빠르다. 셋 다 서버가 아니라 클라이언트가 구현한다. 서버는 이 세 통로를 통해 호스트가 가진 능력, 즉 파일 접근 범위(Roots), LLM 모델(Sampling), 사용자(Elicitation)를 안전하게 빌려 쓴다. 서버가 스스로 전체 파일 시스템을 뒤지거나, 자체 모델 API 키를 들고 있거나, 사용자 화면을 직접 띄우는 대신, 클라이언트에게 요청을 보내고 클라이언트가 통제권을 쥔 채 응답한다. 방향이 서버에서 클라이언트로 흐르지만 최종 결정권은 언제나 클라이언트와 사용자에게 남는다는 점이 핵심이다.

서버가 제공하는 primitive인 tool, resource, prompt는 [[mcp-02-server-features|MCP 서버 기능]]에서 다뤘다. 이 글은 방향이 반대인 세 기능, 즉 서버가 클라이언트에게 요청하는 흐름을 다룬다. 세 기능이 각각 무엇을 빌리는지 한 줄로 요약하면 다음과 같다.

:::info
Roots는 클라이언트의 파일 경계를, Sampling은 클라이언트가 붙인 모델을, Elicitation은 클라이언트 뒤의 사용자를 서버가 빌려 쓰는 통로다. 셋 다 요청은 서버가 하지만 응답과 통제는 클라이언트가 쥔다.
:::

## Roots: 작업 가능한 경계 선언

Roots는 클라이언트가 서버에게 접근 가능한 URI 또는 파일 시스템 경계를 알려주는 기능이다. 클라이언트는 자신이 서버에 열어 줄 작업 영역을 root 목록으로 선언한다. 대표적으로 사용자가 편집기에서 열어 둔 프로젝트 폴더가 root가 된다. 예를 들어 코드 리뷰 MCP 서버는 클라이언트가 노출한 workspace root를 확인하고, 그 안에서만 파일을 읽고 분석한다.

Roots가 중요한 이유는 서버가 임의로 전체 파일 시스템을 탐색하지 못하게 만드는 데 있다. 서버는 클라이언트가 승인한 경계 밖을 볼 근거가 없고, 클라이언트는 root 목록에 최소한의 URI만 담아 노출 범위를 좁힐 수 있다. 즉 Roots는 서버가 무엇을 요구하든 실제 접근 범위를 클라이언트가 정하는 구조다. root 목록이 전달하는 정보는 대체로 다음과 같다.

- 각 root는 보통 파일 시스템 위치를 가리키는 URI로 표현되며, 사용자가 연 폴더 하나에 대응한다
- 여러 root를 동시에 노출할 수 있어 다중 프로젝트나 monorepo 작업 영역을 함께 표현한다
- 사용자가 폴더를 열거나 닫으면 클라이언트가 목록을 갱신해 서버에 알려, 경계가 세션 중에도 사용자 행동을 따라간다

Roots는 보안 기능이자 UX 기능이다. 사용자는 "이 서버가 이 프로젝트 폴더 안에서만 작업한다"는 경계를 눈으로 확인할 수 있고, 서버는 상대 경로와 프로젝트 구조를 일관되게 해석할 수 있다. 사용자가 다른 폴더를 열거나 닫으면 클라이언트가 root 목록을 갱신해 서버에 알려 주므로, 경계는 세션 중에도 고정되지 않고 사용자 행동을 따라 움직인다.

한 가지 유의할 점은 Roots가 접근 범위를 "통보"하는 채널이지 그 자체로 강제 격리 장치는 아니라는 것이다. 실제 격리, 즉 서버 프로세스가 경계 밖 파일을 물리적으로 못 읽게 막는 일은 호스트 환경과 권한 설정의 몫이다. 이 경계를 어떻게 강제하고 감사할지는 [[mcp-05-security-operations|MCP 보안과 운영]]에서 다룬다.

## Sampling: 서버가 모델 호출을 요청하는 경우

Sampling은 서버가 클라이언트에게 LLM completion을 요청하는 역방향 기능이다. 방향이 흥미롭다. 보통은 클라이언트(호스트 앱) 안의 모델이 서버의 tool을 호출하지만, Sampling에서는 반대로 서버가 클라이언트가 보유한 모델에게 추론을 부탁한다.

이 구조의 실익은 서버가 자체 모델 API 키를 갖지 않아도 된다는 데 있다. 서버는 호스트가 이미 연결해 둔 모델을 제한적으로 빌려 쓰고, 모델 선택과 비용 부담은 호스트 쪽에 남는다. 예를 들어 문서 검색 서버가 검색 결과를 자연어로 요약해야 하지만 스스로 모델을 붙이고 싶지 않다면, 요약 프롬프트를 Sampling 요청으로 보내 클라이언트의 모델이 대신 처리하게 만들 수 있다. 여러 도구가 각자 API 키와 과금 계정을 관리하는 대신, 모델 접근을 호스트 한 곳으로 모으는 효과가 있다.

Sampling의 설계 의도에는 사람이 개입하는 흐름(human-in-the-loop)이 들어 있다. 서버가 프롬프트를 보내면 클라이언트가 그 요청을 사용자에게 보여 주고 승인을 받은 뒤 모델을 호출한다. 서버는 "요청"만 할 뿐 모델을 직접 실행하지 못하며, 요청의 각 축을 누가 정하는지가 분명하게 갈린다.

- 어떤 모델을 호출할지: 클라이언트가 결정한다
- 서버가 프롬프트에 실을 수 있는 컨텍스트 범위: 클라이언트가 제한한다
- 요청을 실제로 실행할지 여부: 사용자가 승인한다
- 모델 응답을 그대로 돌려줄지, 검토·수정 후 돌려줄지: 사용자와 클라이언트가 정한다

다만 Sampling은 강력한 만큼 남용 위험이 크다. 통제가 없다면 다음과 같은 문제가 생길 수 있다.

- 악의적이거나 잘못 설계된 서버가 프롬프트에 민감 데이터를 실어 밖으로 빼돌린다
- 무관한 작업으로 호스트 모델 비용을 소모한다
- 사용자가 의도하지 않은 추론을 반복 호출한다 그래서 클라이언트는 프롬프트 검토, 서버가 볼 수 있는 컨텍스트 제한, 호출 빈도와 비용 통제 같은 장치를 반드시 둔다. 서버 요청을 자동 승인하지 않는 것이 기본이며, 이 통제를 어디에 두고 무엇으로 감사할지는 [[mcp-05-security-operations|MCP 보안과 운영]]에서 이어 다룬다.

## Elicitation: 실행 중 구조화된 사용자 입력 요청

Elicitation은 서버가 작업을 진행하다가 사용자에게 추가 정보를 요청하는 기능이다. 요청은 임의의 자유 텍스트가 아니라 스키마로 구조를 갖춰 전달된다. 서버가 "이런 필드가 이런 타입으로 필요하다"고 스키마로 명시하면, 클라이언트는 그에 맞는 입력 폼을 사용자에게 보여 주고 값을 받아 서버로 돌려준다.

전형적인 쓰임은 다음과 같다.

- 누락 파라미터 수집: 항공권 예약 도구가 여권 영문명이나 좌석 선호가 빠졌다는 사실을 알면, 서버는 클라이언트를 통해 사용자에게 필요한 값을 요청한다
- 실행 전 확인: 되돌리기 어려운 작업을 실행하기 직전에 "정말 진행할까요" 같은 확인을 구조화된 입력으로 받는다
- 분기 선택: 여러 처리 경로가 가능할 때 사용자가 하나를 고르도록 선택지를 스키마로 제시한다

Elicitation의 값어치는 LLM이 임의로 누락 값을 추측하지 않게 만드는 데 있다. 필요한 필드를 모델의 상상에 맡기는 대신 서버가 명시적으로 요청하므로, 잘못된 값이 조용히 채워지는 사고를 줄인다. 스키마 기반이라 클라이언트가 타입 검증과 폼 렌더링을 일관되게 처리할 수 있다는 점도 폼 중심 업무와 잘 맞는다.

여기서도 통제권은 사용자에게 있다. 사용자는 요청받은 값을 채워 줄 수도, 거절하거나 취소할 수도 있다. 서버는 사용자 화면을 직접 건드리지 못하고 클라이언트를 매개로만 요청한다. 민감 정보가 오갈 수 있으므로, 어떤 값을 요청받았고 사용자가 무엇을 제출했는지, 그 값이 어디에 저장되고 전송되는지를 명확히 표시하고 남기는 일이 중요하다.

## 세 기능을 관통하는 원칙: 클라이언트가 통로를 통제한다

세 기능을 각각 보면 파일 경계, 모델 호출, 사용자 입력으로 서로 다른 주제처럼 보이지만, 관통하는 원칙은 하나다. 이 기능들은 서버가 아니라 클라이언트가 구현하며, 서버가 호스트의 능력을 안전하게 빌리는 통로라는 것이다. 빌리는 대상만 다를 뿐 구조는 같다.

- Roots: 서버가 호스트의 파일 접근 범위를 빌린다
- Sampling: 서버가 호스트가 연결한 LLM 모델을 빌린다
- Elicitation: 서버가 호스트 뒤의 사용자를 빌린다

이 점이 [[mcp-02-server-features|MCP 서버 기능]]과 대칭을 이룬다. tool, resource, prompt에서는 서버가 능력을 제공하고 클라이언트가 소비한다. Roots, Sampling, Elicitation에서는 반대로 서버가 요청하고 클라이언트가 능력을 내어 준다. 두 방향을 합쳐야 MCP가 단순 함수 호출 규약이 아니라 호스트와 서버가 서로의 자원을 조율하는 프로토콜이 된다.

통로를 클라이언트가 쥐고 있다는 사실은 실무에 직접적인 결과를 남긴다. 첫째, 서버는 이 기능들의 존재를 당연시할 수 없다. 연결된 클라이언트가 해당 기능을 구현하지 않았다면 Sampling도 Elicitation도 애초에 불가능하다. 둘째, 같은 기능이라도 클라이언트마다 승인 UX와 노출 정책이 달라, 서버가 기대한 흐름이 그대로 재현되지 않을 수 있다. 그래서 이 기능들을 쓰는 서버는 "요청이 거절되거나 지원되지 않을 수 있다"를 정상 경로로 가정하고 설계해야 한다.

## 한 흐름에서 세 기능이 함께 쓰이는 예

세 기능은 따로 노는 옵션이 아니라 하나의 작업 흐름 안에서 자연스럽게 이어진다. 코드 리팩터링 MCP 서버를 예로 들면 흐름은 다음과 같이 전개된다.

1. Roots: 클라이언트가 사용자의 프로젝트 폴더를 root로 노출한다. 서버는 그 경계 안의 파일만 읽어 리팩터링 후보를 찾는다.
2. Sampling: 서버가 변경 요약 문구를 만들어야 하지만 자체 모델이 없으므로, 요약 프롬프트를 Sampling 요청으로 보낸다. 클라이언트는 사용자에게 프롬프트와 대상 모델을 보여 주고 승인을 받은 뒤 결과를 돌려준다.
3. Elicitation: 여러 파일을 실제로 수정하기 직전에, 서버는 "이 파일들을 변경합니다. 진행할까요"를 구조화된 확인 입력으로 요청한다. 사용자가 승인하면 그때 변경이 적용된다.

이 흐름에서 서버는 파일 경계, 모델, 사용자 확인이라는 세 가지 호스트 자원을 차례로 빌렸지만, 각 단계의 승인과 범위는 모두 클라이언트와 사용자가 통제했다. 세 기능을 관통하는 원칙이 실제 작업에서 어떻게 맞물리는지 보여 주는 전형적인 예다.

## 설계 원칙

| 기능 | 서버가 원하는 것 | 클라이언트가 지켜야 할 것 |
|------|------------------|--------------------------|
| Roots | 작업 경계 | 최소 권한 URI만 노출, 경계 변화 통지 |
| Sampling | 모델 추론 | 사용자 승인, 프롬프트 검토, 모델·비용 통제 |
| Elicitation | 추가 입력 | 스키마 검증, 민감 정보 표시, 거절 경로 제공 |

이 표의 방향은 일정하다. 왼쪽은 서버의 요구이고, 오른쪽은 클라이언트가 그 요구를 받아 주되 통제권을 놓지 않기 위한 조건이다. 서버 요구가 강할수록 클라이언트 쪽 통제 항목이 늘어난다는 점이 세 기능에 공통으로 나타난다.

## 실무 관점: capability negotiation과 승인 UX

실제로 세 기능을 쓸 때 먼저 확인할 것은 "이 클라이언트가 무엇을 지원하는가"다. MCP는 연결 초기화 단계에서 클라이언트와 서버가 각자의 capability를 서로 알린다(capability negotiation). 서버는 이 협상 결과를 보고 상대 클라이언트가 Roots, Sampling, Elicitation 중 무엇을 구현했는지 판단해야 한다. 어떤 클라이언트는 세 기능을 모두 지원하고, 어떤 클라이언트는 Roots만 지원하거나 Sampling을 아예 제공하지 않는다. 협상 결과를 무시하고 지원하지 않는 기능을 호출하면 흐름이 그 자리에서 끊긴다.

따라서 서버 구현은 기능 부재를 정상 상황으로 다뤄야 한다. Sampling을 지원하지 않는 클라이언트에 연결되면 자체 요약을 포기하거나 대체 경로로 우회하고, Elicitation이 없으면 누락 값을 즉시 오류로 반환하기보다 사용자에게 다른 방식으로 알리는 식이다. 기능을 당연시하고 짠 서버는 특정 클라이언트에서만 동작하는 반쪽짜리가 된다.

클라이언트 쪽에서 가장 신경 쓸 지점은 Sampling 승인 UX다. 좋은 승인 화면은 서버가 보낸 프롬프트 전문, 호출될 모델, 그리고 승인/거절 선택지를 사용자에게 함께 보여 준다. 나아가 응답을 서버에 돌려주기 전에 사용자가 내용을 검토하거나 수정할 여지를 두면, 서버가 프롬프트나 결과를 통해 원치 않는 데이터를 흘려보내는 위험을 줄일 수 있다. Roots는 사용자가 폴더를 고르는 명시적 동작으로, Elicitation은 스키마 기반 폼과 거절 버튼으로 통제권을 노출하는 것이 자연스럽다.

이 세 기능을 어디까지 열어 줄지, 그리고 승인과 노출을 어떻게 감사할지는 결국 보안 설계와 맞닿는다. transport 계층에서 이 요청들이 어떻게 오가는지는 [[mcp-04-transports|MCP Transport]]에서, consent와 권한 통제는 [[mcp-05-security-operations|MCP 보안과 운영]]에서 이어 다룬다.
