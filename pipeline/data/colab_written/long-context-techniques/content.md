# Long Context LLM: 100K+ 토큰 처리의 원리와 기법

## 들어가며

:::info
이 글은 LLM의 컨텍스트 윈도우 확장 기법을 체계적으로 다루는 튜토리얼이다. [[1_attention-is-all-you-need|Attention]] 메커니즘에 대한 기본 이해를 전제로 하며, [[inference-optimization-mfu|추론 최적화]]와 [[context-compression|Context Compression]]을 함께 참고하면 좋다.
:::

2023년까지 대부분의 LLM은 4K~8K 토큰의 컨텍스트 윈도우를 가졌다. 2024년에는 [[gemini|Gemini]] 1.5(1M+), Claude 3(200K), GPT-4 Turbo(128K)로 급격히 확장되었고, 2025년에는 [[gemini-2-5|Gemini 2.5 Pro]](2M+), Claude 4(1M+), GPT-5(256K+)까지 도달하며 1M 토큰 이상이 사실상 표준이 되었다. 2026년 현재, 대부분의 주요 LLM은 최소 128K 이상의 컨텍스트를 지원하며, 프론티어 모델은 2M 토큰 이상을 처리할 수 있다.

이 글에서는 컨텍스트 윈도우를 확장하는 **핵심 기법**과 **효율적인 장문 처리 전략**을 비교 분석하고, 실전에서 어떤 기법을 선택해야 하는지 가이드를 제공한다.

---

## Long Context가 어려운 이유

### Attention의 이차 복잡도

Transformer의 Self-Attention은 시퀀스 길이 $n$에 대해 $O(n^2)$ 연산이 필요하다. 이 이차 복잡도는 컨텍스트 길이가 늘어나면 급격히 증가한다.

| 컨텍스트 길이 | 연산량 | 기준 대비 배율 | 실용성 |
|-------------|--------|:------------:|--------|
| 4K | 16M | 1x | 기본 |
| 32K | 1B | 64x | 단일 GPU 가능 |
| 128K | 16.4B | 1,024x | 최적화 필요 |
| 512K | 262B | 16,384x | 다중 GPU 또는 효율화 기법 필수 |
| 1M | 1T | 62,500x | 분산 처리 + 효율화 기법 조합 필수 |

### KV-Cache 메모리 폭발

추론 시 KV-Cache는 시퀀스 길이에 비례하여 증가한다:

$$\text{KV 메모리} = 2 \times L \times d \times n \times \text{precision}$$

여기서 $L$은 레이어 수, $d$는 모델 차원, $n$은 시퀀스 길이, precision은 데이터 타입 크기이다.

| 모델 규모 | 컨텍스트 길이 | KV-Cache (FP16) | 단일 GPU 가능 여부 |
|----------|-------------|:---------------:|:---------:|
| 7B (32L, 4096d) | 32K | ~16 GB | A100 80GB 가능 |
| 7B (32L, 4096d) | 128K | ~64 GB | A100 80GB 근소 |
| 70B (80L, 8192d) | 128K | ~320 GB | 불가능 |
| 70B (80L, 8192d) | 1M | ~2.5 TB | 불가능 |

이처럼 Long Context는 **연산 복잡도**와 **메모리 용량** 모두에서 병목이 발생한다.

## 기법 전체 비교

Long Context를 달성하기 위한 주요 기법을 목적별로 분류하면 다음과 같다.

| 기법 | 분류 | 목적 | 핵심 아이디어 | 대표 모델 |
|------|------|------|-------------|----------|
| Position Interpolation | 위치 인코딩 | RoPE 확장 | 위치 인덱스 스케일링 | CodeLlama |
| YaRN | 위치 인코딩 | 개선된 RoPE 확장 | 주파수별 차등 스케일링 | Qwen2.5, Yi |
| NTK-aware Scaling | 위치 인코딩 | RoPE 확장 | 주파수 베이스 조정 | 다수 오픈소스 |
| Sliding Window | 어텐션 효율화 | 복잡도 감소 | 로컬 윈도우 제한 | Mistral, Mixtral |
| Ring Attention | 분산 처리 | 다중 디바이스 | KV 링 전달 | 연구 모델 |
| GQA | KV-Cache 절감 | 메모리 절약 | KV 헤드 그룹화 | [[llama-3]], Qwen2.5 |
| KV-Cache 양자화 | KV-Cache 절감 | 메모리 절약 | 정밀도 축소 | vLLM, TGI |
| KV-Cache 압축 | KV-Cache 절감 | 메모리 절약 | 불필요 토큰 제거 | H2O, StreamingLLM |

## 위치 인코딩 확장 기법

### RoPE 복습

RoPE(Rotary Position Embedding)는 현재 대부분의 LLM이 사용하는 위치 인코딩이다. 위치 $m$에서의 쿼리-키 내적이 상대적 거리 $m-n$에만 의존하도록 회전 행렬을 적용한다.

문제는 학습 시 최대 길이(예: 4K)보다 긴 시퀀스에서 **학습하지 않은 위치에 대한 외삽(extrapolation)**이 필요하며, 이 경우 성능이 급격히 저하된다는 점이다.

### Position Interpolation (PI)

Chen et al.(2023)이 제안한 방법이다. 학습된 위치 범위를 **압축**하여 더 긴 시퀀스를 수용한다:

$$f'(x, m) = f(x, \frac{m \cdot L}{L'})$$

4K로 학습된 모델에 32K 컨텍스트를 적용하려면, 위치 인덱스를 $\frac{1}{8}$로 스케일링한다. 이 방식은 외삽(extrapolation)이 아니라 **보간(interpolation)**이므로 안정적이다.

| 항목 | 내용 |
|------|------|
| 핵심 원리 | 위치 인덱스를 선형 스케일링하여 학습된 범위 내로 매핑 |
| 장점 | 소량의 추가 학습(1,000 steps)으로 4~8배 확장 가능 |
| 한계 | 해상도가 낮아져 가까운 토큰 간 구분력 감소 |
| 적용 모델 | CodeLlama (4K → 16K) |

### YaRN (Yet another RoPE extensioN)

Peng et al.(2023)이 Position Interpolation의 한계를 극복하기 위해 제안했다. 핵심 아이디어는 **주파수별 차등 스케일링**이다.

- **고주파 성분** (짧은 거리 인코딩): 보간 없이 유지하여 가까운 토큰 구분력 보존
- **저주파 성분** (긴 거리 인코딩): 보간 적용하여 먼 토큰까지 확장
- **중간 주파수**: 고주파와 저주파 사이를 부드럽게 전환

| 항목 | 내용 |
|------|------|
| 핵심 원리 | RoPE 차원별 주파수에 따라 스케일링 비율을 차등 적용 |
| 장점 | PI 대비 같은 확장 비율에서 더 높은 품질 |
| 한계 | 하이퍼파라미터 튜닝이 필요 |
| 적용 모델 | Qwen2.5, Yi-34B |

### NTK-aware Scaling

NTK(Neural Tangent Kernel) 이론에 기반한 접근이다. 위치 인코딩의 **주파수 베이스** $\theta$를 조정하여, 별도 학습 없이도 컨텍스트를 확장할 수 있다.

$$\theta' = \theta \cdot \alpha^{d/(d-2)}$$

| 항목 | 내용 |
|------|------|
| 핵심 원리 | RoPE의 base frequency를 확장 비율에 맞게 스케일링 |
| 장점 | 추가 학습 없이 즉시 적용 가능 |
| 한계 | 대폭 확장(8x 이상)에서 품질 저하 |
| 적용 모델 | 다양한 오픈소스 모델 (런타임 적용) |

### 위치 인코딩 기법 비교

| 기법 | 추가 학습 | 확장 비율 | 근거리 품질 | 원거리 품질 | 구현 난이도 |
|------|:---------:|:---------:|:----------:|:----------:|:----------:|
| PI | 필요 (소량) | 4~8x | 보통 | 좋음 | 쉬움 |
| YaRN | 필요 (소량) | 4~32x | 좋음 | 좋음 | 보통 |
| NTK-aware | 불필요 | 2~4x | 좋음 | 보통 | 쉬움 |
| Dynamic NTK | 불필요 | 2~8x | 좋음 | 보통 | 쉬움 |

## Sliding Window Attention

Mistral/Mixtral이 채택한 방법이다. 각 토큰이 **최근 W개의 토큰에만** 어텐션을 수행하여 복잡도를 선형으로 낮춘다.

```
윈도우 크기 W = 4096

토큰 위치 0~4095: 전체 어텐션
토큰 위치 4096: 위치 1~4096에만 어텐션 (0은 제외)
토큰 위치 8192: 위치 4097~8192에만 어텐션
```

### 정보 전파 메커니즘

단일 레이어에서는 윈도우 W 내부만 볼 수 있지만, 레이어를 쌓으면 **간접적으로** 윈도우 밖 정보에 접근할 수 있다. $k$개 레이어를 거치면 최대 $k \times W$ 거리의 토큰까지 정보가 전파된다.

| 항목 | 내용 |
|------|------|
| 복잡도 | $O(n \cdot W)$ - 시퀀스 길이에 선형 |
| 장점 | 메모리와 연산 모두 효율적, 구현 간단 |
| 한계 | 윈도우 밖의 정보에 대한 직접 접근 불가 |
| 적용 모델 | Mistral 7B (W=4096), Mixtral 8x7B |

:::warning
Sliding Window Attention은 **긴 문서 전체를 참조해야 하는 작업**(예: 문서 요약, 장편 Q&A)에서는 성능이 저하될 수 있다. 이런 작업에는 전체 어텐션 또는 하이브리드 방식이 더 적합하다.
:::

## Ring Attention

### 원리

Liu et al.(2023)이 제안한 분산 처리 기법이다. 긴 시퀀스를 **여러 디바이스에 분할**하고, 각 디바이스가 자신의 청크에 대해 어텐션을 수행하면서 KV를 링 형태로 전달한다.

```
Device 0: 토큰 0~32K     → 자체 어텐션 + Device 1의 KV 수신
Device 1: 토큰 32K~64K   → 자체 어텐션 + Device 2의 KV 수신
Device 2: 토큰 64K~96K   → 자체 어텐션 + Device 0의 KV 수신
(... 링 형태로 KV 블록이 순환)
```

이론적으로 **디바이스 수에 비례하여 컨텍스트 길이를 확장**할 수 있다. N개 디바이스를 사용하면 단일 디바이스 대비 N배의 시퀀스를 처리할 수 있다.

### 장점과 한계

| 항목 | 내용 |
|------|------|
| 확장성 | 디바이스 수에 비례하여 컨텍스트 확장 |
| 통신 패턴 | P2P 링 통신 (AllReduce 불필요) |
| 장점 | 이론적으로 무한 컨텍스트 가능, 메모리 병목 해소 |
| 한계 | 디바이스 간 고대역폭 필요, 구현 복잡 |
| 적용 | 연구 단계, 일부 대규모 학습 파이프라인 |

### Flash Attention과의 관계

[[inference-optimization-mfu|Flash Attention]]은 어텐션의 **연산 효율**을 높이는 것이지, 복잡도 자체를 줄이지는 않는다. 그러나 HBM-SRAM 간 데이터 이동을 최적화하여 메모리 효율이 크게 개선된다.

| 비교 항목 | Flash Attention | Ring Attention |
|----------|:--------------:|:--------------:|
| 목적 | 단일 GPU 효율화 | 다중 GPU 확장 |
| 복잡도 변화 | $O(n^2)$ 유지 | 디바이스당 $O((n/N)^2)$ |
| 메모리 효과 | SRAM 활용으로 피크 메모리 감소 | 시퀀스 분할로 디바이스당 메모리 감소 |
| 조합 가능 | - | Flash Attention과 함께 사용 가능 |

## KV-Cache 최적화 기법

Long Context에서 KV-Cache가 메모리 병목이 되므로, 이를 최적화하는 기법이 핵심이다.

### GQA (Grouped Query Attention)

KV 헤드를 그룹으로 묶어 KV-Cache를 줄이는 구조적 접근이다. [[llama-3|LLaMA 3]], Qwen2.5 등 최신 모델이 기본 채택하고 있다.

| 어텐션 방식 | Q 헤드 | K 헤드 | V 헤드 | KV 메모리 비율 |
|-----------|:------:|:------:|:------:|:------------:|
| MHA | 32 | 32 | 32 | 100% |
| GQA (8그룹) | 32 | 8 | 8 | 25% |
| GQA (4그룹) | 32 | 4 | 4 | 12.5% |
| MQA | 32 | 1 | 1 | 3.125% |

GQA는 MHA 대비 KV-Cache를 대폭 줄이면서도, MQA보다 높은 표현력을 유지하는 균형점을 제공한다.

### KV-Cache 양자화

KV-Cache의 정밀도를 낮추어 메모리를 절감하는 방법이다.

| 정밀도 | 토큰당 KV 크기 | 메모리 절감률 | 품질 영향 |
|--------|:------------:|:-----------:|:--------:|
| FP16 | 기준 | 0% | 없음 |
| INT8 | 50% | 50% | 미미 |
| INT4 | 25% | 75% | 약간 |
| FP8 | 50% | 50% | 극소 |

vLLM 2.0+에서는 `--kv-cache-dtype fp8` 옵션으로 간단히 적용할 수 있다.

### KV-Cache 압축 (Eviction)

모든 토큰의 KV를 유지하지 않고, 중요하지 않은 토큰을 제거하거나 병합하는 방법이다.

| 기법 | 전략 | 유지 토큰 | 장점 | 한계 |
|------|------|----------|------|------|
| H2O | 어텐션 점수 기반 | 상위 K개 heavy hitter | 동적 선택, 정보 손실 최소 | 매 스텝 점수 계산 오버헤드 |
| StreamingLLM | 위치 기반 | 초기 몇 개 + 최근 윈도우 | 무한 스트리밍 가능, 간단 | 중간 정보 완전 손실 |
| Scissorhands | 히스토리 기반 | 과거 중요도 누적 | 장기 중요도 반영 | 구현 복잡 |

## "Lost in the Middle" 문제

### 현상

Liu et al.(2023)의 발견에 따르면, LLM이 긴 컨텍스트의 **처음과 끝**에 위치한 정보는 잘 활용하지만, **중간에 위치한 정보는 무시**하는 경향이 있다.

### 원인 분석

| 원인 | 설명 |
|------|------|
| 어텐션 편향 | Self-Attention이 시작과 끝에 집중하는 구조적 편향 |
| 학습 데이터 패턴 | 중요 정보가 시작/끝에 위치하는 데이터 분포 |
| 위치 인코딩 한계 | 긴 거리의 위치 정보가 희석되는 RoPE 특성 |
| Attention Sink | 초기 토큰에 어텐션이 과도하게 집중되는 현상 |

### 벤치마크 결과

다중 문서 질의응답(Multi-Document QA) 태스크에서 정보 위치에 따른 정확도 변화:

| 정보 위치 | 정확도 (10 docs) | 정확도 (20 docs) | 정확도 (30 docs) |
|----------|:---------------:|:---------------:|:---------------:|
| 처음 (1~2번째) | ~85% | ~80% | ~75% |
| 중간 (5~6번째) | ~60% | ~50% | ~40% |
| 끝 (마지막) | ~80% | ~75% | ~70% |

### 실전 대응 전략

1. **RAG 결과 배치 최적화**: 가장 관련성 높은 문서를 **처음 또는 끝**에 배치
2. **Context 압축**: 매우 긴 입력에서는 [[context-compression|Context Compression]]으로 핵심만 추출
3. **Chunk 분할 처리**: 긴 문서를 청크로 나누어 개별 처리 후 결과 통합
4. **반복 삽입**: 핵심 정보를 입력의 시작과 끝 모두에 배치

## 프레임워크별 Long Context 설정

### vLLM에서 Long Context 추론

```python
from vllm import LLM, SamplingParams

# Long Context 모델 로드 (128K 컨텍스트)
llm = LLM(
    model="meta-llama/Llama-3.1-70B-Instruct",
    tensor_parallel_size=4,          # 4 GPU TP
    max_model_len=131072,            # 128K 컨텍스트
    kv_cache_dtype="fp8",            # KV-Cache FP8 양자화
    enable_chunked_prefill=True,     # 청크 프리필 (메모리 효율)
    max_num_batched_tokens=32768,    # 프리필 청크 크기
)

# 긴 입력 처리
sampling_params = SamplingParams(temperature=0.7, max_tokens=4096)
outputs = llm.generate([long_prompt], sampling_params)
```

## 정리

| 기법 | 분류 | 목적 | 메모리 효과 | 품질 영향 | 구현 난이도 |
|------|------|------|:---------:|:---------:|:---------:|
| Position Interpolation | 위치 인코딩 | 컨텍스트 확장 | 없음 | 보통 | 쉬움 |
| YaRN | 위치 인코딩 | 컨텍스트 확장 | 없음 | 좋음 | 보통 |
| NTK-aware | 위치 인코딩 | 컨텍스트 확장 | 없음 | 보통 | 쉬움 |
| Sliding Window | 어텐션 효율화 | 복잡도 감소 | 크게 절감 | 원거리 제한 | 쉬움 |
| Ring Attention | 분산 처리 | 다중 디바이스 확장 | 분산 저장 | 없음 | 어려움 |
| GQA | KV-Cache 절감 | 메모리 절약 | 75~97% 절감 | 미미 | 모델 설계 시 |
| KV-Cache 양자화 | KV-Cache 절감 | 메모리 절약 | 50~75% 절감 | 미미~약간 | 쉬움 |
| KV-Cache 압축 | KV-Cache 절감 | 메모리 절약 | 가변 | 작업 의존 | 보통 |

Long Context는 단순히 "더 긴 입력을 받는 것"이 아니라, **위치 인코딩, 어텐션 효율화, 메모리 최적화, 분산 처리**의 네 가지 축에서의 종합 최적화 문제다. 실전에서는 하드웨어 환경과 사용 목적에 따라 여러 기법을 조합하여 적용하는 것이 핵심이다.
