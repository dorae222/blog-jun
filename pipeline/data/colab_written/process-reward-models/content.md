# Process Reward Models: 단계별 검증으로 추론 향상하기

## 들어가며

:::info
이 글은 [[reasoning-vs-inference|Reasoning vs Inference]] 시리즈의 **SW Reasoning** 축에 해당하며, [[test-time-compute-scaling|Test-Time Compute Scaling]] 글과 함께 읽으면 좋다.
:::

LLM이 수학 문제를 풀 때, 최종 답만 맞으면 되는가, 아니면 **풀이 과정도 올바른지** 확인해야 하는가?

이 질문에 대한 답이 **Process Reward Model(PRM)**과 **Outcome Reward Model(ORM)**의 차이를 결정한다. OpenAI의 "Let's Verify Step by Step"(Lightman et al., 2023)은 이 문제에 대한 체계적 실험을 통해, **과정을 검증하는 것이 결과만 검증하는 것보다 우월**함을 증명했다.

---

## ORM vs PRM

### Outcome Reward Model (ORM)

ORM은 **최종 답변만** 평가한다.

```
풀이: "x + 3 = 7이므로 x = 4"
ORM 평가: 정답(4) ✓ → 보상 +1
```

장점은 학습이 간단하다는 것이다. 정답 여부만 알면 되므로, 자동으로 대량의 학습 데이터를 생성할 수 있다. 그러나 치명적인 문제가 있다: **잘못된 추론으로 우연히 정답에 도달한 경우도 높은 보상을 받는다.**

```
풀이: "x + 3 = 7. 양변에서 3을 빼면 x = 5.
       아, 잠깐, 다시 계산하면 x = 4."   ← 중간 과정이 틀림
ORM 평가: 정답(4) ✓ → 보상 +1           ← 그래도 보상
```

이런 풀이가 높은 보상을 받으면, 모델은 **올바른 추론 패턴이 아니라 정답을 우연히 맞추는 패턴**을 학습하게 된다.

### Process Reward Model (PRM)

PRM은 **추론의 각 단계를 독립적으로 평가**한다.

```
풀이 단계 1: "x + 3 = 7"           → PRM: ✓ 올바른 설정
풀이 단계 2: "양변에서 3을 빼면"     → PRM: ✓ 올바른 연산
풀이 단계 3: "x = 4"               → PRM: ✓ 올바른 결론
```

각 단계가 이전 단계로부터 논리적으로 올바르게 도출되었는지를 검증한다. 잘못된 단계가 있으면 **그 이후의 모든 경로를 차단**할 수 있다.

## Let's Verify Step by Step: 핵심 발견

### 실험 설계

Lightman et al.(2023)은 MATH 데이터셋에서 ORM과 PRM의 효과를 체계적으로 비교했다.

핵심 실험: **Best-of-N 선택에서 어떤 검증기가 더 좋은 답변을 골라내는가?**

- 동일한 생성 모델(GPT-4 계열)로 N개의 풀이를 생성
- ORM으로 최고 풀이를 선택 vs PRM으로 최고 풀이를 선택
- N = 1, 10, 100, 1000까지 변화시키며 정답률 비교

### 결과

PRM이 **모든 N에서 ORM을 능가**했다. 특히 N이 커질수록(test-time compute가 증가할수록) 격차가 벌어졌다:

- N=100일 때, PRM은 MATH에서 **78.2%** 정답률 달성
- 같은 조건에서 ORM은 약 72% — **6%p 격차**
- Majority Voting(다수결)은 약 69% — PRM이 **9%p 이상 우위**

이 결과가 중요한 이유: [[test-time-compute-scaling|test-time compute scaling]]에서 **검증기의 품질이 scaling의 효율을 결정**한다는 것을 보여주기 때문이다. 같은 연산 예산을 투입해도, 좋은 검증기가 있으면 더 큰 성능 향상을 얻을 수 있다.

### PRM800K 데이터셋

이 논문의 또 다른 핵심 기여는 **PRM800K** 데이터셋이다:

- MATH 문제에 대한 **75,000개 풀이**의 **800,000개 단계별 레이블**
- 각 단계에 대해 인간 검증자가 positive / negative / neutral 레이블을 부여
- 이전까지 이 규모의 프로세스 감독 데이터는 존재하지 않았음

PRM800K는 후속 연구(Math-Shepherd, [[deepseek-r1|DeepSeek-R1]]의 보상 설계 등)의 기반이 되었다.

## PRM의 작동 메커니즘

### 단계 분할 (Step Segmentation)

PRM을 학습시키려면 먼저 **추론을 단계로 분할**해야 한다. 일반적인 방법:

1. **줄바꿈 기반**: 각 줄을 하나의 단계로 취급 (가장 단순)
2. **문장 기반**: 완결된 문장 단위로 분할
3. **논리적 분할**: 수학적 변환이나 추론의 전환점을 기준으로 분할

실제로 대부분의 연구는 줄바꿈 기반을 사용한다. 추론 모델(o1, R1)의 `<think>` 블록은 자연스러운 단계 분할을 제공하므로 PRM 적용이 용이하다.

### 단계별 점수 계산

PRM은 각 단계 $s_i$에 대해 점수 $r(s_i | s_1, ..., s_{i-1}, q)$를 할당한다. 여기서 $q$는 원래 질문이다.

전체 풀이의 점수는 보통 다음 중 하나로 집계된다:

- **최솟값**: $R = \min_i r(s_i)$ — 가장 약한 고리가 전체 품질을 결정
- **곱**: $R = \prod_i r(s_i)$ — 모든 단계가 올바를 확률
- **마지막 단계**: $R = r(s_n)$ — 최종 단계의 누적 평가

"Let's Verify Step by Step"에서는 **최솟값** 방식이 가장 효과적이었다. 이는 직관적으로도 타당하다: 풀이의 품질은 **가장 취약한 추론 단계**에 의해 결정되기 때문이다.

## PRM + Test-Time Compute

PRM은 [[test-time-compute-scaling|test-time compute scaling]]의 핵심 구성 요소다.

### Best-of-N + PRM

가장 직접적인 활용: N개의 풀이를 생성하고, PRM으로 가장 높은 점수의 풀이를 선택한다.

```
질문: "삼각형의 넓이가 24이고 밑변이 8일 때, 높이는?"

풀이 1: "넓이 = 밑변 × 높이 / 2, 24 = 8h/2, h = 6"     → PRM: 0.95
풀이 2: "넓이 = 밑변 × 높이, 24 = 8h, h = 3"            → PRM: 0.12
풀이 3: "24/8 = 3, 3 × 2 = 6"                          → PRM: 0.78

→ PRM 선택: 풀이 1 (0.95)
```

풀이 3은 정답이지만 중간 과정이 불명확하여 PRM 점수가 낮다. PRM은 **올바른 결과뿐 아니라 올바른 과정**을 가진 풀이를 선호한다.

### Beam Search + PRM

더 정교한 활용: 추론 과정을 트리로 구성하고, PRM으로 각 분기의 품질을 평가하며 탐색한다.

1. 1단계에서 K개의 후보 생성 → PRM으로 상위 B개 선택
2. 선택된 B개에서 각각 K개의 2단계 생성 → 다시 상위 B개 선택
3. 반복하여 최종 풀이에 도달

이 방식은 **단순 Best-of-N보다 같은 연산으로 더 높은 정답률**을 달성한다. Snell et al.(2024)의 연구에서 beam search + PRM이 test-time compute의 가장 효율적인 활용법임을 보여줬다.

## 프로세스 감독의 어려움

### 레이블링 비용

PRM의 가장 큰 장벽은 **학습 데이터 구축 비용**이다. ORM은 정답/오답만 판별하면 되지만(자동화 가능), PRM은 **각 단계의 올바름을 인간이 판단**해야 한다.

PRM800K의 경우, 75,000개 풀이의 800,000개 단계를 인간이 검토했다. 이는 막대한 비용과 시간이 소요된다.

### 자동 프로세스 감독

이 비용 문제를 해결하기 위한 연구 방향:

- **Monte Carlo 추정**: 각 단계에서 나머지를 여러 번 완성시키고, 정답 도달 비율로 단계의 품질을 추정 (Math-Shepherd, Wang et al., 2024)
- **Self-taught 방식**: 모델 자체가 각 단계를 평가하도록 학습 (ReST-MCTS)
- **합성 데이터**: 의도적으로 특정 단계에 오류를 주입하여 PRM 학습 데이터 생성

[[deepseek-r1|DeepSeek-R1]]은 흥미롭게도 PRM을 **사용하지 않았다**. 대신 최종 정답 여부만으로 GRPO를 학습시켜, 모델 내부에서 자연스럽게 프로세스 검증 능력이 **창발**하도록 했다. 이는 외부 PRM 없이도 일부 프로세스 감독의 효과를 얻을 수 있음을 시사한다.

## 수학을 넘어: PRM의 확장

### 코드 생성

코드는 수학과 유사하게 **실행 결과로 자동 검증**이 가능하다. 각 코딩 단계(함수 설계, 구현, 테스트)에 PRM을 적용하여 코드 품질을 개선할 수 있다.

### 개방형 문제의 한계

에세이 작성, 전략 수립, 창작 등 **정답이 명확하지 않은 문제**에서는 PRM 적용이 어렵다. "이 문단이 논리적으로 올바른가?"를 판단하는 것은 "이 수학 단계가 맞는가?"보다 훨씬 주관적이다.

이 한계는 test-time compute scaling 전체의 한계이기도 하다 — 검증 가능한 문제에서 가장 효과적이고, 검증이 어려운 문제에서는 효과가 제한적이다.

## 정리

| 비교 항목 | ORM | PRM |
|----------|-----|-----|
| 평가 대상 | 최종 답변만 | 각 추론 단계 |
| 학습 데이터 | 자동 생성 가능 | 인간 레이블 필요 (비싸지만 자동화 연구 진행 중) |
| 오류 검출 | 최종 결과가 맞으면 중간 오류 무시 | 중간 단계 오류 포착 가능 |
| Best-of-N 성능 | 기본 | **6%p+ 향상** (MATH 기준) |
| 활용 | 단순 선택 | Tree Search, Beam Search에 핵심 |

PRM은 **"정답을 맞추는 것"에서 "올바르게 추론하는 것"**으로의 전환을 대표한다. 이 전환이 중요한 이유는, 올바른 추론 과정을 가진 모델이 **새로운 문제에서도 일관되게 높은 성능**을 보이기 때문이다. 우연히 정답을 맞추는 모델은 문제가 약간만 변형되면 틀리지만, 올바르게 추론하는 모델은 변형에도 강건하다.
