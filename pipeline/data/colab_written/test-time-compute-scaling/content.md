# Test-Time Compute Scaling: 추론 시간에 더 생각하기

## 들어가며

:::info
이 글은 [[reasoning-vs-inference|Reasoning vs Inference]] 시리즈의 **SW Reasoning** 축에 해당하며, [[process-reward-models|Process Reward Models]] 글과 함께 읽으면 좋다.
:::

LLM의 성능을 높이는 전통적 방법은 **모델을 더 크게 만드는 것**이었다. GPT-3(175B) → GPT-4(~1.8T) → … 이 scaling law는 학습 시간(training-time)에 더 많은 연산을 투입하는 것이다.

그러나 2024년, 근본적으로 다른 질문이 떠올랐다: **"학습 대신 추론 시간에 더 많은 연산을 투입하면 어떨까?"** Snell et al.(2024)의 "Scaling LLM Test-Time Compute Optimally Can be More Effective than Scaling Model Parameters"가 이 패러다임의 이론적 기반을 제시했고, OpenAI o1과 DeepSeek-R1이 이를 실제로 구현했다.

핵심 통찰: **같은 총 연산 예산이라면, 더 큰 모델을 한 번 실행하는 것보다 작은 모델을 여러 번 실행하고 최선을 선택하는 것이 더 효율적일 수 있다.**

---

## 두 가지 Scaling Law

### Training-Time Compute Scaling

Kaplan et al.(2020)과 Hoffmann et al.(2022, Chinchilla)이 확립한 법칙:

- 모델 크기, 데이터 양, 학습 연산량이 증가하면 성능이 **예측 가능하게 향상**
- 최적의 모델 크기와 데이터 양은 연산 예산에 의해 결정
- 이 법칙은 GPT-4, LLaMA 등 대규모 모델 개발의 이론적 근거

한계: 모델 크기를 키우는 것은 **학습 비용뿐 아니라 추론 비용도 증가**시킨다. 10배 큰 모델을 배포하면 매 요청마다 10배의 연산이 필요하다.

### Test-Time Compute Scaling

추론 시간에 투입하는 연산량을 늘려 성능을 향상시키는 새로운 패러다임:

- 같은 모델로 **여러 번 생성**하고 최선을 선택 (Best-of-N)
- 각 추론 단계를 **검증**하며 탐색 (Beam Search + PRM)
- 문제 난이도에 따라 연산량을 **적응적으로 조절**

핵심 장점: **추론 연산은 필요할 때만 사용**할 수 있다. 쉬운 질문에는 적은 연산을, 어려운 질문에는 많은 연산을 할당하여 평균 비용을 낮출 수 있다.

## Test-Time Compute 전략

### 1. Best-of-N (Majority Voting)

가장 단순한 전략: 같은 질문에 대해 N개의 답변을 생성하고, **가장 많이 등장하는 답변**을 선택한다.

```
질문: "1부터 100까지의 합은?"

답변 1: 5050 ✓
답변 2: 5050 ✓
답변 3: 4950 ✗
답변 4: 5050 ✓
답변 5: 5000 ✗

→ 다수결: 5050 (3/5)
```

Self-Consistency(Wang et al., 2023)가 이 방법의 대표적 구현이다.

**장점**: 구현이 극히 간단, 추가 모델 불필요
**한계**: N이 커질수록 비용이 선형 증가하지만 성능 향상은 로그 스케일로 감소 (수확체감)

### 2. Reward Model 기반 선택

N개의 답변 중 다수결이 아니라, **보상 모델(Reward Model)**이 가장 좋다고 판단하는 답변을 선택한다.

보상 모델의 두 가지 유형:
- **Outcome Reward Model (ORM)**: 최종 답변의 품질만 평가
- **Process Reward Model (PRM)**: 각 추론 **단계의** 품질을 평가 → 더 정밀한 선택 가능

PRM은 [[process-reward-models|별도 글]]에서 상세히 다룬다.

### 3. Tree Search (탐색 기반)

단순히 완성된 답변을 비교하는 대신, **추론 과정 자체를 탐색 트리로 구성**하고 최적 경로를 찾는 전략이다.

작동 방식:
1. 추론의 각 단계에서 **여러 후보 경로를 분기**
2. [[process-reward-models|PRM]]으로 각 경로의 품질을 평가
3. 유망한 경로만 확장하고, 비유망한 경로는 가지치기
4. 최종적으로 가장 높은 누적 점수의 경로를 선택

이는 알파고(AlphaGo)의 MCTS(Monte Carlo Tree Search)와 구조적으로 유사하다. AlphaGo가 바둑에서 수를 "탐색"했다면, test-time compute는 LLM에서 추론 경로를 "탐색"하는 것이다.

### 4. Sequential Revision (순차적 수정)

하나의 답변을 생성한 후, **모델이 스스로 검토하고 수정**하는 과정을 반복한다.

```
[초기 답변] → [자기 검토: "이 부분이 틀렸다"] → [수정된 답변] → [재검토] → [최종 답변]
```

Reflexion(Shinn et al., 2023)이 대표적이다. 추론 모델의 `<think>` 태그 내에서 "Wait, let me reconsider..."와 같은 자기 수정 행동은 이 전략의 내재화된 형태로 볼 수 있다.

## 적응적 연산 할당 (Adaptive Compute)

Test-time compute의 가장 강력한 아이디어는 **문제 난이도에 따라 연산량을 조절**하는 것이다.

### 문제 난이도 분류

Snell et al.(2024)의 핵심 발견:

- **쉬운 문제**: test-time compute를 늘려도 이미 정답률이 높아 이득이 적음
- **중간 난이도 문제**: test-time compute 증가에 따라 **가장 큰 성능 향상**
- **극히 어려운 문제**: 모델의 능력 범위를 벗어나 test-time compute를 아무리 늘려도 해결 불가

최적 전략: **중간 난이도 문제에 연산을 집중**하고, 쉬운 문제는 빠르게 처리, 극히 어려운 문제는 조기 포기.

### Compute-Optimal Scaling

같은 총 연산 예산 $C$가 있을 때, 두 가지 선택지:

1. **큰 모델 1회 실행**: 14B 모델로 한 번에 답변
2. **작은 모델 N회 실행**: 1.5B 모델로 여러 번 생성 + PRM으로 선택

Snell et al.의 실험 결과, 적절한 test-time compute 전략을 사용하면 **1.5B 모델 + 다회 추론이 14B 모델 1회 추론을 능가**하는 영역이 존재한다.

이는 실무적으로 중요한 함의를 가진다:
- 작은 모델은 배포 비용이 낮음
- 적응적 연산으로 평균 비용을 관리 가능
- 특히 **추론 품질이 중요한 소수의 어려운 질문**에서 cost-effective

## 추론 모델과의 연결

### o1과 R1: Test-Time Compute의 제품화

OpenAI o1과 [[deepseek-r1|DeepSeek-R1]]은 test-time compute scaling을 **모델 내부에 내재화**한 것이다.

외부적 test-time compute (Best-of-N, Tree Search):
- 모델 **외부에서** 여러 번 실행하고 선택
- 추가 인프라(PRM, 탐색 알고리즘) 필요
- 사용자가 연산량을 조절 가능

내재화된 test-time compute (o1, R1):
- 모델 **내부에서** 긴 추론 체인을 생성하며 스스로 탐색/검증
- RL 학습을 통해 탐색 전략을 모델 가중치에 내재화
- 사용자에게 투명 — 긴 `<think>` 출력으로만 관찰 가능

### 두 접근법의 결합

흥미롭게도, 두 접근법은 **상호 배타적이 아니다**:
- R1을 여러 번 실행하고 Best-of-N 선택 → 추가 성능 향상 가능
- R1의 추론 단계에 PRM을 적용 → 더 정밀한 탐색 가능

이 조합은 아직 체계적으로 탐구되지 않은 영역이며, 향후 연구의 유망한 방향이다.

## 한계와 열린 질문

### 1. 비용 효율의 경계

Test-time compute를 무한히 늘릴 수는 없다. 수확체감이 존재하며, 특정 시점 이후로는 더 큰 모델을 사용하는 것이 효율적이다. 이 **교차점**을 정확히 예측하는 것은 아직 어려운 문제다.

### 2. 검증기의 한계

PRM/ORM의 품질이 test-time compute의 효과를 결정한다. 검증기가 부정확하면 잘못된 답변을 선택하게 되며, 이는 test-time compute의 이점을 상쇄한다.

### 3. 개방형 문제에서의 적용

수학/코드는 정답이 명확하여 검증이 용이하다. 그러나 에세이 작성, 창작, 전략 수립 같은 **개방형 문제**에서는 "더 좋은 답변"을 판단하는 것 자체가 어렵다.

## 정리

| 전략 | 핵심 메커니즘 | 비용 | 효과 |
|------|------------|------|------|
| Best-of-N | 다수결 / 보상 기반 선택 | N배 | 로그 스케일 향상 |
| Tree Search | 추론 단계별 탐색 + 가지치기 | 가변 | 높음 (PRM 품질 의존) |
| Sequential Revision | 자기 검토 + 수정 반복 | 반복 횟수 비례 | 중간 |
| 내재화 (o1/R1) | 긴 CoT 내부 탐색 | 토큰 수 비례 | 높음 |

Test-time compute scaling은 **"더 크게"에서 "더 오래 생각하게"**로의 패러다임 전환을 대표한다. 모델 크기를 키우는 것만이 성능 향상의 유일한 경로가 아니라, **같은 모델로 더 깊이 생각하는 것**이 또 다른 강력한 경로임을 보여준다.
