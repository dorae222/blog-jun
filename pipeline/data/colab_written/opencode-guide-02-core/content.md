## Bubble Tea TUI 프레임워크 심층

### Bubble Tea란

Bubble Tea는 Charm 팀이 만든 Go 언어용 TUI 프레임워크다. Elm 아키텍처(The Elm Architecture)에 기반하여, Model-Update-View 패턴으로 터미널 애플리케이션을 구축한다. React의 상태 관리와 유사한 개념이지만, 브라우저가 아닌 터미널에서 동작한다.

```
사용자 입력 → Message → Update(model, msg) → 새로운 Model → View(model) → 화면 렌더링
```

이 아키텍처가 OpenCode에 주는 이점은 다음과 같다.

| 특성 | 설명 |
|------|------|
| 반응형 UI | 상태 변경 시 화면이 즉시 업데이트된다 |
| 키보드 중심 | 마우스 없이 모든 조작이 가능하다 |
| 비동기 처리 | AI 응답을 기다리는 동안 UI가 멈추지 않는다 |
| 테마 지원 | 30개 이상의 내장 테마와 커스텀 테마를 지원한다 |
| 크로스 플랫폼 | macOS, Linux, Windows 터미널에서 일관된 경험을 제공한다 |

### Charm 생태계

OpenCode는 Bubble Tea 외에도 Charm 팀의 다른 라이브러리를 활용한다.

| 라이브러리 | 역할 |
|-----------|------|
| **Bubble Tea** | TUI 프레임워크 (핵심) |
| **Lip Gloss** | 터미널 스타일링, 색상, 레이아웃 |
| **Bubbles** | 재사용 가능한 TUI 컴포넌트 (텍스트 입력, 리스트 등) |
| **Glamour** | 마크다운 렌더링 |

이 조합 덕분에 OpenCode의 TUI는 단순한 텍스트 출력이 아니라, 구문 강조, 마크다운 렌더링, 테이블 표시 등 풍부한 시각적 경험을 제공한다.

### TUI 화면 구성 상세

OpenCode TUI의 주요 화면 요소를 세부적으로 살펴보자.

```
+---------------------------------------------------+
|  [모델명]  [세션명]  [토큰: 2.4K/128K]  [에이전트]  |  <- 상태 바
+---------------------------------------------------+
|                                                    |
|  User: 이 함수를 리팩토링해줘 @src/handler.go      |
|                                                    |
|  Assistant:                                        |
|  파일을 분석하겠습니다.                              |
|                                                    |
|  [Tool: read] src/handler.go                       |
|  [Tool: edit] src/handler.go (line 24-56)          |
|                                                    |
|  리팩토링이 완료되었습니다. 주요 변경사항:            |
|  - 에러 처리 로직을 별도 함수로 분리                 |
|  - ...                                             |
|                                                    |
+---------------------------------------------------+
|  > _                                               |  <- 프롬프트 입력
+---------------------------------------------------+
```

상태 바에서는 현재 사용 중인 모델, 세션 이름, 토큰 사용량을 실시간으로 확인할 수 있다. 토큰 사용량이 컨텍스트 윈도우 한계에 근접하면 자동 압축(auto-compact)이 트리거된다.

## 75+ 모델 지원 상세

OpenCode는 AI SDK와 Models.dev를 기반으로 75개 이상의 LLM 프로바이더를 지원한다. 인기 있는 프로바이더는 기본으로 미리 로드되어 있다.

### OpenAI 모델

| 모델 | 특징 | 권장 용도 |
|------|------|-----------|
| `gpt-4.1` | 최신 플래그십 모델, 뛰어난 코딩 능력 | 복잡한 코드 생성, 리팩토링 |
| `gpt-4.1-mini` | 빠르고 비용 효율적 | 일상적인 코딩 작업 |
| `gpt-4.1-nano` | 초경량, 최저 비용 | 간단한 질문, 코드 설명 |
| `o4-mini` | 추론 특화 모델 | 복잡한 알고리즘 설계, 디버깅 |

```json
{
  "provider": {
    "openai": {
      "apiKey": "{env:OPENAI_API_KEY}"
    }
  },
  "model": "openai/gpt-4.1",
  "small_model": "openai/gpt-4.1-mini"
}
```

### Ollama - 로컬 모델

Ollama는 로컬에서 LLM을 실행할 수 있게 해주는 도구다. API 비용 없이 완전히 무료로 AI 코딩을 사용할 수 있다.

```bash
# 코딩에 적합한 로컬 모델 다운로드
ollama pull qwen2.5-coder:32b
ollama pull codellama:34b
ollama pull deepseek-coder-v2:16b
```

OpenCode에서 Ollama 모델 사용 설정은 다음과 같다.

```json
{
  "provider": {
    "ollama": {}
  },
  "model": "ollama/qwen2.5-coder:32b"
}
```

Ollama를 사용할 때의 고려사항은 다음과 같다.

| 항목 | 클라우드 API | Ollama (로컬) |
|------|-------------|---------------|
| 비용 | 토큰당 과금 | 무료 (전기 요금만) |
| 응답 속도 | 빠름 | GPU에 따라 다름 |
| 모델 품질 | 최신, 최고 성능 | 상대적으로 낮음 |
| 프라이버시 | 데이터가 외부로 전송 | 완전히 로컬 |
| 컨텍스트 윈도우 | 대체로 큼 (128K+) | 모델에 따라 다름 |

### 세션 중 모델 전환

OpenCode의 강력한 기능 중 하나는 **세션 도중에 모델을 전환**할 수 있다는 점이다. 대화 컨텍스트를 유지하면서 다른 모델로 바꿀 수 있다.

```
# TUI에서 모델 전환
/model

# 또는 커맨드 팔레트에서
```

예를 들어, 빠른 질문은 `gpt-4.1-mini`로 처리하고, 복잡한 리팩토링은 `claude-opus-4`로 전환하는 식으로 유연하게 활용할 수 있다.

## 도구 시스템

OpenCode의 AI 에이전트는 단순히 텍스트를 생성하는 것이 아니라, 다양한 **도구(Tools)**를 호출하여 실제 작업을 수행한다. 이것이 OpenCode를 단순 채팅봇이 아닌 코딩 에이전트로 만드는 핵심이다.

### 내장 도구 목록

| 도구 | 기능 | 설명 |
|------|------|------|
| **read** | 파일 읽기 | 텍스트 파일 읽기, 이미지/PDF 감지, 50KB 제한 |
| **write** | 파일 쓰기 | 파일 생성/덮어쓰기, diff 생성, LSP 진단 수집 |
| **edit** | 파일 편집 | 기존 파일의 특정 부분 수정 |
| **bash** | 명령 실행 | 셸 명령 실행, tree-sitter로 명령 파싱 |
| **glob** | 파일 검색 | 패턴으로 파일 검색 |
| **grep** | 내용 검색 | 파일 내용에서 패턴 검색 |
| **diagnostics** | LSP 진단 | 코드 오류, 경고, 힌트 조회 |
| **hover** | 타입 정보 | 특정 위치의 타입/문서 정보 조회 |

### 도구 실행 흐름

도구가 실행되는 과정을 단계별로 살펴보자.

```
1. 사용자: "src/main.go의 handleRequest 함수에 에러 처리를 추가해줘"
2. AI 모델: read 도구 호출 → src/main.go 파일 내용 확인
3. AI 모델: diagnostics 도구 호출 → 현재 코드의 문제점 확인
4. AI 모델: edit 도구 호출 → handleRequest 함수 수정
5. AI 모델: diagnostics 도구 호출 → 수정 후 새로운 에러 없는지 확인
6. AI 모델: 결과를 사용자에게 보고
```

### write 도구의 동작

파일을 쓸 때 OpenCode는 단순히 파일을 저장하는 것이 아니라 다음 과정을 거친다.

1. 변경 사항의 diff를 생성하여 사용자에게 보여준다
2. 사용자 승인 후 파일을 작성한다
3. LSP 서버에서 해당 파일과 관련 파일(최대 5개)의 진단 정보를 수집한다
4. 새로운 에러가 발생했다면 AI에게 알려 추가 수정을 유도한다

이 피드백 루프 덕분에 AI가 작성한 코드의 품질이 높아진다.

### bash 도구의 안전장치

bash 도구는 tree-sitter를 사용하여 명령어를 파싱하고, 파일 경로를 `realpath`로 해석한다. 위험한 명령(예: `rm -rf /`)에 대해서는 사용자 확인을 요구한다.

```json
{
  "tools": {
    "bash": {
      "permission": "ask"
    }
  }
}
```

도구 권한 설정 옵션은 다음과 같다.

| 설정 | 동작 |
|------|------|
| `"allow"` | 항상 허용 (확인 없음) |
| `"ask"` | 실행 전 사용자 확인 |
| `"deny"` | 항상 차단 |

## 세션 관리

OpenCode는 SQLite 데이터베이스를 사용하여 세션을 영구 저장한다. 터미널을 닫아도 이전 대화를 이어갈 수 있다.

### 세션 저장 구조

```
~/.local/share/opencode/
  ├── sessions.db       # SQLite 데이터베이스
  ├── auth.json         # 인증 정보
  └── mcp-auth.json     # MCP 인증 토큰
```

세션 데이터는 Drizzle ORM을 통해 SQLite에 저장되며, 글로벌 이벤트 버스로 실시간 UI 업데이트를 발생시킨다.

### 세션 관리 명령

```
/session            # 세션 목록 보기
/session new        # 새 세션 시작
Ctrl+X → n          # 새 세션 (단축키)
Ctrl+X → s          # 세션 목록 (단축키)
```

### 프로젝트별 세션

세션은 프로젝트 디렉토리 기준으로 관리된다. 같은 프로젝트에서 여러 세션을 유지하면서, 서로 다른 작업 흐름을 병렬로 진행할 수 있다.

```
~/project-a/
  세션 1: 기능 A 개발
  세션 2: 버그 수정
  세션 3: 리팩토링

~/project-b/
  세션 1: 초기 설정
  세션 2: API 개발
```

## 컨텍스트 관리

AI 모델의 컨텍스트 윈도우는 제한되어 있다. OpenCode는 이를 효율적으로 관리하는 시스템을 갖추고 있다.

### 자동 압축 (Auto-Compact)

대화가 길어져서 모델의 컨텍스트 윈도우 한계에 근접하면, OpenCode가 자동으로 대화를 요약한다.

```
컨텍스트 사용량 모니터링
    ↓
한계 근접 감지 (버퍼: 20,000 토큰)
    ↓
미디어 첨부 제거 (이미지, PDF)
    ↓
대화 요약 생성
    ↓
오래된 도구 출력 정리
    ↓
요약된 컨텍스트로 계속
```

자동 압축 설정은 `opencode.json`에서 조정할 수 있다.

```json
{
  "compaction": {
    "reserved": 20000
  }
}
```

`reserved` 값은 압축이 트리거되기 전에 남겨둘 안전 버퍼(토큰 수)다. 값을 늘리면 더 일찍 압축이 시작되고, 줄이면 더 많은 컨텍스트를 유지한다.

### 수동 압축

자동 압축을 기다리지 않고 직접 컨텍스트를 정리할 수도 있다.

```
/compact
```

이 명령은 현재 대화를 요약하고 컨텍스트 공간을 확보한다. 대화가 길어지기 전에 주기적으로 사용하면 효율적이다.

### 파일 참조 (@)

`@` 기호로 파일을 참조하면, 해당 파일의 내용이 컨텍스트에 추가된다. 퍼지 검색을 지원하므로 정확한 경로를 몰라도 빠르게 찾을 수 있다.

```
@main.go 이 파일의 에러 처리를 개선해줘
@src/utils/ 이 디렉토리의 유틸리티 함수들을 정리해줘
```

:::warning
많은 파일을 한꺼번에 참조하면 컨텍스트 윈도우를 빠르게 소진한다. 필요한 파일만 선택적으로 참조하는 것이 좋다.
:::

## 코드 편집 워크플로우

OpenCode로 실제 코드를 편집하는 워크플로우를 상세히 알아보자.

### 새 파일 생성

```
REST API 핸들러를 만들어줘. 사용자 CRUD 엔드포인트를 포함해줘.
```

AI는 `write` 도구를 사용하여 새 파일을 생성하고, diff를 보여준다.

### 기존 코드 수정

```
@src/handler.go 의 CreateUser 함수에 입력 유효성 검사를 추가해줘
```

AI는 `read` 도구로 파일을 확인한 후, `edit` 도구로 특정 부분만 수정한다.

### 멀티 파일 리팩토링

```
이 프로젝트의 에러 처리를 표준화해줘.
모든 핸들러에서 동일한 에러 응답 형식을 사용하도록 수정해줘.
```

AI는 여러 파일을 순회하면서 일관된 수정을 적용한다.

### 디버깅 워크플로우

```
!go test ./... 테스트 실패 원인을 분석하고 수정해줘
```

셸 명령의 출력(테스트 결과)을 AI에게 전달하고, 분석과 수정을 한 번에 요청할 수 있다.

## 키보드 단축키 상세

### 리더 키 시스템

OpenCode의 리더 키(기본값: `Ctrl+X`)는 Vim의 리더 키 개념과 유사하다. 터미널의 기존 단축키와 충돌을 피하면서 많은 기능에 접근할 수 있게 해준다.

### 전체 단축키 맵

#### 일반 조작

| 단축키 | 동작 |
|--------|------|
| `Ctrl+K` | 커맨드 팔레트 |
| `Ctrl+C` | 현재 작업 중단 |
| `Ctrl+D` | OpenCode 종료 |
| `Enter` | 메시지 전송 |
| `Shift+Enter` | 줄바꿈 (멀티라인 입력) |

#### 리더 키 조합 (Ctrl+X + 키)

| 조합 | 동작 |
|------|------|
| `Ctrl+X` → `h` | 도움말 |
| `Ctrl+X` → `n` | 새 세션 |
| `Ctrl+X` → `s` | 세션 목록 |
| `Ctrl+X` → `m` | 모델 변경 |
| `Ctrl+X` → `a` | 에이전트 변경 |
| `Ctrl+X` → `t` | 테마 변경 |
| `Ctrl+X` → `f` | 파일 브라우저 |

#### 프롬프트 특수 입력

| 접두사 | 기능 | 예시 |
|--------|------|------|
| `/` | 슬래시 명령 | `/help`, `/model`, `/compact` |
| `@` | 파일 참조 | `@src/main.go` |
| `!` | 셸 명령 주입 | `!git status` |

### 커스텀 키바인딩

`opencode.json`에서 키바인딩을 커스터마이징할 수 있다.

```json
{
  "keybinds": {
    "command_list": "ctrl+p",
    "new_session": "ctrl+n",
    "session_list": "ctrl+shift+s"
  }
}
```

:::tip
Vim 사용자라면 커뮤니티 플러그인을 통해 Vim 스타일 키바인딩을 적용할 수 있다. `h/j/k/l` 네비게이션, 모달 편집 등을 TUI에서 사용할 수 있다.
:::

## 에이전트 시스템 심층

### Build 에이전트

Build 에이전트는 OpenCode의 기본 에이전트로, 모든 도구에 접근할 수 있다. 코드 생성, 파일 수정, 셸 명령 실행, 테스트 등 전체 개발 워크플로우를 담당한다.

```
[Build 에이전트 워크플로우]
코드 분석 → 계획 수립 → 파일 수정 → LSP 진단 → 추가 수정 → 완료 보고
```

### Plan 에이전트

Plan 에이전트는 읽기 전용 모드로, 코드를 분석하고 계획을 세우지만 실제로 파일을 수정하지는 않는다. 비활성화되는 도구는 다음과 같다.

- `write` - 파일 작성 불가
- `edit` - 파일 수정 불가
- `bash` - 일부 명령 제한

단, `.opencode/plans/*.md` 파일은 예외적으로 작성할 수 있다. 이를 통해 Plan 에이전트가 분석 결과를 계획 문서로 남길 수 있다.

### 에이전트 전환 활용 예시

```
# 1. Plan 에이전트로 분석
/agent plan
이 프로젝트의 아키텍처를 분석하고 리팩토링 계획을 세워줘

# 2. Build 에이전트로 전환하여 실행
/agent build
위 계획대로 리팩토링을 진행해줘
```

이 워크플로우의 장점은 Plan 단계에서 충분히 분석하고, Build 단계에서 정확하게 실행할 수 있다는 것이다. 실수로 코드가 수정되는 것을 방지하면서 안전하게 작업할 수 있다.

## 슬래시 명령 완전 가이드

### 기본 명령

| 명령 | 설명 | 단축키 대체 |
|------|------|-------------|
| `/help` | 사용 가능한 모든 명령 표시 | `Ctrl+X` → `h` |
| `/model` | 모델 선택/변경 | `Ctrl+X` → `m` |
| `/theme` | 테마 변경 | `Ctrl+X` → `t` |
| `/compact` | 대화 컨텍스트 압축 | - |
| `/clear` | 대화 내용 초기화 | - |
| `/init` | AGENTS.md 생성 | - |
| `/session` | 세션 관리 | `Ctrl+X` → `s` |
| `/agent` | 에이전트 전환 | `Ctrl+X` → `a` |

### 커스텀 명령 생성

프로젝트별로 자주 사용하는 작업 흐름을 커스텀 명령으로 정의할 수 있다. `.opencode/commands/` 디렉토리에 마크다운 파일을 생성한다.

```markdown
---
description: "코드 리뷰를 수행합니다"
model: "anthropic/claude-sonnet-4-20250514"
subtask: true
---

다음 파일을 리뷰해줘. 코드 품질, 버그 가능성, 성능 이슈를 중점적으로 확인해줘.
리뷰 결과를 .opencode/plans/review.md에 작성해줘.
```

이 파일을 `.opencode/commands/review.md`로 저장하면, `/review` 명령으로 사용할 수 있다.

커스텀 명령의 설정 옵션은 다음과 같다.

| 옵션 | 설명 |
|------|------|
| `description` | 명령 설명 (커맨드 팔레트에 표시) |
| `model` | 이 명령에 사용할 모델 (기본 모델 대신) |
| `subtask` | `true`로 설정하면 서브에이전트로 실행 (메인 컨텍스트 오염 방지) |

## 정리

이 글에서 다룬 OpenCode의 핵심 기능을 정리한다.

- **Bubble Tea TUI**: Elm 아키텍처 기반의 반응형 터미널 인터페이스로, 30+ 테마와 키보드 중심 조작을 지원한다
- **75+ 모델 지원**: OpenAI, Anthropic, Google, Ollama, OpenRouter 등 거의 모든 LLM 프로바이더를 세션 도중에도 자유롭게 전환할 수 있다
- **도구 시스템**: read, write, edit, bash, grep, diagnostics 등 실질적인 코딩 도구를 AI가 자율적으로 호출한다
- **세션 관리**: SQLite 기반 영구 저장으로 터미널을 닫아도 대화를 이어갈 수 있다
- **컨텍스트 관리**: 자동 압축으로 긴 대화에서도 효율적으로 컨텍스트를 유지한다
- **에이전트 시스템**: Build(개발)과 Plan(분석) 에이전트를 전환하며 안전하게 작업한다
- **커스텀 명령**: 프로젝트별 반복 작업을 슬래시 명령으로 자동화한다

다음 글 [[opencode-guide-03-advanced|OpenCode 고급 활용]]에서는 LSP 통합과 커스텀 설정을 다룬다.
