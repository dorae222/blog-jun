# Small Language Models: 작지만 강한 모델들

## 들어가며

:::info
이 글은 1B~7B 규모의 Small Language Models(SLM) 전반을 다루는 튜토리얼이다. 모델별 상세 스펙은 [[phi]], [[llama-3]], [[gemini]] 등 개별 아키텍처 포스트를, 경량화 기법은 [[quantization-guide]], [[distillation-guide]], [[pruning-guide]]를 참고하라.
:::

2023년부터 AI 커뮤니티에서 흥미로운 흐름이 시작되었다. "더 크게"만이 정답이 아니라, **"얼마나 작으면서도 강할 수 있는가"**가 핵심 질문이 된 것이다.

Small Language Models(SLM)은 일반적으로 **1B~7B 파라미터** 규모의 모델을 지칭한다. GPT-4(~1.8T)나 LLaMA-3.1-405B에 비하면 수십~수백 배 작지만, 올바른 학습 전략을 적용하면 특정 과제에서 대형 모델에 준하는 성능을 보인다.

이 글에서는 SLM이 부상한 배경, 주요 모델 비교, 핵심 설계 원칙, 실전 코드 예제, 배포 가이드까지 체계적으로 정리한다.

---

## SLM 정의와 범위

SLM(Small Language Model)은 일반적으로 **1B~14B 파라미터** 규모의 언어 모델을 지칭한다. 다만, 학계와 산업계에서 합의된 정확한 경계는 없으며, 맥락에 따라 달라진다.

| 분류 | 파라미터 범위 | 예시 |
|------|------------|------|
| Tiny LM | 100M 미만 | DistilBERT, TinyBERT |
| Small LM (SLM) | 1B ~ 14B | Phi-3, Gemma-2, Qwen2.5 |
| Large LM (LLM) | 30B ~ 405B | LLaMA-3.1-70B, GPT-4 |
| Frontier LM | 400B+ | GPT-4, Claude 3.5 |

이 글에서는 **1B~14B 범위**를 SLM으로 정의하고, 이 구간의 모델들을 집중 분석한다.

---

## SLM이 부상한 이유

### 배포 비용 절감

대형 모델의 추론 비용은 크기에 비례한다. 70B 모델 서빙에 필요한 GPU 메모리와 연산은 7B 모델의 약 10배다. 대량의 요청을 처리하는 프로덕션 환경에서 이 차이는 **운영 비용의 10배 차이**로 직결된다.

### 엣지/온디바이스 배포

스마트폰, IoT 기기, 로컬 서버에서 LLM을 실행하려면 모델이 작아야 한다. [[quantization-guide|4-bit 양자화]]를 적용하면 3B 모델은 약 2GB, 7B 모델은 약 4GB로 줄어들어 일반 노트북이나 스마트폰에서도 실행 가능하다.

### 프라이버시와 규제

의료, 법률, 금융 등 데이터를 외부 API로 보낼 수 없는 분야에서, **로컬 실행 가능한 SLM**은 유일한 선택지다. GDPR 등 데이터 주권 규제가 강화되면서 이 수요는 더욱 커지고 있다.

### 파인튜닝 접근성

70B 모델의 풀 파인튜닝은 여러 장의 A100/H100이 필요하지만, 7B 모델은 **RTX 3090 한 장**으로도 LoRA 파인튜닝이 가능하다. 이는 개인 연구자와 스타트업의 AI 접근성을 크게 높인다.

## SLM 규모별 분류

SLM은 파라미터 수에 따라 세 구간으로 나눌 수 있다. 각 구간별 특성과 적합한 용도가 다르다.

| 구간 | 파라미터 범위 | 4-bit 양자화 메모리 | 주요 타깃 | 대표 모델 |
|------|------------|-------------------|----------|----------|
| Nano | 0.5B ~ 1.5B | 0.5 ~ 1 GB | 스마트폰, IoT, 임베디드 | Qwen2.5-0.5B, Phi-3.5-mini |
| Small | 1.5B ~ 4B | 1 ~ 2.5 GB | 노트북, 태블릿, 엣지 서버 | Phi-3-mini(3.8B), Gemma-2-2B, LLaMA-3.2-3B |
| Medium | 4B ~ 9B | 2.5 ~ 5 GB | 데스크톱 GPU, 클라우드 서버 | Qwen2.5-7B, Gemma-2-9B, LLaMA-3.1-8B |

## SLM 핵심 설계 원칙

### 원칙 1: 데이터 품질 > 데이터 양

Phi 시리즈의 핵심 교훈이다. 웹 크롤링 데이터 수조 토큰보다, **교과서 품질의 합성 데이터 수십억 토큰**이 더 효과적이다.

고품질 데이터의 세 축:

| 데이터 유형 | 설명 | 예시 |
|------------|------|------|
| 교과서 품질 | 명확한 설명, 단계적 추론, 연습 문제 | 프로그래밍 교재 형식의 텍스트 |
| 합성 데이터 | GPT-4 등 대형 모델이 생성한 교육용 텍스트 | 단계별 문제 풀이, 코드 설명 |
| 필터링된 웹 | 웹 데이터 중 교과서 수준만 선별 | 고품질 기술 블로그, 문서 |

### 원칙 2: 증류 (Knowledge Distillation)

대형 모델의 지식을 소형 모델로 전이하는 [[distillation-guide|증류]]는 SLM의 핵심 전략이다.

| 증류 방식 | 설명 | 적용 사례 |
|----------|------|----------|
| 로짓 증류 | 교사 모델의 출력 분포를 학습 | Gemma-2 시리즈 |
| 데이터 증류 | 교사 모델이 생성한 데이터로 학습 | Phi 시리즈 (합성 데이터) |
| 추론 증류 | 교사의 추론 과정(Chain-of-Thought)을 학습 | [[deepseek-r1|DeepSeek-R1]] Distill 시리즈 |

:::warning
증류의 핵심 제약은 **용량 격차(capacity gap)**이다. 교사와 학생의 크기 차이가 너무 크면 학생이 교사의 지식을 흡수하지 못한다. 일반적으로 교사:학생 비율이 10:1을 넘지 않는 것이 권장된다.
:::

### 원칙 3: 아키텍처 최적화

SLM은 같은 파라미터 수에서 더 높은 성능을 내기 위한 아키텍처 개선을 적극 적용한다.

| 기법 | 효과 | 적용 모델 |
|------|------|----------|
| GQA (Grouped Query Attention) | KV 캐시 메모리 절감, 추론 속도 향상 | LLaMA-3, Qwen2.5, Gemma-2 |
| RoPE 확장 | 긴 컨텍스트 지원 (128K+) | Phi-3 (128K), Qwen2.5 (128K) |
| SwiGLU Activation | FFN 효율 향상 | LLaMA 계열 전체 |
| RMSNorm | LayerNorm 대비 연산 절감 | 대부분의 최신 SLM |

### 원칙 4: 양자화 친화적 설계

SLM은 [[quantization-guide|양자화]]와 함께 사용되는 경우가 많으므로, 양자화 후에도 성능 저하가 최소화되도록 설계된다.

| 양자화 수준 | 메모리 절감 | 성능 저하 | 적합한 용도 |
|------------|-----------|----------|-----------|
| FP16 | 2x | 없음 | GPU 서빙 기본값 |
| INT8 | 4x | 매우 적음 (1% 미만) | 서버 배포 |
| INT4 (GPTQ/AWQ) | 8x | 적음 (2~3%) | 엣지/로컬 배포 |
| 2-bit | 16x | 상당함 (5~10%) | 극한 엣지 |

## 실전: SLM 로딩 및 실행

SLM을 실제로 로딩하고 실행하는 방법을 프레임워크별로 살펴본다. FP16 기본 로딩부터 4-bit 양자화, 로컬 실행까지 단계별로 정리한다.

## Transformers로 SLM 로딩

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

# Qwen2.5-3B 로딩 (FP16)
model_name = "Qwen/Qwen2.5-3B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.float16,
    device_map="auto",
)

# 추론 실행
messages = [
    {"role": "system", "content": "당신은 한국어 AI 비서입니다."},
    {"role": "user", "content": "SLM의 장점을 3가지로 요약해주세요."}
]
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt").to(model.device)

outputs = model.generate(**inputs, max_new_tokens=256, temperature=0.7)
response = tokenizer.decode(outputs[0][inputs.input_ids.shape[-1]:], skip_special_tokens=True)
print(response)
```

## 4-bit 양자화 로딩 (BitsAndBytes)

```python
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,
)

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct",
    quantization_config=bnb_config,
    device_map="auto",
)
# 7B 모델이 약 4GB VRAM만으로 실행 가능
```

## SLM 파인튜닝 전략

SLM의 가장 큰 장점 중 하나는 **낮은 비용으로 도메인 특화가 가능**하다는 점이다.

## 파인튜닝 방식별 비교

| 방식 | 학습 파라미터 | GPU 메모리 (7B) | 학습 시간 (10K 샘플) | 성능 |
|------|-------------|----------------|-------------------|------|
| Full Fine-tuning | 100% | ~56 GB | 4~8시간 | 최고 |
| LoRA (r=16) | ~0.5% | ~16 GB | 1~2시간 | 우수 |
| QLoRA (4-bit + LoRA) | ~0.5% | ~6 GB | 2~3시간 | 좋음 |
| Prompt Tuning | ~0.01% | ~14 GB | 30분 | 제한적 |

:::tip
**개인 GPU 사용자를 위한 권장**: RTX 3090(24GB)에서 QLoRA로 7B 모델을 파인튜닝하는 것이 가성비 최적이다. 데이터셋 1만~5만 샘플이면 도메인 특화에 충분하며, 3시간 이내에 학습이 완료된다.
:::

## SLM vs LLM: 성능 격차 분석

SLM이 LLM을 완전히 대체할 수는 없다. 용도에 따라 어떤 격차가 있는지 정확히 이해하는 것이 중요하다.

| 능력 | SLM (3B~7B) | LLM (70B~405B) | 격차 수준 |
|------|-------------|----------------|----------|
| 단순 분류/감정 분석 | 90~95% | 95~98% | 작음 |
| 요약 | 85~90% | 92~96% | 중간 |
| 코드 생성 (단순) | 80~88% | 90~95% | 중간 |
| 코드 생성 (복잡) | 50~65% | 80~90% | 큼 |
| 수학 추론 | 60~80% | 85~95% | 큼 |
| 다단계 논리 추론 | 40~60% | 75~90% | 매우 큼 |
| 세계 지식 QA | 55~70% | 80~90% | 큼 |
| 창의적 글쓰기 | 60~75% | 85~95% | 큼 |

:::warning
SLM의 **환각(hallucination) 빈도**는 대형 모델보다 높다. 세계 지식의 저장 용량이 제한적이기 때문이다. SLM을 프로덕션에 투입할 때는 반드시 RAG나 외부 검색을 병행하여 사실 정확성을 보완해야 한다.
:::

## SLM 추론 최적화

[[inference-optimization-mfu|추론 최적화]]는 SLM의 실전 활용에서 핵심이다. 동일 모델이라도 최적화 수준에 따라 처리량이 5~10배 차이 날 수 있다.

### 최적화 기법별 효과

| 기법 | 속도 향상 | 메모리 절감 | 구현 난이도 |
|------|----------|-----------|-----------|
| KV Cache | 2~3x | 추가 메모리 필요 | 자동 적용 |
| Flash Attention 2 | 1.5~2x | 20~40% 절감 | 라이브러리 교체 |
| Continuous Batching | 3~5x (처리량) | 동일 | vLLM/TGI 사용 |
| Speculative Decoding | 2~3x | 드래프트 모델 추가 | 중간 |
| [[quantization-guide|양자화]] (INT4) | 1.5~2x | 75% 절감 | GPTQ/AWQ 적용 |
| PagedAttention | 1x | 50~90% 절감 | vLLM 사용 |

## 정리

SLM의 핵심 가치는 **"작은 모델 + 좋은 데이터 + 올바른 학습 전략"**의 조합이다.

**핵심 요약**:
- **데이터 품질**이 모델 크기보다 중요하다 (Phi 시리즈가 실증)
- **증류**와 **양자화**를 적절히 조합하면 10배 작은 모델로 80~90% 성능 달성 가능
- **엣지 배포**(0.5B~3B), **로컬 실행**(3B~7B), **서버 서빙**(7B~14B) 등 용도별 최적 구간이 명확하다
- SLM은 대형 모델을 **대체**하는 것이 아니라 **보완**하는 위치다
- 단순 분류, 요약, 코드 생성(단순) 등에서는 SLM으로 충분하며, 복잡한 추론은 여전히 LLM이 필요하다

SLM 기술은 빠르게 발전하고 있으며, "충분히 좋은"의 기준선은 해마다 높아지고 있다. [[quantization-guide|양자화]], [[distillation-guide|증류]], [[pruning-guide|가지치기]] 등 경량화 기법과 결합하면, SLM의 활용 범위는 앞으로 더 넓어질 것이다.
