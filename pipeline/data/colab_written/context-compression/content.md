# Context Compression: 긴 입력을 효율적으로 처리하기

## 들어가며

:::info
이 글은 LLM의 입력 비용과 지연시간을 줄이는 **Context Compression** 기법을 체계적으로 정리한다. [[long-context-techniques|Long Context 기법]]과 함께 읽으면 LLM의 입력 처리 전략 전반을 파악할 수 있다.
:::

LLM의 컨텍스트 윈도우가 100K~1M 토큰으로 확장되었지만, 길어진 입력은 곧바로 **비용 폭증**과 **지연시간 증가**로 이어진다. API 비용은 입력 토큰 수에 정비례하고, Prefill 시간은 시퀀스 길이의 제곱에 비례한다.

Context Compression은 LLM에 전달하는 입력을 **핵심만 남기고 압축**하여 비용과 지연시간을 줄이는 전략이다. 단순히 비용 절감에 그치지 않고, 불필요한 정보를 제거함으로써 LLM이 핵심에 집중하게 하여 **응답 품질 자체를 높이는 효과**도 있다.

이 글에서는 프롬프트 압축, 요약 기반 압축, 선택적 검색, KV-Cache 압축 등 주요 기법을 비교하고, 시나리오별 선택 가이드를 제시한다.

---

## 왜 압축이 필요한가

RAG 파이프라인에서 5개 문서(각 2,000 토큰)를 검색하여 LLM에 전달하는 경우를 생각하자:

| 방식 | 입력 토큰 | GPT-4o 비용 (per query) | 일일 10K 쿼리 월 비용 |
|------|----------|----------------------|-------------------|
| 전체 전달 | 10,000 | $0.025 | $7,500/월 |
| 50% 압축 | 5,000 | $0.0125 | $3,750/월 |
| 70% 압축 | 3,000 | $0.0075 | $2,250/월 |
| 80% 압축 | 2,000 | $0.005 | $1,500/월 |

80% 압축 시 월 $6,000을 절감할 수 있다. 서비스 규모가 클수록 이 차이는 더 극적으로 벌어진다.

## 지연시간과 품질 효과

### Prefill 시간 감소

[[inference-optimization-mfu|추론 최적화]]에서 다뤘듯이, Prefill 단계는 입력 길이에 크게 영향을 받는다. 시퀀스 길이에 따른 Attention 연산량은 $O(n^2)$이므로, 입력을 절반으로 줄이면 Prefill 연산량은 약 **1/4**로 감소한다.

| 입력 길이 | 상대 Prefill 시간 | TTFT 체감 |
|----------|-----------------|----------|
| 10,000 토큰 | 1.0x (기준) | ~500ms |
| 5,000 토큰 | ~0.25x | ~125ms |
| 2,000 토큰 | ~0.04x | ~20ms |

### "Lost in the Middle" 완화

[[long-context-techniques|Long Context]]에서 다뤘듯이, LLM은 긴 입력의 **중간에 위치한 정보를 무시하는 경향**이 있다. 입력이 10,000 토큰이면 중간 3,000~7,000 구간의 정보를 놓칠 수 있다. 압축을 통해 전체 길이를 줄이면 이 문제가 자연스럽게 완화된다.

## LLMLingua: 토큰 레벨 프롬프트 압축

Jiang et al.(2023)이 제안한 **토큰 레벨 프롬프트 압축** 기법이다. 작은 LLM(GPT-2 등)을 사용하여 각 토큰의 **perplexity(정보량)**를 측정하고, perplexity가 낮은 토큰(예측이 쉬운, 즉 중복적인 토큰)을 제거한다.

**작동 원리**:

1. 소형 언어 모델(GPT-2, LLaMA-7B 등)로 프롬프트의 각 토큰에 대해 perplexity 계산
2. 지시문(instruction), 질문(question), 데모(demonstration) 부분을 분리하여 **차등 압축**
3. 정보량이 높은 토큰(perplexity 높음)을 우선 보존
4. 지정된 압축률에 도달할 때까지 정보량 낮은 토큰 제거

```python
from llmlingua import PromptCompressor

compressor = PromptCompressor(
    model_name="microsoft/llmlingua-2-bert-base-multilingual-cased-meetingbank"
)

original_prompt = """
다음 문서들을 참고하여 질문에 답하세요.

문서 1: Transformer는 2017년 Google에서 발표한 아키텍처입니다.
Self-attention 메커니즘을 통해 시퀀스의 모든 위치 간
의존성을 학습합니다. 이전의 RNN/LSTM 대비 병렬 처리가
가능하여 학습 속도가 크게 향상되었습니다...

질문: Transformer의 핵심 메커니즘은?
"""

compressed = compressor.compress_prompt(
    original_prompt,
    rate=0.5,   # 50%로 압축
    force_tokens=["질문:", "답하세요"]  # 반드시 보존할 토큰
)

print(f"원본: {compressed['origin_tokens']} 토큰")
print(f"압축: {compressed['compressed_tokens']} 토큰")
print(f"압축률: {compressed['ratio']}")
print(f"압축 프롬프트: {compressed['compressed_prompt']}")
```

## LLMLingua-2와 LongLLMLingua

### LLMLingua-2

LLMLingua의 후속 연구로, 기존의 causal LM 기반 perplexity 대신 **BERT 기반 토큰 분류기**를 사용한다. 각 토큰을 "보존" 또는 "제거"로 분류하는 이진 분류 문제로 접근하여, 처리 속도가 LLMLingua 대비 **3~6배 빠르다**.

| 비교 항목 | LLMLingua | LLMLingua-2 |
|----------|-----------|-------------|
| 기반 모델 | GPT-2 / LLaMA (causal LM) | BERT (bidirectional) |
| 압축 방식 | Perplexity 기반 토큰 선택 | 이진 분류 기반 토큰 선택 |
| 처리 속도 | 1.0x (기준) | 3~6x 빠름 |
| 양방향 문맥 | 미활용 (단방향) | 활용 (양방향) |
| 다국어 지원 | 제한적 | multilingual BERT로 지원 |

### LongLLMLingua

RAG 시나리오에 특화된 버전이다. 핵심 차이점: **질문과의 관련성을 고려**하여 문서별로 다른 압축률을 적용한다.

- 관련성 높은 문서: 압축률 낮음 (정보 최대 보존)
- 관련성 낮은 문서: 압축률 높음 (핵심만 추출)
- 질문 토큰을 조건으로 perplexity를 재계산하여 **질문-인식(question-aware) 압축** 수행

## Selective Context

Li et al.(2023)이 제안한 기법으로, LLMLingua와 유사하게 소형 LM의 **self-information**을 기준으로 토큰을 필터링한다. 각 토큰의 self-information $I(t) = -\log P(t|context)$를 계산하고, 임계값 이하인 토큰을 제거한다.

LLMLingua와의 차이:

| 비교 항목 | Selective Context | LLMLingua |
|----------|------------------|-----------|
| 기준 지표 | Self-information | Perplexity |
| 질문 인식 | 없음 | 있음 (LongLLMLingua) |
| 차등 압축 | 없음 (균일) | 있음 (구간별) |
| 구현 복잡도 | 낮음 | 중간 |

Selective Context는 구현이 간단하여 빠르게 적용하기에 좋지만, 질문을 고려하지 않으므로 RAG 환경에서는 LongLLMLingua가 더 적합하다.

## RECOMP: 학습 기반 압축

Xu et al.(2023)이 제안한 기법으로, 검색된 문서를 **요약하여 압축하는 전용 모델**을 학습시킨다. 두 가지 접근법을 제시한다:

**Extractive RECOMP**: 검색된 문서에서 질문에 관련된 **문장을 선택**하여 추출한다. 각 문장의 유용성 점수를 계산하여 상위 문장만 컨텍스트로 전달한다.

**Abstractive RECOMP**: 검색된 문서를 바탕으로 질문에 맞는 **요약문을 새로 생성**한다. 인코더-디코더 모델(T5 등)을 활용하며, LLM의 성능을 기준으로 학습(distillation)한다.

| 비교 항목 | Extractive RECOMP | Abstractive RECOMP |
|----------|-------------------|-------------------|
| 출력 | 원문 문장 선택 | 새 요약문 생성 |
| 충실도 | 높음 (원문 그대로) | 중간 (재작성) |
| 압축률 | 중간 (60~80%) | 높음 (80~95%) |
| 모델 크기 | 작음 (문장 분류기) | 중간 (T5-base) |

## AutoCompressor: 내부 표현 압축

Chevalier et al.(2023)이 제안한 기법으로, LLM 자체를 확장하여 긴 컨텍스트를 **소수의 "summary token"으로 압축**한다.

작동 방식:
1. 긴 문서를 세그먼트 단위로 나눈다
2. 각 세그먼트를 LLM에 통과시켜 **summary vector**를 생성한다
3. 다음 세그먼트 처리 시 이전 summary vector를 soft prompt로 주입한다
4. 최종적으로 전체 문서가 소수의 벡터로 압축된다

장점: 매우 높은 압축률 (수천 토큰을 수십 개 벡터로)

한계: LLM의 추가 학습이 필요하고, 범용 LLM API에서는 사용 불가하다.

---

## 문서 요약 기반 압축

LLM 자체를 사용하여 긴 문서를 **핵심 요약**으로 변환한 후, 요약을 컨텍스트로 사용하는 직관적인 방법이다.

```python
def hierarchical_summarize_and_query(documents, query, llm):
    """계층적 요약 + 질의 파이프라인"""
    # 1단계: 각 문서 요약 (병렬 처리 가능)
    summaries = []
    for doc in documents:
        summary = llm.invoke(
            f"다음 문서에서 '{query}'와 관련된 핵심 정보를 3문장으로 요약하라:\n{doc}"
        )
        summaries.append(summary)

    # 2단계: 요약을 컨텍스트로 사용하여 질의
    context = "\n---\n".join(summaries)
    answer = llm.invoke(f"Context:\n{context}\n\nQuestion: {query}")
    return answer
```

| 장점 | 단점 |
|------|------|
| 구현이 직관적이고 간단 | 요약 과정에서 세부 정보 손실 |
| 기존 LLM API만으로 가능 | 요약 호출 자체의 API 비용 발생 |
| 질문 맞춤 요약 가능 | 지연시간 증가 (LLM 이중 호출) |
| 다국어 지원 자연스러움 | 요약의 품질이 LLM 성능에 의존 |

## 선택적 검색과 Reranking

처음부터 **정확하게 검색**하여 불필요한 문서를 제외하는 전략이다. 압축이 아닌 **정밀한 선별**로 입력 토큰을 줄인다.

```python
# 1단계: 넓은 검색으로 후보군 확보 (top-20)
candidates = hybrid_search(query, top_k=20)

# 2단계: Cross-Encoder Reranking으로 정밀 선택 (top-3)
reranked = cross_encoder_rerank(query, candidates, top_k=3)

# 결과: 3개 문서만 LLM에 전달 (20개 -> 3개 = 85% 감소)
```

[[hybrid-search-reranking|하이브리드 검색 + Reranking]]이 이 전략의 핵심이다. 검색 정확도를 높여 처음부터 LLM에 전달할 문서 수를 최소화한다.

## 청크 크기 최적화

RAG에서 청크 크기를 줄이면 각 검색 결과의 토큰 수가 줄어든다:

| 청크 크기 | 검색 결과 5개 시 총 토큰 | top-3 시 총 토큰 | 비고 |
|----------|---------------------|-----------------|------|
| 1,000 토큰 | 5,000 | 3,000 | 문맥 풍부 |
| 500 토큰 | 2,500 | 1,500 | 균형점 |
| 200 토큰 | 1,000 | 600 | 문맥 부족 위험 |

너무 작은 청크는 **컨텍스트가 부족**하여 검색 품질이 저하된다. 200~500 토큰이 일반적인 균형점이다. Parent-Child chunking(작은 청크로 검색하되 부모 청크를 반환)으로 이 한계를 극복할 수도 있다.

## KV-Cache가 문제인 이유

KV-Cache 압축은 프롬프트 텍스트 자체가 아닌, LLM 추론 시 생성되는 **Key-Value Cache의 메모리 사용량을 줄이는** 기법이다. 서빙 인프라 레벨에서 적용되며, 사용자에게는 투명하게 동작한다.

Transformer의 Decode 단계에서는 이전 토큰들의 Key, Value 텐서를 캐싱하여 재연산을 방지한다. 이 캐시는 시퀀스 길이에 비례하여 증가한다:

$$\text{KV-Cache 크기} = 2 \times L \times H \times d \times s \times \text{dtype\_bytes}$$

- $L$: 레이어 수, $H$: 어텐션 헤드 수, $d$: 헤드 차원, $s$: 시퀀스 길이

LLaMA-3 70B 기준, 시퀀스 길이별 KV-Cache 크기:

| 시퀀스 길이 | KV-Cache (FP16) | 비율 (모델 대비) |
|-----------|----------------|---------------|
| 2,048 | 2.5 GB | 1.8% |
| 8,192 | 10 GB | 7.1% |
| 32,768 | 40 GB | 28.6% |
| 131,072 | 160 GB | 114% (모델보다 큼) |

긴 시퀀스에서 KV-Cache가 **모델 가중치보다 더 큰 메모리**를 차지하게 된다. 배치 처리 시에는 이 문제가 더욱 심각해진다.

---

## KV-Cache 양자화

KV-Cache의 Key, Value 텐서를 FP16에서 **INT8 또는 INT4로 양자화**하여 메모리를 절반~1/4로 줄이는 기법이다.

| 양자화 방식 | 메모리 절감 | 품질 영향 | 구현 난이도 |
|-----------|----------|---------|----------|
| FP16 (기준) | 0% | 없음 | 기본값 |
| INT8 (per-channel) | 50% | 거의 없음 | 낮음 |
| INT4 (per-group) | 75% | 약간 | 중간 |
| FP8 (E4M3) | 50% | 거의 없음 | 낮음 |
| 혼합 (Key=INT4, Value=INT8) | ~62% | 미미 | 중간 |

vLLM, TensorRT-LLM 등의 추론 엔진에서 플래그 하나로 활성화할 수 있다.

## KV-Cache Eviction과 Merging

### Eviction (토큰 퇴거)

시퀀스 전체의 KV-Cache를 유지하는 대신, **중요하지 않은 토큰의 캐시를 제거**하는 기법이다.

**H2O (Heavy-Hitter Oracle)**: Attention score가 높은 "Heavy Hitter" 토큰의 KV만 유지하고, 나머지를 제거한다. 최근 연구에 따르면 전체 토큰의 20~30%만으로도 full KV-Cache 대비 90% 이상의 성능을 유지한다.

**StreamingLLM**: 처음 몇 개 토큰(attention sink)과 최근 토큰의 KV만 유지하는 방식이다. 무한 길이 스트리밍 추론에 적합하다.

| Eviction 전략 | 유지 토큰 | 압축률 | 성능 유지 | 적합 시나리오 |
|--------------|---------|-------|---------|------------|
| H2O | Top-K attention 토큰 | 70~80% | 높음 | 일반 추론 |
| StreamingLLM | Sink + Recent | 80~95% | 중간 | 무한 스트리밍 |
| Scissorhands | 빈도 기반 선택 | 60~80% | 높음 | 배치 추론 |

### Merging

유사한 토큰의 Key-Value를 **병합**하여 캐시 크기를 줄이는 기법이다. 인접 토큰의 Key 벡터가 유사한 경우, 가중 평균으로 병합한다. Eviction과 달리 정보 손실이 더 적다는 장점이 있다.

## 압축률별 성능 트레이드오프

압축률에 따른 성능 변화의 일반적인 패턴:

| 압축률 | 성능 변화 | 주로 제거되는 정보 | 권장 시나리오 |
|-------|---------|---------------|------------|

| 30~50% | 미미 | 부연 설명, 예시의 일부 | 일반 프로덕션 |

| 70~85% | 유의미한 저하 | 핵심 정보 일부 손실 시작 | 고빈도 저복잡도 쿼리 |
| 85~95% | 심각한 저하 | 핵심 정보 대량 손실 | 비권장 |

:::tip
**실전 권장**: 50~60% 압축률이 비용 절감과 품질 유지의 최적 균형점이다. 이 구간에서는 대부분의 벤치마크에서 5% 미만의 성능 저하로 토큰 비용을 절반 이상 줄일 수 있다.
:::

## RAG에서의 컨텍스트 최적화

### 계층적 압축 파이프라인

RAG 시스템에서는 여러 압축 기법을 **계층적으로 조합**하여 효과를 극대화할 수 있다:

```
질문 -> 넓은 검색(top-20) -> Reranking(top-5) -> 프롬프트 압축(50%) -> LLM
```

각 단계에서의 토큰 감소:

| 단계 | 문서 수 | 총 토큰 | 누적 감소율 |
|------|--------|--------|-----------|
| 초기 검색 (top-20) | 20 | 20,000 | 0% |
| Reranking (top-5) | 5 | 5,000 | 75% |
| 프롬프트 압축 (50%) | 5 | 2,500 | 87.5% |
| **최종** | **5** | **2,500** | **87.5%** |

### 적응적 컨텍스트 길이

질문의 복잡도에 따라 컨텍스트 양을 **동적으로 조절**하면 평균 비용을 더 줄일 수 있다:

| 질문 유형 | 필요 컨텍스트 | 검색 전략 | 압축 전략 |
|----------|------------|---------|---------|
| 단순 사실 확인 | 1~2 청크 | top-3 + rerank top-1 | 불필요 |
| 비교/분석 | 3~5 청크 | top-10 + rerank top-5 | 50% 압축 |
| 종합적 요약 | 5~10 청크 | top-20 + rerank top-10 | 60~70% 압축 |
| 멀티홉 추론 | 3~5 청크 (다단계) | 반복 검색 | 단계별 요약 |

## 시나리오별 선택 가이드

### Long Document QA

문서 길이 10,000~100,000 토큰의 단일 문서에 대한 질의응답.

| 권장 기법 | 이유 |
|----------|------|
| LLMLingua / LLMLingua-2 | 단일 문서의 토큰 레벨 압축에 최적 |
| Selective Context | 간단한 구현으로 빠른 적용 |
| KV-Cache Eviction | 서빙 레벨에서 투명하게 적용 가능 |

### Multi-turn Chat

대화 히스토리가 누적되어 컨텍스트가 증가하는 시나리오.

| 권장 기법 | 이유 |
|----------|------|
| 대화 요약 (오래된 턴 요약) | 이전 대화를 압축하여 최근 대화에 집중 |
| StreamingLLM (KV-Cache) | 무한 대화 스트리밍에 적합 |
| 슬라이딩 윈도우 + 요약 | 최근 N턴은 전체 유지, 나머지는 요약 |

### RAG 파이프라인

검색된 다수의 문서 청크를 LLM에 전달하는 시나리오.

| 권장 기법 | 이유 |
|----------|------|
| 선택적 검색 + Reranking | 검색 정확도 자체를 높여 불필요한 문서 배제 |
| LongLLMLingua | 질문 인식 압축으로 RAG에 최적화 |
| RECOMP | 학습된 요약 모델로 검색 결과 압축 |
| 청크 크기 최적화 | 인프라 레벨에서 기본 적용 |

### 서빙 인프라 최적화

모델 서빙 엔진 레벨에서 적용하는 시나리오.

| 권장 기법 | 이유 |
|----------|------|
| KV-Cache INT8 양자화 | 품질 저하 없이 메모리 50% 절감 |
| KV-Cache Eviction (H2O) | 배치 크기 증가로 처리량 향상 |
| PagedAttention (vLLM) | KV-Cache 메모리 단편화 해소 |

## 기법 조합 전략

단일 기법이 아닌 **여러 기법을 조합**하면 효과가 배가된다.

| 조합 | 총 압축률 | 적합 시나리오 | 복잡도 |
|------|---------|------------|-------|
| Reranking + LLMLingua | ~90% | 프로덕션 RAG | 중간 |
| 청크 최적화 + Reranking | ~85% | 간단한 RAG | 낮음 |
| 대화 요약 + LLMLingua | ~80% | 멀티턴 챗봇 | 중간 |
| RECOMP + KV-Cache 양자화 | ~87% | 고성능 RAG 서빙 | 높음 |
| 전체 파이프라인 (검색+압축+KV) | ~95% | 대규모 서비스 | 높음 |

## 정리

| 기법 | 적용 레벨 | 압축률 | 추가 비용 | 품질 유지 | 구현 난이도 |
|------|---------|-------|---------|---------|----------|
| LLMLingua | 프롬프트 전처리 | 50~80% | 낮음 | 높음 | 낮음 |
| LongLLMLingua | RAG 전처리 | 50~80% | 낮음 | 매우 높음 | 중간 |
| RECOMP | 검색 후처리 | 70~90% | 중간 | 높음 | 높음 |
| Selective Context | 프롬프트 전처리 | 40~60% | 낮음 | 중간 | 낮음 |
| AutoCompressor | 모델 내부 | 50~90% | 높음 | 중간 | 매우 높음 |
| 문서 요약 | 프롬프트 전처리 | 70~90% | 높음 | 중간 | 낮음 |
| 선택적 검색 | 검색 단계 | 60~85% | 중간 | 높음 | 중간 |
| 청크 최적화 | 인덱싱 | 50~75% | 없음 | 중간 | 낮음 |
| KV-Cache 양자화 | 추론 엔진 | 50~75% | 없음 | 높음 | 낮음 |
| KV-Cache Eviction | 추론 엔진 | 30~80% | 없음 | 중간~높음 | 중간 |

Context Compression은 **"더 많은 정보를 넣는 것"에서 "더 좋은 정보만 넣는 것"**으로의 패러다임 전환이다. 실전에서는 단일 기법이 아닌 **계층적 조합**(검색 정밀화 + 프롬프트 압축 + KV-Cache 최적화)으로 최대 효과를 달성할 수 있다. 핵심은 자신의 시나리오에 맞는 조합을 찾는 것이며, 50~60% 압축률에서 시작하여 성능 모니터링과 함께 점진적으로 최적화해 나가는 것을 권장한다.
