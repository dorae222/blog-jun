# CrewAI: 역할 기반 AI 에이전트 오케스트레이션

**CrewAI Inc.** · **2024-01-01** · **Multi-Agent Framework** · **MIT**

## 개요

CrewAI는 역할 기반 멀티 에이전트 오케스트레이션 프레임워크로, AI 에이전트를 '크루(crew)' 단위로 조직하여 복잡한 작업을 분업 처리하도록 설계되었다. 2024년 초 CrewAI Inc.가 공개한 이 오픈소스 프레임워크는, AutoGen의 대화 중심 접근 방식과 달리 선언적 API를 통해 에이전트 역할과 태스크를 명확히 분리하여 직관적인 워크플로 구성을 가능하게 한다.

CrewAI의 핵심 비유는 **실제 회사 조직**이다. 리서처, 작가, 편집자처럼 각 에이전트에 명확한 역할(role), 목표(goal), 배경(backstory)을 부여하고, 이들이 정해진 태스크를 순차적 또는 계층적으로 처리한다. 이 직관적인 추상화 덕분에 프로그래밍 경험이 적은 사용자도 쉽게 멀티 에이전트 시스템을 구축할 수 있어, 빠른 속도로 커뮤니티가 성장했다.

멀티 에이전트 프레임워크 선택에서 핵심 트레이드오프는 **사용 편의성 vs 유연성**이다. AutoGen은 자유로운 대화를 통해 높은 유연성을 제공하지만 학습 곡선이 가파르고, LangGraph는 그래프 기반으로 정밀한 제어가 가능하지만 보일러플레이트가 많다. CrewAI는 이 스펙트럼에서 "사용 편의성" 측에 위치하며, 가장 적은 코드로 프로덕션 수준의 멀티 에이전트 시스템을 구축할 수 있다.

## 아키텍처 상세

CrewAI의 아키텍처는 세 가지 핵심 추상화를 중심으로 구성된다.

### Agent

역할, 목표, 배경 스토리를 가진 자율적 단위다. 각 에이전트는 독립적인 LLM 설정과 도구 목록을 보유한다.

에이전트의 역할 기반 설계는 프롬프트 엔지니어링의 **페르소나 기법(persona prompting)**을 구조적으로 확장한 것이다. 단순히 "너는 연구원이다"라는 시스템 프롬프트를 넘어서, `role`, `goal`, `backstory` 세 가지 속성이 에이전트의 행동을 다층적으로 제약한다. `role`은 에이전트의 정체성을, `goal`은 최적화 목표를, `backstory`는 도메인 전문성과 의사결정 스타일을 결정한다. 이 삼중 구조 덕분에 LLM은 단일 시스템 프롬프트보다 훨씬 일관된 전문가 행동을 생성한다.

또한 각 에이전트는 `allow_delegation` 파라미터를 통해 자신의 작업을 다른 에이전트에게 위임할 수 있다. 예를 들어, 편집자 에이전트가 팩트체킹이 필요한 부분을 발견하면 리서처 에이전트에게 검증을 위임하는 것이 가능하다. 이 위임 메커니즘은 에이전트 간의 동적 협업을 가능하게 하며, 정적인 태스크 할당의 한계를 보완한다.

### Task

에이전트가 수행할 구체적 작업 명세다. 설명, 기대 출력, 담당 에이전트를 정의하며, `context` 파라미터로 이전 태스크의 결과를 참조할 수 있다.

태스크 분해(task decomposition)는 CrewAI 워크플로 설계의 핵심이다. 복잡한 목표를 원자적 단위의 태스크로 분해하고, 각 태스크를 가장 적합한 에이전트에 할당하는 과정이 시스템 성능을 좌우한다. `context` 파라미터를 통한 태스크 체이닝은 이전 태스크의 출력을 다음 태스크의 입력으로 전달하여, 정보 흐름을 명시적으로 관리한다. 이는 암묵적 대화 기록에 의존하는 AutoGen과의 핵심적인 차이점이다.

태스크에는 `output_file`, `output_json`, `output_pydantic` 등의 출력 형식 지정 옵션이 있어, 구조화된 데이터를 다음 단계로 전달하거나 파일로 저장할 수 있다. `human_input=True` 옵션을 활성화하면 태스크 완료 전에 사용자 검토를 요청하는 human-in-the-loop 패턴도 구현 가능하다.

### Crew

에이전트와 태스크의 조합으로, 실행 프로세스 타입과 전체 설정을 정의한다.

```python
from crewai import Agent, Task, Crew, Process

# 에이전트 정의
researcher = Agent(
    role="시니어 리서처",
    goal="최신 AI 트렌드에 대한 심층 분석 제공",
    backstory="10년 경력의 AI 연구원으로 논문 분석에 전문성이 있다",
    tools=[search_tool, arxiv_tool],
    llm="gpt-4"
)

writer = Agent(
    role="기술 블로거",
    goal="복잡한 기술 주제를 일반 독자가 이해하기 쉬운 글로 변환",
    backstory="기술 매거진에서 5년간 기고한 프리랜서 작가",
    llm="claude-3-5-sonnet"
)

editor = Agent(
    role="편집장",
    goal="글의 정확성, 가독성, SEO 최적화를 검증",
    backstory="미디어 업계 15년 경력의 편집 전문가",
    llm="gpt-4o"
)

# 태스크 정의
research_task = Task(
    description="2025년 AI 에이전트 프레임워크 동향을 조사하라",
    expected_output="핵심 트렌드 5가지와 각각의 상세 분석",
    agent=researcher
)

writing_task = Task(
    description="조사 결과를 바탕으로 블로그 포스트를 작성하라",
    expected_output="2000자 이상의 기술 블로그 글",
    agent=writer,
    context=[research_task]
)

editing_task = Task(
    description="블로그 포스트의 품질을 검토하고 최종 수정하라",
    expected_output="발행 가능한 최종 원고",
    agent=editor,
    context=[writing_task]
)

# 크루 실행
crew = Crew(
    agents=[researcher, writer, editor],
    tasks=[research_task, writing_task, editing_task],
    process=Process.sequential
)

result = crew.kickoff()
```

### 프로세스 타입

| 프로세스 | 실행 방식 | 적합한 상황 |
|---------|----------|------------|
| Sequential | 태스크가 정의된 순서대로 실행 | 의존성이 명확한 파이프라인 |
| Hierarchical | 매니저 에이전트가 위임 | 동적 의사결정이 필요한 작업 |
| Consensual | 에이전트 간 합의 (실험적) | 품질 검증이 중요한 작업 |

**Sequential 프로세스**는 가장 단순하고 예측 가능한 실행 방식이다. 태스크 A의 출력이 태스크 B의 입력이 되는 파이프라인 패턴에 적합하며, 디버깅과 결과 추적이 용이하다.

**Hierarchical 프로세스**는 별도의 매니저 에이전트를 자동으로 생성하여, 정의된 태스크들을 동적으로 할당한다. 매니저는 각 에이전트의 역할과 능력을 파악하고, 태스크의 요구사항에 따라 최적의 에이전트를 선택한다. 결과물이 기대에 미치지 못하면 재작업을 지시하거나 다른 에이전트에게 재할당할 수도 있다. 이 방식은 실제 조직의 관리자-실무자 관계를 모사하며, 복잡한 프로젝트에서 유연한 리소스 배분이 가능하다.

### 메모리 시스템

CrewAI는 에이전트의 학습과 적응을 위한 다층 메모리 시스템을 제공한다.

- **단기 메모리(Short-term Memory)**: 현재 크루 실행 내에서의 대화 맥락과 중간 결과를 저장한다. 태스크 간 정보 전달과 에이전트 간 협업의 기반이 된다.
- **장기 메모리(Long-term Memory)**: 여러 실행에 걸쳐 축적된 경험과 패턴을 저장한다. SQLite 기반으로 구현되며, 에이전트가 과거 성공/실패 사례를 참조하여 점진적으로 성능을 개선할 수 있다.
- **엔티티 메모리(Entity Memory)**: 태스크 수행 중 등장하는 핵심 개체(인물, 조직, 개념 등)에 대한 구조화된 정보를 추출하고 저장한다. 이를 통해 에이전트가 도메인 지식을 점진적으로 구축할 수 있다.

메모리 시스템은 `memory=True` 설정으로 활성화되며, RAG(Retrieval-Augmented Generation) 패턴과 유사하게 관련 기억을 검색하여 에이전트의 프롬프트에 주입한다.

### 도구 생태계

CrewAI는 LangChain 도구와 완벽히 호환되며, 자체 도구 데코레이터(`@tool`)를 통해 커스텀 도구를 쉽게 정의할 수 있다.

```python
from crewai_tools import tool

@tool("데이터베이스 조회")
def query_database(query: str) -> str:
    """SQL 쿼리를 실행하여 결과를 반환한다"""
    result = db.execute(query)
    return str(result)
```

기본 제공 도구로는 `SerperDevTool`(웹 검색), `ScrapeWebsiteTool`(웹 스크래핑), `FileReadTool`(파일 읽기), `PDFSearchTool`(PDF 검색), `CodeInterpreterTool`(코드 실행) 등이 있다. 에이전트는 도구를 자율적으로 선택하고 실행하며, 도구 실행 결과를 기반으로 다음 행동을 결정하는 ReAct(Reasoning + Acting) 패턴을 따른다.

## 핵심 혁신

1. **선언적 에이전트 정의**: Agent, Task, Crew의 세 가지 추상화만으로 복잡한 멀티 에이전트 시스템을 구축할 수 있다. AutoGen의 명시적 대화 관리에 비해 코드량이 $\frac{1}{3}$ 이하로 줄어든다.

2. **역할 기반 전문화**: 각 에이전트에 역할과 배경을 부여함으로써, LLM이 해당 전문가의 관점에서 사고하도록 유도한다. 이는 프롬프트 엔지니어링의 페르소나 기법을 구조화한 것이다.

3. **에이전트별 LLM 독립 설정**: 비용이 많이 드는 분석 작업에는 GPT-4를, 단순 요약에는 GPT-4o-mini를 사용하는 등 태스크 특성에 맞는 모델 배분이 가능하다.

4. **계층적 프로세스**: 매니저 에이전트가 자동으로 작업을 분배하고 결과를 검증하는 계층적 구조를 프레임워크 수준에서 지원한다.

### LangGraph와의 상세 비교

LangGraph는 상태 그래프(stateful graph)를 명시적으로 정의하여 에이전트의 실행 흐름을 제어한다. 노드(처리 단계)와 엣지(조건부 분기)로 구성된 그래프를 통해 복잡한 조건부 로직, 루프, 병렬 실행을 세밀하게 제어할 수 있다. 반면 CrewAI는 이러한 제어 흐름을 프레임워크 내부에 추상화하여 사용자가 "무엇을(what)" 할지만 정의하면 "어떻게(how)" 실행할지는 프레임워크가 결정한다. 따라서 **정밀한 흐름 제어가 필요한 경우 LangGraph**, **빠른 프로토타이핑과 직관적 구성이 필요한 경우 CrewAI**가 적합하다.

### AutoGen과의 상세 비교

AutoGen은 에이전트 간 자유로운 대화(conversation)를 통해 협업이 이루어진다. 각 에이전트가 메시지를 주고받으며 자율적으로 문제를 해결하는 방식으로, 예측하기 어려운 창발적 행동이 나타날 수 있다. CrewAI는 이와 달리 태스크 단위의 명시적 실행 흐름을 강제하여 결과의 재현성과 예측 가능성을 높인다. AutoGen이 "토론"에 가깝다면, CrewAI는 "업무 분장표"에 가까운 패러다임이다.

## 구현

**콘텐츠 제작 파이프라인**: 리서처 $\rightarrow$ 작가 $\rightarrow$ 편집자 크루를 구성하여, 주제 조사부터 초안 작성, 교정까지의 콘텐츠 제작 프로세스를 자동화한다.

**고객 지원 에스컬레이션**: 1차 상담 에이전트, 기술 전문가 에이전트, 매니저 에이전트로 구성된 크루가 고객 문의를 분류하고 적절한 수준에서 처리한다.

**시장 분석 보고서**: 데이터 수집 에이전트, 분석 에이전트, 시각화 에이전트, 보고서 작성 에이전트가 협업하여 포괄적인 시장 분석 보고서를 생성한다.

**코드 리뷰 자동화**: 코드 분석 에이전트가 정적 분석과 패턴 검출을 수행하고, 보안 전문가 에이전트가 취약점을 검토하며, 리뷰어 에이전트가 최종 피드백을 통합하여 구조화된 코드 리뷰를 생성한다.

**데이터 파이프라인 모니터링**: 데이터 수집기 에이전트가 메트릭을 수집하고, 분석가 에이전트가 이상치를 탐지하며, 대응 에이전트가 자동 복구 또는 알림을 생성하는 계층적 크루로 데이터 파이프라인을 모니터링한다.

## 한계 및 과제

1. **LLM 호출 비용**: 멀티 에이전트 시스템은 본질적으로 단일 에이전트보다 많은 LLM 호출을 발생시킨다. 에이전트 간 위임이 활발한 계층적 프로세스에서는 비용이 기하급수적으로 증가할 수 있다. 단순한 작업에 멀티 에이전트를 적용하면 오버엔지니어링이 될 수 있으므로, 복잡도와 비용 간의 균형을 신중히 판단해야 한다.

2. **디버깅 어려움**: 에이전트 간의 상호작용이 복잡해질수록 문제 원인을 추적하기 어렵다. 특히 계층적 프로세스에서 매니저의 위임 결정이 의도와 다를 때, 어떤 에이전트의 어떤 판단이 잘못되었는지 파악하기 쉽지 않다. `verbose=True` 모드로 실행 로그를 확인할 수 있지만, 로그 자체가 방대해져 분석이 부담스럽다.

3. **제한적 제어 흐름**: 조건부 분기, 동적 루프, 병렬 실행 등 복잡한 제어 흐름을 구현하기 어렵다. Sequential과 Hierarchical 두 가지 모드 외에는 사용자가 실행 흐름을 세밀하게 커스터마이징하기 어려우며, 이 점에서 LangGraph에 비해 유연성이 부족하다.

4. **메모리 시스템의 미성숙**: 장기 메모리와 엔티티 메모리가 제공되지만, 대규모 프로덕션 환경에서의 안정성과 스케일링이 충분히 검증되지 않았다. 메모리 검색의 정확도나 관련성 판단이 때때로 부정확하며, 메모리가 축적될수록 노이즈가 증가하는 문제가 있다.

5. **결과 품질의 비결정성**: 동일한 크루 설정으로 동일한 입력을 처리해도 결과가 매번 다를 수 있다. LLM의 확률적 특성에 의한 것이지만, 멀티 에이전트에서는 각 단계의 변동이 누적되어 최종 결과의 분산이 더욱 커진다. 프로덕션 환경에서 일관된 품질을 보장하기 위해서는 `temperature=0` 설정과 출력 검증 로직이 필수적이다.

## 관련 모델

CrewAI는 AutoGen의 멀티 에이전트 협업 아이디어에서 영감을 받아, 선언적 API와 역할 기반 추상화로 사용 편의성을 극대화했다. LangChain 도구 생태계와의 호환성이 높으며, CrewAI Enterprise를 통해 에이전트 모니터링, 배포, 비용 추적 기능을 제공한다.
